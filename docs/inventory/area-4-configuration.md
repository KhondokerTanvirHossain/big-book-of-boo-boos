## Area 4 — configuration (reconciled 2026-09-17)

### 4.1 Server config keys, Project settings/secrets, feature flags


Source snapshot: medplum `main` @ `fbc8e7b4b` (2026-09-11, server 5.1.x); big-book @ `45dc7b0` (ADR-006 decided). `Source` paths are relative to `packages/server/src` unless stated; `Project.d.ts` = `packages/fhirtypes/dist/Project.d.ts`. Docs snapshot `docs/medplum-docs/self-hosting/{server-config,setting-configuration,project-settings}.md` scraped 2026-09-12.

Disposition vocabulary (per the area brief): `keep` (Big Book needs an equivalent — proposed Spring property given), `→ HAPI` (HAPI/Spring already has it — property named), `→ Keycloak` (realm/client config), `wire Keycloak` (Table B only), `drop` (Medplum- or AWS-specific / non-goal, with reason), `defer v0.x`.

Every key in Table A is declared in `config/types.ts` (`MedplumServerConfig` and its nested interfaces). Defaults come from `config/utils.ts:17-84` (`addDefaults`) unless the "Default" cell says otherwise; a bare `—` means no default is applied anywhere and the value is `undefined` at runtime. "Required?" means *required for the server to start or for the named feature to work*, not "declared non-optional in TypeScript" — the only key whose absence throws at load time is `baseUrl` (`config/loader.ts:63-65`).

#### Table B — Project settings / secrets / systemSettings

**Structural facts established by the read-site sweep:**

- There is **no generic accessor** — no `getProjectSetting`, `getSystemSetting`, `getProjectSecret` anywhere in `packages/server/src` or `packages/core/src`. Every read is an inline `find()` against one named field. Consequently **`systemSetting` never falls back to `setting`** (and vice versa): each name lives in exactly one field, fixed by its call site. Only domain-specific wrappers exist (`getProjectSmtpConfig`, `isMfaRequired`, `getUserFhirQuota`, …).
- `Project.systemSecret` is **never read by name** — it is only merged wholesale into the bot secrets map (PS-033).
- `config.defaultProjectSystemSetting` (CFG-125) is a **seed applied at project creation only** (`fhir/operations/projectinit.ts:174`), not a runtime fallback. There is no `defaultProjectSetting`/`defaultProjectSecret`/`defaultProjectSystemSecret`.
- Access-policy exposure (`fhir/accesspolicy.ts:341-348`): to a **project admin**, `systemSetting` is readonly and `systemSecret`/`superAdmin`/`strictMode` are hidden — admins read/write `setting` + `secret` only. To a **non-admin member**, all four fields are hidden.
- `ProjectSetting` value slots are `valueString` | `valueBoolean` | `valueInteger` | `valueDecimal` (`Project.d.ts:252-278`); no `valueDecimal` name is used by any read site.

#### Notes

##### (a) The loader precedence chain, the env name-mangling rule, and BB-R-011.3

**How a key is resolved, exactly.**

1. The server takes **one** config identifier: `runFromCli` passes `argv[2]`, defaulting to `file:medplum.config.json` (`index.ts:61`). There is no `MEDPLUM_CONFIG` environment variable and no implicit env reading.
2. That identifier is split on commas (`loader.ts:49`). Each segment is one source, resolved by prefix (`loader.ts:78-94`):
   - `file:<path>` — `JSON.parse(readFileSync(path))`, path relative to the runtime cwd (`loader.ts:276-278`).
   - `env` — every `MEDPLUM_*` environment variable (`loader.ts:173-268`).
   - `aws:<[region:]ssm-path-prefix>` — `GetParametersByPath` with `WithDecryption: true`, paginated (`cloud/aws/config.ts:17-70`).
   - `gcp:<projectId>:<secretId>` — one GCP Secret Manager secret whose payload is a flat JSON map (`cloud/gcp/config.ts:35-47`).
   - `azure:<vaultHost>:<secretName>` — one Azure Key Vault secret, same flat-map shape (`cloud/azure/config.ts:39-51`).
   - anything else → `throw new Error('Unrecognized config type: ' + configType)`.
3. Segments are loaded **left to right and deep-merged, later wins** (`loader.ts:54-61`). `deepMerge` (`loader.ts:102-121`): objects recurse, **arrays replace wholesale**, primitives overwrite.
4. `baseUrl` is then checked; absent/blank/non-string → throw (`loader.ts:63-65`). This is the **only** required-key check in the whole loader.
5. `addDefaults` fills the ~35 defaulted keys (`config/utils.ts:17-84`), including the auto-generated signing key.
6. `warnInvalidDataWarehouseConfig` logs (never throws) if `dataWarehouse.enabled` is set with bad config (`validate-config.ts:93-102`). There is **no** other validation — no schema, no unknown-key rejection, no type check beyond the env coercion below.

**So: precedence is positional, not source-ranked.** `file:x.json,env` means env wins; `env,file:x.json` means the file wins; `file:x.json` alone never reads any `MEDPLUM_*` variable. Medplum's own `setting-configuration.md` claims "environment variables will take precedence" when both are present — **false** (T38 above).

Within the AWS loader there is a second, internal precedence: the seven `*Secrets` pseudo-keys (CFG-153..159) are resolved **first** into whole objects, then all remaining parameters are applied over them (`cloud/aws/config.ts:41-67`), so `/medplum/prod/database.maxConnections` overrides a value that came from the Secrets Manager blob.

**The env name-mangling rule** (`loader.ts:173-267`), exactly:

1. Skip any variable not starting with `MEDPLUM_`; strip that prefix.
2. Match a **section prefix**, in this order (first match wins) — `DATABASE_`, `READONLY_DATABASE_`, `CACHE_REDIS_`, `RATE_LIMIT_REDIS_`, `PUBSUB_REDIS_`, `BACKGROUND_JOBS_REDIS_`, `REDIS_`, `SMTP_`, `BULLMQ_`, `FISSION_`, `WORKERS_`, `DATA_WAREHOUSE_`. Strip it and target that sub-object. Note `REDIS_` is tested **after** the four qualified redis prefixes, which is why `MEDPLUM_RATE_LIMIT_REDIS_HOST` does not land in `redis`.
3. Inside `DATABASE_` and `READONLY_DATABASE_` only, a further `SSL_` prefix targets `…​.ssl`. **No other nesting is reachable from env** — `capabilityStatement.*`, `workers.bullmq.<worker>`, `arrayColumnPadding.*` and `database.ssl.*` beyond the flat leaves cannot be expressed except as a whole-object JSON string.
4. Lower-case the remainder, then replace `_x` with `X`: `MAX_CONNECTIONS` → `max_connections` → `maxConnections`. This is why `MEDPLUM_DATABASE_MAXCONNECTIONS` silently produces the useless key `maxconnections` — **unknown keys are never rejected**, they are just stored and ignored.
5. Coerce the string by consulting `isIntegerConfig` / `isFloatConfig` / `isBooleanConfig` / `isObjectConfig` / `isArrayConfig` with **both** the dotted path and the bare leaf (`loader.ts:250-264`). Integers → `parseInt`, booleans → `value === 'true'` (so `"1"`, `"yes"`, `"TRUE"` all mean **false**), objects → `JSON.parse` (throws on bad JSON), arrays → comma-split with trim, everything else stays a string.
6. Consequence: a key that is in none of those sets stays a **string**. `heartbeatEnabled`, `saveAuditEvents`, `autoDownloadEnabled`, `dispatchEnabled`, `subscriptionsEnabled`, `preCommitSubscriptionsEnabled`, `vmContextBotsEnabled`, `introspectionEnabled`, `allowProjectSmtp`, `botCustomFunctionsEnabled` (this one *is* listed) — checking `booleanKeys` at `config/utils.ts:185-208` against the boolean keys in `types.ts` shows several booleans **missing from the set**, so `MEDPLUM_HEARTBEAT_ENABLED=false` yields the string `"false"`, which is truthy. This is a real footgun and a direct argument for Spring's typed binding.

**Big Book's Spring equivalent, and whether BB-R-011.3 is achievable.** Yes, and more cheaply than Medplum. Spring Boot's `Environment` already defines the precedence Big Book wants, without any loader code: command-line args → `SPRING_APPLICATION_JSON` → OS environment variables → `application-{profile}.yml` → `application.yml` → `@ConfigurationProperties` defaults. Relaxed binding makes `BIGBOOK_FHIR_BASE_URL` → `bigbook.fhir.base-url` with no hand-written mangling, no missing-from-the-boolean-set bug, and typed binding with JSR-380 validation (`@NotBlank`, `@Positive`) so a bad value fails **at startup**, not on the first request. This matches ARCHITECTURE.md §5's stated order exactly ("Environment variables → Helm values/compose `.env` → defaults in `application.yml`"), so nothing in the architecture needs to change.

What Medplum does that would **not** fit BB-R-011.3, and should be dropped (D32):

- **Cloud-provider secret loaders** (`aws:`, `gcp:`, `azure:`) — three SDK dependencies fetching config at boot. Big Book's answer is Vault in `full` (BIGBOOK stack table) via Spring Cloud Vault, which is an additional `PropertySource`, not a replacement loader, and is absent from `lite` entirely.
- **Comma-composed positional sources** — replaced by Spring profiles (`--spring.profiles.active=lite`), which is also how CFG-062's worker-pool split would be expressed (D41).
- **Config file as the primary source.** BB-R-011.3's "env/values only" means the shipped `application.yml` holds defaults and *nothing environment-specific*; compose `.env` and Helm `values.yaml` supply the rest as env vars. The `lite` install (Note (b)) needs no config file at all.
- **No Docker-secrets loader exists in Medplum** despite the brief's mention — `grep` for `/run/secrets` across `packages/server` returns nothing. Big Book gets this free: Spring Boot reads `/run/secrets/*` via `spring.config.import=configtree:/run/secrets/` in one line, which is the cleanest answer to "secrets never in values files" for compose, and the Kubernetes equivalent is a mounted Secret with the same configtree import.

**Smallest working `lite` config.** Not a file — a compose `.env`, which is exactly what BB-R-011.3 asks for:

```sh
### .env — the whole of lite's configuration
BIGBOOK_BASE_URL=http://localhost:8080/
POSTGRES_PASSWORD=<generated at install>
KEYCLOAK_ADMIN_PASSWORD=<generated at install>
BIGBOOK_BOOTSTRAP_ADMIN_EMAIL=admin@example.invalid
BIGBOOK_BOOTSTRAP_ADMIN_PASSWORD=<generated; printed once>
### only with the admin overlay:
### BIGBOOK_BOOTSTRAP_ADMIN_CLIENT_SECRET=<generated>
```

Five lines, three of them generated by the install script — which is what makes BB-R-011.1's "two commands max" work. Compare Medplum's shipped `medplum.config.json`: 30+ keys including a Redis block, Google and reCAPTCHA credentials, and AWS Lambda settings, none of which a laptop install needs. **Recommendation:** the install script generates `.env` with the three secrets and echoes the admin password once; `docker compose up -d` needs nothing else. A `bigbook.yml` file is supported but never required — which is the strongest form of "configuration by env/values only".

##### (c) Secrets handling

**What Medplum does to keep secrets out of config files:** very little in the open-source path, and quite a lot in the AWS path.

- The **AWS path is the only real story**: SSM parameters with `WithDecryption: true` (`cloud/aws/config.ts:32`) and the seven `*Secrets` pseudo-keys (CFG-153..159) that pull whole credential blobs from Secrets Manager. GCP Secret Manager and Azure Key Vault are equivalents, one flat-JSON secret each.
- **The `file:` path has no protection at all.** The shipped `packages/server/medplum.config.json` contains `database.password`, `redis.password`, a Google OAuth client id, and — notably — `recaptchaSiteKey` and `recaptchaSecretKey` with real-looking Medplum values **committed to the repository** (CFG-066/067). Whatever their status upstream, the pattern is exactly what BB-R-011.3 forbids.
- **`signingKeyPassphrase` is auto-generated per process** when storage is built-in (`config/utils.ts:60-81`), with a logged warning that URLs break across restarts and replicas. It is a convenience, not a secrets-management story.
- **No Docker-secrets support** (no `/run/secrets` reader anywhere).

**What is stored in plaintext in the `Project` resource** — this is the part BB-R-011.3 does *not* address:

- `Project.secret[]` — PS-031..039 plus every bot secret. Plaintext columns in Postgres. **Readable by any project admin** through a plain FHIR read of `Project`: the injected admin policy (`fhir/accesspolicy.ts:341-348`) hides `systemSecret`, `superAdmin` and `strictMode` and makes `systemSetting` readonly, but leaves `setting` and `secret` fully readable and writable. So `smtpPassword` (PS-036) and `OPENAI_API_KEY` (PS-031) are admin-visible by design.
- `Project.systemSecret[]` — hidden from project admins by that same policy, readable by super-admins, and still plaintext at rest.
- Adjacent, from area 1 D36: `ClientApplication.secret` is stored in clear and returned on **every** read, never masked.
- Non-admin members see none of the four fields (all hidden), so the exposure is bounded by admin membership, not by encryption.

**What BB-R-011.3's "secrets never in values files" actually requires**, and what it does not:

1. **Requires:** no secret literal in `values.yaml`, `application.yml`, or any file committed to a chart or repo. Helm takes `existingSecret` references; compose takes `.env` (git-ignored) or `/run/secrets` via `spring.config.import=configtree:/run/secrets/`. Both are one line of Spring config — see (a).
2. **Requires:** the shipped `application.yml` has **no** default for any secret-typed property. CFG-127's `medplum_admin` default is the exact anti-pattern (S1).
3. **Does not cover** at-rest secrets inside the FHIR store. `Project.secret` is a *resource field*, not a values file, and Big Book will copy the shape for wire-compat (BB-R-005.6). **D35: state this explicitly in BB-R-005.6** — in `lite`, `Project.secret` is plaintext in Postgres and readable by project admins, exactly like Medplum; Vault (`full`) is the only profile where it is not. Otherwise the brick reads as a stronger promise than the code can keep.
4. **Suggests a test:** a CI check that greps the chart and compose files for anything matching a password/secret/key property name with a non-empty literal default. Cheap, and it is the only way BB-R-011.3 stays true after ten releases.

#### Contradictions with REQUIREMENTS.md/ADRs

**BB-R-011.3** — *"Configuration by env/values only; every key documented in one table (`docs/guides/config.md`), with defaults; secrets never in values files."*

- **"env/values only" — achievable, and Medplum is the cautionary tale, not the model.** Medplum has five loaders selected by a single CLI argument with positional precedence (Note (a)); the `env` source is opt-in and its name mangling is hand-rolled, lossy (only two nesting levels reachable), untyped for several boolean keys, and silently ignores misspellings. Spring's native property resolution gives Big Book the ARCHITECTURE.md §5 order for free. **No contradiction — but the brick should name Spring's order explicitly so "env/values only" is not read as "we will write a loader".**
- **"every key documented in one table, with defaults"** — Medplum documents ~90 of ~159 flattened keys, misses most nested tuning keys, documents two keys that **do not exist** (`auditEventLogGroup`, `auditEventLogStream`, T39), and states a precedence rule that is **false** (T38). A hand-maintained table drifts. **Recommend** generating `docs/guides/config.md` from the `@ConfigurationProperties` classes and failing CI on an undocumented property (T40).
- **"secrets never in values files"** — achievable and cheap (configtree / `existingSecret`), **but it does not cover `Project.secret`**, which is plaintext at rest and admin-readable in Medplum and will be in Big Book too. Code reality: `fhir/accesspolicy.ts:341-348` hides `systemSecret` from project admins but leaves `secret` readable and writable; `email/utils.ts:37` reads `smtpPassword` straight out of it. **D35: BB-R-005.6 must say so, or it over-promises.**
- Also: the shipped `medplum.config.json` contains real-looking `recaptchaSecretKey` and `redis.password` values in the repository. Whatever their upstream status, Big Book's shipped `application.yml` must have **no secret-typed default at all** (S1).

**BB-R-005.6** — *"Project settings (v0.1 subset): `checkReferencesOnWrite`, `defaultProfile`, `features[]`, `defaultPatientAccessPolicy`, `setting[]`/`secret[]` (secrets in Keycloak client attrs or env for `lite`; Vault in `full`), `rateLimit` (→ BB-R-023, v0.2)."*

- **`rateLimit` is `systemSetting`, not `setting`** (`ratelimit.ts:50`, read `:144-146`) — super-admin-only, and it is one of **seven** rate/quota system settings, not one: `rateLimit`, `authRateLimit`, `loginRateLimit`, `userFhirQuota`, `totalFhirQuota`, `enableFhirQuota`, `resourceCap` (+`enableResourceCap`). Area 1 T9 already flagged the field; this area supplies the full list and the read sites (PS-015..022).
- **The brick's list is not the runtime-read list.** `checkReferencesOnWrite`, `defaultProfile` and `defaultPatientAccessPolicy` are **top-level `Project` fields**, not `setting[]` entries — mixing them into a "settings subset" conflates two storage shapes. The actual runtime-read `Project.setting` names are the fourteen in Table B rows PS-001..PS-014.
- **`secret[]` "in Keycloak client attrs or env for `lite`"** contradicts wire-compat: Big Book will expose `Project.secret` on the `Project` resource (BB-R-014.3, v0.2), which means it is in Postgres like Medplum's, whatever backs it. Keycloak client attributes are also plaintext and admin-readable, so the phrasing promises a protection it does not deliver. See D35.
- **Missing from the subset, and needed in v0.1:** `mfaRequired` (PS-001) is required by BB-R-004.3; `allowedPractitionerEmailDomain` (PS-007) is the GAP area 1 flagged at ADM-011.

**BB-R-004.3** — *"MFA (TOTP) per user; project can require MFA at invite (`mfaRequired`) — Keycloak required action, set by BB-R-005 invite."*

- Code reality (`auth/utils.ts:129`, PS-001): `mfaRequired` is **not only an invite-time flag**. It is `Project.setting[mfaRequired].valueBoolean OR User.mfaRequired`, evaluated at **every password login**, and the project value **wins over** a user-level `false` — a project cannot grant an exception. Users who have not enrolled are forced to enroll at their next login, including **existing** users. The brick's "at invite" framing understates it: flipping the project setting retroactively gates everyone.
- **Two sibling settings are missing from the brick:** `allowedMfaMethods` (PS-002 — `totp`/`email`; area 1 D38 correctly makes email OTP non-goal) and `appName` (PS-003), which white-labels the TOTP authenticator issuer and the MFA email. Without `appName`, every Big Book tenant's authenticator entry says whatever the realm display name says — a visible branding gap in a multi-tenant product (T41).
- Keycloak's mapping is a **conditional-OTP authentication flow bound per organisation**, not a per-user required action, if the "project can require it" semantics are to be preserved. Area 1 D38 already puts this at v0.2 — consistent, but BB-R-004.3 still says v0.1.

**BB-R-023** — *"Rate limits per project/user — wire Traefik — v0.2."*

- Code reality: Medplum has **two different mechanisms**, and Traefik covers only one.
  1. **HTTP rate limits** — three categories (`login` 5/min, `auth` 1200/min *documented* but `160` actually applied, `default` 60000/min), keyed by **IP address** (`ratelimit.ts:116-120`), Redis-backed, overridable per project by PS-015..017. Traefik's `RateLimit` middleware does this.
  2. **FHIR interaction quota** — cost-weighted per interaction (READ 1, HISTORY 10, SEARCH 20, WRITE 100), enforced per **membership** and per **project**, with an async variant that *delays* rather than rejects (`asyncDelayScaling`, CFG-116). Plus a **resource cap** (PS-021, resources created per project per 24h). **Traefik cannot express any of this** — it has no notion of a per-request cost or a per-tenant token bucket keyed on a JWT claim.
- So BB-R-023's single "wire Traefik" fill is **insufficient for the second mechanism**. Either drop cost-weighted quotas and resource caps as non-goals, or accept that they are glue (D36). Also note the keying difference: Medplum limits **by IP**, so a whole clinic behind one NAT shares a bucket; Traefik would do the same unless keyed on the project claim.
- Two code-level oddities for the parity guide: `defaultAuthRateLimit`'s `addDefaults` value (`160`) makes `ratelimit.ts`'s stated category default (`1200`) unreachable (CFG-113), and `defaultRateLimit: -1` is a magic sentinel that disables the limiter entirely (CFG-112).

**BB-R-003.4** — *"Introspection togglable per project (`graphql-introspection` feature); depth/search-count limits configurable."*

- **The `graphql-introspection` feature flag is dead** (FF-010) — zero read sites in `packages/server`, `packages/core`, `packages/app` or `packages/fhir-router`; only test fixtures and mocks. Introspection is controlled **server-wide** by `introspectionEnabled` (CFG-095) → `FhirRouter` option → `fhir-router/src/graphql/graphql.ts:127-128`. The per-project check was removed by commit `a54b65933` "FHIR Router (#1435)". Medplum's own docs still list the flag as working. **Area 2's finding is confirmed, and the brick is wrong about Medplum: "togglable per project" is not what Medplum does.** Big Book can still choose per-tenant toggling, but should say so as a deliberate improvement rather than as parity.
- The "depth/search-count limits configurable" half **is** real and **is** per project — `graphqlMaxDepth` (PS-026), `graphqlMaxSearches` (PS-027), plus `graphqlBatchedSearchSize` (PS-028) — all `systemSetting`, super-admin-only. HAPI's GraphQL provider has no equivalent knobs, so these are **glue**, not wire. The brick's `Fill: wire HAPI GraphQL` understates it.

**BB-R-001.4** — *"Batch (`type: batch`) and transaction (`type: transaction`) bundles…"* (unconditional)

- Code reality (FF-013): in Medplum, **a `transaction` Bundle is only atomic if the project holds the `transaction-bundles` feature**. Without it, `fhir-router/src/batch.ts:874` degrades transactions to batch semantics — no DB transaction, no rollback, no serialization-failure retry. Medplum's own docs describe this under "transaction limits". Big Book's brick promises transactions unconditionally, and HAPI is atomic by default. **No change needed to the brick** — but the parity guide must record that Medplum's default behaviour differs, or a wire-compat test written against a Medplum project without the flag will "pass" for the wrong reason.

**ADR-006 implications** (`lite` = Postgres + Keycloak + Big Book; HAPI embedded)

- **Redis is a hard dependency of Medplum's server** — `initRedis` is unconditional (`redis.ts:44-47`), and rate limiting, every BullMQ queue, websockets, FHIRcast, the server registry and the resource cache all require it. Five config objects (CFG-041..049) exist to tune and split it. ADR-006's three containers leave no room for it, so all five are `drop` in v0.1 (D33). This is only sound because BB-R-023 (rate limits) is v0.2 and Traefik-based, BB-R-007.8 (websockets) is deferred, and HAPI's subscription delivery is DB-backed rather than queue-backed. **If any of those three change, ADR-006's container count is back in play** — worth one line in the ADR's Consequences.
- **`workers.enabled` and the two shipped partial config files** (CFG-062, D41) are Medplum's documented way to split an HTTP pool from a worker pool. ADR-006 puts everything in one JVM, so the whole mechanism drops for `lite`. The `full` equivalent is a Spring profile, not a config key — consistent with BB-R-011.2's `profile: lite|full`.
- **HAPI-embedded shifts ~40 of Table A's keys from "Big Book config" to "HAPI/Spring config"** (all of `database.*`, `port`, `logLevel`, `shutdownTimeoutMilliseconds`, `keepAliveTimeout`, `accurateCountThreshold`, `bcryptHashSalt`…). BB-R-011.3's "one table" must therefore document **Spring/HAPI properties alongside `bigbook.*` ones**, or half the surface an operator touches will be undocumented. That is a real scope note for `docs/guides/config.md`: it is not a table of Big Book's own properties, it is a table of everything an operator sets.
- **ADR-006 removes the `signingKey` problem** (CFG-014..016): with HAPI embedded and `lite` storage in the database, there are no presigned URLs to sign in v0.1, so Medplum's auto-generated-throwaway-key warning has no Big Book analogue until BB-R-009.3/BB-R-027 land in v0.2 with MinIO (whose presigner needs no separate key pair — see (d)).

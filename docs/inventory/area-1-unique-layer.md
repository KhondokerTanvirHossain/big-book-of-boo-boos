#### Contradictions with REQUIREMENTS.md/ADRs

1. **BB-R-005.4 field list is the deprecated shape.** Brick: "`POST /admin/projects/:id/invite` with resourceType, name, email, `scope`, `admin`, `accessPolicy`, `mfaRequired`, `sendEmail`". Medplum's current `InviteRequest` (`packages/core/src/client.ts:612-637`) marks top-level `admin`, `accessPolicy`, `access` as `@deprecated` in favour of `membership: Partial<ProjectMembership>`; the docs page and app send `membership.admin`. It also has `firstName`/`lastName` (no `name`), `externalId`, `patient`, `password`, `upsert`, `forceNewMembership`. For v0.2 byte-compat (BB-R-005.5a / BB-R-014.4) both the deprecated and `membership.*` forms must be accepted, with `membership.*` winning (ADM-016).
2. **BB-R-005.2 scope defaults are incomplete.** Brick: "Practitioner defaults `server`, Patient defaults `project`." Code (ADM-009): RelatedPerson also defaults `server`, and any invite with `externalId` is forced project-scoped regardless of `resourceType`/`scope`.
3. **BB-R-006.4 covers only two of four default policies.** Brick: "Default policies per project (Practitioner default, Admin default) with the promote/demote swap." Medplum `Project.defaultAccessPolicies[].profileType` is `'Patient'|'Practitioner'|'RelatedPerson'|'Admin'`; invite assigns Patient (with legacy `defaultPatientAccessPolicy` fallback) and RelatedPerson (parameterised `%patient`) defaults too (ADM-017). BB-R-005.6 lists only `defaultPatientAccessPolicy`, the legacy field.
4. **BB-R-004.9 / ADR-003 assume `:projectId` is authoritative.** The brick's exit test ("`/auth/me` under each token shows the right membership") is fine, but any BB implementation that validates `:projectId` against the token will be *stricter* than Medplum, where the path id is ignored for project admins (ADM-002) and only honoured for super admins on invite/client. Not a contradiction in text, but a wire-compat trap: Medplum's app passes the id and expects it to be ignored when it equals the current project.
5. **BB-R-013.3 "Clients (create → shows secret once)".** Medplum does not show the secret once: `ClientApplication.secret` is stored in clear and returned on every FHIR read and in ADM-019 (`project.secret` is a different field, but `ClientApplication.secret` is readable via `GET /fhir/R4/ClientApplication/{id}`). Keycloak also keeps client secrets retrievable by admins, so BB can either match Medplum (retrievable) or diverge; the brick currently asserts the divergent behaviour.
6. **BB-R-005.6 settings subset lacks `allowedPractitionerEmailDomain` and `allowedMfaMethods`.** Both are read by the invite/MFA paths (ADM-011, ADM-026); with the v0.1 subset the domain check is silently absent.
7. **BB-R-004.1 "password reset/set — Keycloak realm login flows"** does not cover the *admin-initiated* variants (ADM-005, ADM-027, ADM-033) or admin MFA reset (ADM-026) that the Medplum app's Account Security panel calls; those are Keycloak admin-API operations, not login flows. Marked GAP above.
8. **BB-R-014.4 lists `/admin/projects`, `/admin/projects/:id`, `/admin/projects/:id/invite|client|members`.** There is no `GET /admin/projects` (list) route in Medplum; the app lists projects via `/auth/me` and FHIR `Project` search. Conversely `/admin/projects/:id/bot|settings|secrets|sites|setpassword` and `members/:id/mfa/reset|resetpassword` are absent from the brick.
9. **Docs vs code:** `user-management/index.md` shows `PATCH /admin/projects/:id/members/:mid` with JSON Patch; no such route exists (only POST with a full resource). The Big Book port should not implement PATCH for compat.
10. **BB-R-005.7 / ADR-004 `X-Project` header vs Medplum path id.** Brick (commit `b4d4aad`): "Super-admin tokens select the target partition with an `X-Project` header." Medplum has no such header: a super admin targets another project via the `:projectId` path segment, and only on `invite` (ADM-008, `systemRepo.readResource('Project', :projectId)`) and `client` (ADM-007); on every other project-admin route the super admin acts on its *own* project (ADM-002/019-027). For v0.2 SDK-grade compat the path id must remain authoritative for super admins on those two routes; `X-Project` can be additive, but ADR-004 #4 ("a super-admin write without it gets 400") would break `@medplum/core`/CLI callers that only send the path id. Recommend: path id wins when present; `X-Project` only for routes that have no path id (`/fhir/R4/*`).
11. **ADR-004 screen inventory names routes that do not exist in Medplum.** "`GET /admin/projects`, `GET/PUT /admin/projects/:id`, `GET /admin/projects/:id/members[?profileType=]`, `PUT /admin/projects/:id/members/:mid`" (and BB-R-013.1 "project switcher = `GET /admin/projects`"). Medplum has none of these: there is no project list route (the app uses `/auth/me` → `logins[]`/`projects` and FHIR `Project` search); project edits are `POST .../settings|secrets|sites` (ADM-020..022), not `PUT`; members are listed by FHIR search `ProjectMembership?profile-type=Practitioner|Patient|ClientApplication|Bot` (never via `/admin`); member update is `POST` (ADM-024), not `PUT`. Fine as Big Book-only routes in v0.1, but they must not be documented as Medplum-compatible and BB-R-014.4 should list the Medplum spellings from this table instead.

#### Notes for the Java port

- **`:projectId` is decorative for project admins.** Only invite (ADM-008) and client (ADM-007) read it, and only when the caller is super admin; everything else uses the token's project. `@medplum/app` always passes the current project id, so a strict implementation (403 on mismatch) is compatible with the app but stricter than Medplum. Recommend: enforce equality for non-super-admins (cheap, safer), honour the path id for super admins, and treat ADR-004's `X-Project` header as a fallback for routes without a path id (see contradiction 10).
- **Super-admin "act on another project" is inconsistent in Medplum itself.** A super admin can invite into or create a client for project X via the path id, but `GET /admin/projects/X`, settings/secrets/sites, and member routes silently operate on the super admin's own project (`ctx.project`). The Medplum app works around this by having the super admin *log in to* the target project (`/auth/me` `logins[]` switcher). Big Book's `X-Project` design (ADR-004) is cleaner; just keep the two path-id routes byte-compatible.
- **Super admin is a project property.** `superAdmin` lives on `Project`, and a token's powers depend on which project it was issued for. In Keycloak this maps to a realm role granted only to memberships of the bootstrap project (BB-R-005.7); `/auth/me` must expose `project.superAdmin: true` for `@medplum/app` to render the Super Admin menu.
- **Invite is non-atomic and ordered:** User (conditional create) → `UserSecurityRequest` → profile (conditional create) → membership → email. A failure after step 1 leaves a User with no membership; a re-invite then finds it (`existingUser=true`) and sends the "existing user" email with no set-password link. Keycloak port: create user with `UPDATE_PASSWORD` required action, then org membership, then send `execute-actions-email` last; make the whole thing idempotent on (email, project, scope).
- **Existing-user semantics:** for an existing same-scope User, `password`, `mfaRequired`, `firstName`, `lastName` are silently ignored; only a membership is added. Same for an existing profile matched by email in the project (names ignored).
- **Server- vs project-scoped Users are distinct identities** with the same email; the guard in ADM-010 blocks mixing scopes in one project unless `forceNewMembership`. Keycloak has one user per realm per email; project-scoped users can be modelled as users whose only org membership is that org (and `User.project` claim set) — the "same email, two scopes" case cannot be reproduced without a suffixed username. Decide consciously (recommend: single identity, reject cross-scope invites with 409 as Medplum does).
- **Response codes to mirror in v0.2:** invite → **200** (not 201) with `ProjectMembership`; bot and client → **201**; member update with wrong `resourceType`/`id` → **403** (not 400); RelatedPerson email matching >1 → **412** `multipleMatches`; duplicate membership → **409**; email-send failure → **200** with an `OperationOutcome` (`id: allOk`, one `error` issue) after resources were created. `@medplum/app` `InvitePage` inspects that outcome to show the "SES not configured" warning.
- **Email templates** are plain text, sender "Medplum", subjects `Welcome to Medplum` / `Medplum: Welcome to {project}` / `Medplum Password Reset` / `Your multi-factor authentication has been reset`. Links: `{appBaseUrl}setpassword/{id}/{secret}` and `{appBaseUrl}signin`. `sendEmail` must be boolean `false` to suppress (the docs' `"sendEmail":"false"` string still sends). Per-project SMTP/app-name comes from `Project.setting` (v0.2, BB-R-026).
- **`UserSecurityRequest` semantics:** one-time secret (16 bytes hex), typed (`invite`/`reset`/`verify-email`), superseding prior unused requests of the same type, expiry by type, consumed in a transaction. Keycloak action tokens cover this; BB should not persist its own.
- **`setPassword` side effects:** HIBP breach check (outbound HTTPS to api.pwnedpasswords.com — must be optional/offline-safe in `lite`), then revoke all `Login`s. Keycloak: `logout` all user sessions after admin password set to match.
- **MFA reset rotates the TOTP secret** and un-enrols only the chosen method; Medplum stores `mfaSecret` on the User even before enrolment (`mfaRequired` pre-generates it). Keycloak equivalent: delete the `otp` credential and add `CONFIGURE_TOTP` required action; "email" MFA has no Keycloak analogue in v0.x.
- **Membership delete cascade:** deleting the last membership of a project-scoped User deletes the User (never the Practitioner/Patient profile); `Project.owner` cannot be removed. BB needs an owner concept (or accept the divergence) and must delete the Keycloak user only when it is org-only.
- **Promote/demote swap** (`reconcileDefaultAccessPolicy`) runs only on ADM-024, not on plain FHIR `PUT ProjectMembership`; it swaps only when the current policy is exactly the *other* default. If BB implements membership update through the FHIR route as well, apply the same reconcile there or document the difference.
- **Settings/secrets/sites are whole-array replaces** of `Project.setting|secret|site` producing a new Project version; secrets are plaintext in the resource and echoed back by ADM-019. BB should store secrets outside the Project resource (Keycloak client attributes/Vault) and return names only; `@medplum/app` `SecretsPage` expects `project.secret[]` values to edit them, so app-grade compat (v1.0) would need masked values or a divergence note.
- **ClientApplication creation** happens through the *system* repo, so a project admin whose access policy forbids `ClientApplication` writes can still create clients through this route; the secret is 64 hex chars and remains readable. Keycloak: create confidential client with `bigbook.project` attribute + service-account user, and mint the membership with `profile = ClientApplication/<id>` for `/auth/me`.
- **Bot creation** creates a `Binary` (source) + `Bot` + membership and optionally deploys; `runtimeVersion` defaults from server config. Under BB-R-016 bots are compiled Camel routes, so the v0.2 route should accept the same body but reject `sourceCode`/`executableCode` uploads (or store them inert) — decide in the Bot SDK ADR.
- **Super-admin DB routes (ADM-036..044) embed Postgres identifiers into DDL** (validated by `isValidPostgresIdentifier`) and run on the writer pool; `tablesettings` is synchronous. None have a HAPI/Keycloak analogue; document `psql` runbooks instead (BB-R-011.7). `reindex` maps to HAPI `$reindex` but with a different parameter set; the AsyncJob/`job/{id}/status` polling shape used by `SuperAdminStartAsyncJob` is Medplum-specific and only matters for app-grade compat (v1.0).
- **Callers outside the app worth knowing:** `packages/cli/src/utils.ts:107` (bot create) and `packages/cli/src/aws/update-server.ts:46` (migrate) call these routes; examples call bot/client/invite only. `@medplum/core` exposes exactly one typed helper (`invite`); everything else is `medplum.post('admin/...')`, so SDK-grade compat (v0.2) needs only the invite route byte-exact, while bot/client/settings are app-grade.

#### Contradictions with REQUIREMENTS.md / ADRs

1. **BB-R-006.2 — "`admin: true` bypasses."** Not true in Medplum. `membership.admin` never bypasses the compiled AccessPolicy; `accesspolicy.ts` says so explicitly ("The `admin` flag does not bypass the access policy") and `applyProjectAdminAccessPolicy` only *adds* a fixed rule set for the project-admin resource types. Only `Project.superAdmin` bypasses (`Repository.isSuperAdmin()` short-circuits `canPerformInteraction`). What makes admins look unrestricted is that a membership with **no** `accessPolicy`/`access` compiles to `{resourceType:'*'}`. Big Book should model: super-admin project = bypass; admin = ordinary policy + injected admin rules; no policy = full access within project.

2. **BB-R-006.2 — "`ProjectMembership.accessPolicy[]` … list".** `accessPolicy` is `0..1`. The list is `ProjectMembership.access[]` (`{policy, parameter[]}`), and both are concatenated then OR'd. The exit test in BB-R-006 (single policy) still holds; the schema statement does not.

3. **BB-R-006.3 — "`%requestor`".** No `%requestor` variable exists in server code; the built-ins are `%profile` and `%patient` (the latter defaults to the profile unless a `patient` parameter is passed). Everything else comes from `access[].parameter`. Substitution is a raw JSON-string `replaceAll`, so `%name.id` must be substituted before `%name`.

4. **BB-R-006.4 — "Default policies per project (Practitioner default, Admin default)".** Medplum's `Project.defaultAccessPolicies[].profileType` is bound to `Patient | Practitioner | RelatedPerson | Admin`, and `$init` seeds **Patient, RelatedPerson, Admin** (not Practitioner). The promote/demote swap only fires when a membership's policy is *exactly* one of the two recognised defaults. The brick should name all four codes.

5. **BB-R-005.2 — scope defaults.** Matches code, but code adds a third rule the brick omits: **any invite carrying `externalId` is forced project-scoped regardless of resourceType**. Also `User.firstName/lastName` are `1..1` — a "read-only projection of Keycloak" (BB-R-014.3) must always emit both or `@medplum/fhirtypes`-typed consumers break.

6. **BB-R-005.3 — "ProjectMembership links User → Project".** `ProjectMembership.user` is `Reference<User | ClientApplication | Bot>`, and for clients and bots **`user` and `profile` are the same resource**. There is no `User` behind a ClientApplication or Bot. Keycloak-only identity for clients is fine, but the membership row still needs a `user` reference of type `ClientApplication`.

7. **BB-R-005.5 — "External IDs on identities — v0.1 as identifier on the profile resource".** Medplum carries external ids on `ProjectMembership.externalId` (and deprecated `User.externalId`), with a dedicated `external-id` search parameter and a `%`-free lookup in external auth. Putting them on the profile `identifier` diverges from what `MedplumClient`/app users search for; acceptable in v0.1 but must move for v0.2 SDK-grade C.

8. **BB-R-005.6 — settings subset says `rateLimit` is a project setting.** In Medplum `rateLimit`/`authRateLimit`/`loginRateLimit`/quotas are **`systemSetting`** (super-admin only), not `setting`. Conversely `mfaRequired` (BB-R-004.3) is a `Project.setting`, not an invite-only flag: `isMfaRequired = Project.setting[mfaRequired] || User.mfaRequired`.

9. **BB-R-005.7 — "only role that can … override `id`/`meta`".** Correct, with one nuance: a project admin in extended mode may set `meta.account(s)` (`canWriteAccount`), and super-admins may set `meta.project` only for `User` and `Subscription` unless they also hold `canWriteProtectedMeta` (which they do). Effectively matches.

10. **BB-R-005.11 — `X-Project` header for super-admin tokens.** Medplum has no such header. A super-admin token acts in the super-admin project; cross-project writes are done by setting `meta.project` in the body (extended mode), and cross-project reads by searching with `_project=` / `_compartment=`. Introducing `X-Project` is a Big Book invention; it must not be required by `@medplum/core` paths (the SDK will never send it) or SDK-grade C breaks for super-admin users. Recommend: accept `X-Project` **and** `meta.project`, never require either for reads.

11. **BB-R-014.3 — "`User` (read-only projection of Keycloak)".** Medplum project admins *write* Users (name, `mfaRequired`), and the app calls `User/$rescope`, `User/$update-user-email`, MFA endpoints. Read-only is fine for SDK-grade C (core never writes User), but app-grade C (v1.0) will need writes or stubbed operations.

12. **BB-R-014.3 — ClientApplication "readable/writable in Medplum JSON shape".** In Medplum the `secret` is returned on every read of the ClientApplication (no hidden field). Keycloak also allows reading a confidential client's secret via admin API, so this is reproducible, but BB-R-013.3 "Clients (create → shows secret once)" contradicts Medplum semantics; `@medplum/app` `ClientsPage` reads the secret from the resource.

13. **ADR-003 SDK-grade C exit test** lists client-credentials login, `/auth/me`, Patient CRUD/search. Two further `@medplum/core` dependencies on custom types are not in that list but are on the default code path: (a) `MedplumClient` sends `X-Medplum: extended` on every request and `getProfile()`/`getProject()`/`getUserConfiguration()`/`getAccessPolicy()` are populated from `/auth/me`; the `/auth/me` payload must include `project.{id,name,features,strictMode,superAdmin}`, `membership.{id,user,profile,admin}`, `profile`, `config` (a full `UserConfiguration` with a non-empty `menu`), `accessPolicy` (compiled, `basedOn` filled), and optionally `security`; (b) `startAsyncRequest` expects `AsyncJob` JSON at `Content-Location` for any `Prefer: respond-async` call. Neither is in BB-R-014 §3.

14. **BB-R-004.8a / ADR-003 — `Login` non-goal.** Consistent, but note `Login` is also what `/auth/me.security.sessions` and `/auth/revoke` enumerate; SDK-grade C never touches them, app-grade C does (SecurityPage).

15. **BB-R-002.6 — `_compartment=Project/<id>`.** Medplum's `_compartment` search param is synthesised over `meta.compartment`, and a separate `_project` param over `meta.project` (`core/types.ts`). `@medplum/core`'s `AccessPolicy` client-side check (`core/access.ts`) reads `resource.meta.compartment` — so if Big Book never emits `meta.compartment`, a deprecated `resource.compartment` policy evaluated in the browser always fails. Emit `Project/<id>` in `meta.compartment` for extended-mode responses.

16. **BB-R-001.5 — `Project.defaultProfile` "auto-applied when absent".** Matches Medplum exactly (only when `meta.profile` is empty for that resource type).

17. **Non-goals list says "DICOM … CDS Hooks"** — consistent with Dicom* and `Bot.cdsService` fates above. But `Agent` is not in the non-goals; it is the v0.3 HL7v2 agent config, so it needs a v0.3 brick ID (currently GAP).

#### Notes for the Java port

**Where the 24 types live on HAPI.**
- *Load as custom resources* (HAPI `IResourceProvider` + `@ResourceDef` Java classes generated from `profiles-medplum.json`, `kind=resource`, base `DomainResource`): `AccessPolicy`, `ClientApplication`, `UserConfiguration`, `Bot`, `Project`, `ProjectMembership`, `User`. These must round-trip byte-for-byte because `@medplum/core` and `@medplum/app` read/write them through `/fhir/R4/<Type>` (`medplum.readResource('Project', id)`, `searchResources('ProjectMembership', …)`, `updateResource(accessPolicy)`), and `MedplumClient` validates responses only loosely, so the risk is *shape*, not schema. Search parameters must be registered from `search-parameters-medplum.json` (e.g. `ProjectMembership?project=…&user=…&profile-type=Practitioner`, `User?email=`, `AccessPolicy?name=`, `ClientApplication?name=`), otherwise the app's admin pages return empty lists. HAPI's JSON parser rejects unknown top-level elements only in strict mode; keep it lenient and generate the Java model rather than hand-writing.
- *Stored outside FHIR, projected on demand*: `User` (Keycloak user), `ClientApplication` (Keycloak client + BB attributes), `Project` core identity (Keycloak organisation) — but their **FHIR JSON view** must still be served at `/fhir/R4/User/<id>` etc. for SDK-grade C. A small "virtual resource provider" that materialises the JSON from Keycloak (read) and writes back a whitelist of fields is cheaper than double-storing. `ProjectMembership`, `AccessPolicy`, `UserConfiguration` have no Keycloak counterpart and should be real HAPI rows in the tenant partition (`ProjectMembership` additionally indexed globally, as Medplum does via the global shard).
- *Do not model*: `Login`, `JsonWebKey`, `DomainConfiguration`, `UserSecurityRequest` (Keycloak sessions/keys/orgs/action-tokens), `Enterprise`, `Package*`, `Dicom*`, `SmartHealthLink`. `AsyncJob`/`BulkDataExport`: only needed when `Prefer: respond-async` is honoured; HAPI's bulk export uses `$export-poll-status` with a different JSON, so a thin adapter that returns an `AsyncJob`-shaped body from `Content-Location` is the v0.2 bridge. `SmartAppLaunch`, `Cron`, `Agent` per fate above.

**What must stay byte-compatible for `@medplum/core` (ADR-003 SDK-grade C).**
1. `/auth/me` response shape (see contradiction 13). `config.menu` must be non-empty (core/app build the sidebar from it); `accessPolicy` should be the *compiled* policy (`resource[]` present, `basedOn[]` = source refs) because `core/access.ts` uses it client-side for optimistic permission checks (`canWriteResource`, `satisfiedAccessPolicy`) and the app hides buttons based on it.
2. Extended meta: `X-Medplum: extended` ⇒ responses carry `meta.project` (partition id as string), `meta.author` (`{reference:'Practitioner/…'}`), `meta.compartment` (at least `Project/<id>`). Without the header, strip all Medplum meta fields. HAPI has no slot for these; implement as a response interceptor (`SERVER_OUTGOING_RESPONSE`) that injects them from the partition id and the token's `profile` claim, and a request interceptor that strips them on inbound writes (Medplum ignores client-supplied `meta.author` and, for non-super-admins, `meta.project`).
3. Project-admin semantics: `*` policy entries must not grant `Project`/`ProjectMembership`/`User`/`Cron`/`Package*`/`UserSecurityRequest`; admins get the injected rules verbatim (hidden `superAdmin`, `systemSecret`, `strictMode` on Project; hidden `passwordHash`, `mfaSecret` on User; readonly `project`,`user` on ProjectMembership). Reproduce the `readonlyFields`/`hiddenFields` restore-on-write behaviour, or the app's "edit membership" page will silently clear `project`/`user`.
4. `ProjectMembership.meta.project` is always the membership's project; `Project.meta.project` is its own id; server-scoped `User` has **no** `meta.project` — the app's Super Admin "Users" page relies on `User?_project:missing=true`-style queries for server-scoped users. In HAPI terms, server-scoped users live in the default partition.
5. Ids are UUIDs and `ClientApplication.id` **is** the OAuth `client_id`; the SDK's `startClientLogin(clientId, clientSecret)` posts `client_id=<ClientApplication.id>`. Keycloak client `clientId` must therefore equal the FHIR resource id (or Big Book maps `ClientApplication.id` ↔ Keycloak internal id, exposing the FHIR id as `client_id` via a Keycloak client attribute).
6. Value sets: `client-application-status`, `bot-runtime-version`, `project-feature`, `project-membership-profile-type`, `user-mfa-method`, `ip-access-rule-action`, `access-poliicy-interactions` (sic, typo is upstream) are in `valuesets-medplum.json`; load them into HAPI terminology so `$validate` on these types passes.

**Surprises worth recording.**
- The `*` wildcard does not cover project-admin types, and `Project.link` reads never cross for them — a "multi-tenant admin" policy must name `Project`/`ProjectMembership` explicitly.
- `ProjectMembership` for a Bot or ClientApplication is self-referential (`user === profile`); invite for Practitioners creates a *server-scoped* User by default, so "one project ↔ one Keycloak organisation" (BB-R-005.1) needs Keycloak users that belong to several organisations — Keycloak Organizations support that, but per-org attributes (`admin`, `accessPolicy`) do not exist in Keycloak and must live in Big Book's membership row.
- Parameter substitution is textual on the policy JSON, so a `%patient` placeholder inside `criteria` strings, `compartment.reference`, and `writeConstraint.expression` are all rewritten in one pass; port must do the same (or restrict to `criteria`).
- `ClientApplication.secret` is stored and returned in clear; `retiringSecret` doubles it. Both are compared with timing-safe equality.
- Login for `client_credentials` never hits Postgres (Redis only); token introspection works from the JWT + Redis. Keycloak sessions cover this natively.
- `strictMode:false` is a deliberate escape hatch that downgrades validation to JSON-schema — HAPI has no equivalent; treat as always strict.
- The synthetic FHIR R4 project (`161452d9-43b7-5c29-aa7b-c85680fa45c6`) is appended to every repository's project list; base `StructureDefinition`/`ValueSet`/`CodeSystem`/`SearchParameter`/`OperationDefinition` resolve from it and are read-only for everyone except super-admin. HAPI keeps these in its own tables (not partitioned), which is the same effect.
- `Project.features` gates whole subsystems; `defaultProjectFeatures` is server config. Big Book should seed `features` at project create from config to keep `/auth/me.project.features` meaningful to the app (it hides Bots/Cron tabs when absent).
- `UserConfiguration.option` is keyed by `Element.id` (`option[].id`), not a `name` element — an easy port mistake.
- `Cron` is validated on write (cron string + readability of target and `onBehalfOf`) — one of only two types with type-specific write validation (the other being reference checks); everything else relies on the generic validator.

#### Contradictions with REQUIREMENTS.md / ADRs

##### Q1 — Does `MedplumClient` need anything beyond `/oauth2/token` + `/auth/me` for client-credentials and authorization-code logins?

**Endpoints: no — only `/oauth2/authorize` (redirect target), `/oauth2/token`, `/auth/me`, `/oauth2/logout`. Response shapes: yes — three non-standard things the SDK reads.**

Evidence, client credentials:
- `startClientLogin` → `fetchTokens({grant_type:'client_credentials', client_id, client_secret})` (`packages/core/src/client.ts:4339-4348`, `4661-4699`), form-encoded POST to `this.tokenUrl` = `baseUrl + 'oauth2/token'` (`client.ts:1078`), credentials in the body or Basic header (`authCredentialsMethod:'header'`, `client.ts:1084, 4668-4675`). Nothing else is called.
- `verifyTokens` (`client.ts:4708-4738`) parses the **access token payload** and requires: `exp` in the future; and if a `cid` claim exists it must equal `clientId`, otherwise **`client_id` must equal `clientId`** (`4724-4731`) — a Keycloak user token carries `azp`, not `client_id` (service-account tokens do carry `client_id`), so a mapper is needed for authorization-code logins.
- It then stores `LoginState{accessToken, refreshToken, project: tokens.project, profile: tokens.profile}` (`client.ts:4733-4738`, types `568-583`) — **`project` and `profile` are read from the token response** (server `oauth/token.ts:963-964`). They are used for the stored-login list / account switcher (`addLogin`, `syncStoredLoginProject`, `client.ts:3240-3298`) and `checkSessionDetailsMatchLogin` (`4740-4749`); they are not needed for API calls, but `undefined` there breaks `HeaderDropdown`/`getLogins()` displays in `@medplum/app`.
- `setAccessToken` sets `this.medplumServer = isMedplumAccessToken(token)` which is **`typeof payload.login_id === 'string'`** (`client.ts:3224-3229`, `packages/core/src/jwt.ts:90-97`). `refreshProfile` returns immediately when `!this.medplumServer` (`client.ts:3246-3249`). So **without a `login_id` claim the SDK never calls `/auth/me`**, `getProfile()/getProject()/getProjectMembership()/getAccessPolicy()` stay `undefined`, and `@medplum/react`'s `useMedplumProfile` treats the user as signed-out. Big Book must emit a `login_id` claim (any string; the Keycloak session id `sid` is the natural value).
- `/auth/me` must return `SessionDetails {project, membership, profile, config, accessPolicy}` (`client.ts:902-908`); read fields: `profile.id` (`3255`), `project.name` (`3283`), `project.superAdmin` (`3310`), `membership.admin` (`3319`), and the whole `profile`, `config`, `accessPolicy` objects via getters (`3327-3381`).

Evidence, authorization code:
- `signInWithRedirect` → `requestAuthorization` builds `GET <authorizeUrl>?response_type=code&state=<pkceState>&client_id&redirect_uri=<origin>&code_challenge_method=S256&code_challenge&scope=openid profile` (`client.ts:1614-1622`, `4192-4205`); on return `processCode` posts `grant_type=authorization_code, code, client_id, redirect_uri, code_verifier` (`4213-4227`) and runs the same `verifyTokens` path. `state` is never checked. Refresh uses `grant_type=refresh_token` with `client_id` only (`4299-4303`), i.e. a public client. Logout posts `{}` with a bearer to `oauth2/logout` (`1601-1604`). No discovery document, no JWKS fetch, no `/auth/*` call other than `/auth/me`.

Consequence for BB-R-004 §8 / ADR-003 "`/oauth2/authorize|token|userinfo` … proxied to Keycloak unchanged": true for v0.1 (curl-level, BB-R-014 exit test v0.1 — the `curl` samples in `docs/api/oauth/token.md:75-130` send Basic + `grant_type=client_credentials`/`authorization_code`, which Keycloak accepts as-is). **False for SDK-grade C (v0.2)**: `/oauth2/token` must be *wrapped* to (a) add `project` and `profile` to the JSON body and (b) guarantee `login_id` + `client_id` claims in the access token (mappers). Recommend rewording BB-R-004 §8 to "`/oauth2/authorize`, `/oauth2/userinfo`, `/.well-known/jwks.json` proxied; `/oauth2/token` proxied with response enrichment (`project`, `profile`); claims via mappers", and adding "`login_id`, `client_id`" to §9's claim list. BB-R-004 §9 currently says the token carries `project`, `profile`, `membership` claims; Medplum's token carries **`profile`** but neither `project` nor `membership` (MW-007) — Big Book's extra claims are harmless, but the SDK-visible contract is `login_id`/`client_id`/`exp`/`profile`.

##### Q2 — Does `@medplum/app` have any config path to sign in via a plain OIDC redirect without `Login` / `/auth/login`?

**No.**
- `packages/app/src/config.ts:3-10` — `MedplumAppConfig` is exactly `{baseUrl, clientId, googleClientId, recaptchaSiteKey, registerEnabled, awsTextractEnabled}`; `.env.defaults` adds nothing else.
- `packages/app/src/index.tsx:20-31` constructs `MedplumClient({baseUrl, clientId, storagePrefix, cacheTime, autoBatchTime, onUnauthenticated → '/signin?next='})` — no `authorizeUrl`/`tokenUrl` override and no call to `signInWithRedirect`; a grep of `packages/app/src` for `signInWithRedirect|signInWithExternalAuth|processCode|oauth2` returns only `OAuthPage.tsx` (which *is* the Medplum authorization UI, not a consumer of one).
- `packages/app/src/SignInPage.tsx:30-46` renders `<SignInForm>` from `@medplum/react`; `SignInForm` (`packages/react/src/auth/SignInForm.tsx:165-238`) is a state machine over `LoginAuthenticationResponse` that calls `POST auth/method` (`AuthenticationForm.tsx:80`), `startLogin` → `POST auth/login` (`AuthenticationForm.tsx:170`), `startGoogleLogin` → `auth/google` (`:91`), `auth/mfa/login-enroll|verify|send-email` (`SignInForm.tsx:131-212`), `auth/profile` (`ChooseProfileForm.tsx:57`), `auth/scope` (`ChooseScopeForm.tsx:41`), `auth/newproject`, and `GET auth/login/:id` (`SignInForm.tsx:159`) before finally `processCode(code)` (`SignInForm.tsx:74`). Every branch requires a `Login` id.
- The only external-IdP path in the app is `/auth/method` returning `authorizeUrl` (`AuthenticationForm.tsx:60-77`), which redirects to the IdP with `redirect_uri=<server>/auth/external`; the server callback (`auth/external.ts:156-175`) still creates a `Login` and sends the browser to `<app>/signin?login=<id>`, which `SignInForm` resolves through `GET /auth/login/:id`. So even brokered sign-in depends on `Login`, `/auth/external` and `/auth/login/:id`.
- `/oauth2/authorize` itself never renders UI — it redirects to `<appBaseUrl>oauth` (`oauth/authorize.ts:312-318`) and `OAuthPage.tsx:57-66` completes the flow by redirecting `code` to the client. The app is therefore *the* login UI, which is why it cannot be pointed at Keycloak's login page.

Conclusion: the v1.0 line in REQUIREMENTS.md ("blocked on emulating the `Login` sign-in flow; Claude Code to confirm `@medplum/app` has no `signInWithRedirect` config path") is **confirmed — there is no such path; app-grade C stays at v1.0.** Minimum emulation for app-grade C would be: `POST /auth/login`, `GET /auth/login/:id`, `POST /auth/profile`, `POST /auth/scope`, `POST /auth/method` (may return `{}`), `GET /auth/clientinfo/:id` (may return `{}`), and the `code` → `/oauth2/token` handoff, plus MFA routes if `mfaRequired` is used — all backed by Keycloak Direct Access Grants (password grant) with a Big Book-side pending-login table; this is what ADR-003 defers.

##### Other contradictions / clarifications

1. **BB-R-004 §2 "session listing/revocation — Keycloak"**: in Medplum these are `/auth/me.security.sessions` (AUTH-009) and `POST /auth/revoke` (AUTH-017), consumed by `packages/app/src/SecurityPage.tsx:38-50`. The SDK does not read `security` (`SessionDetails` has no such field), so v0.1 may omit it; app-grade needs it (v1.0).
2. **BB-R-004 §5 "Direct external auth — defer v0.2"**: Medplum's direct external auth (MW-004) is "accept a JWT from a configured issuer as bearer". With Keycloak as the only issuer this is Big Book's *baseline* (MW-001), not a deferral; what is deferred is accepting *additional* issuers (Auth0 etc.) directly, which Keycloak cannot do for a resource server. Suggest rewording §5 to "third-party issuers accepted directly (Medplum `externalAuthProviders`) — defer v0.2".
3. **BB-R-004 §8 "`/oauth2/logout` re-shaped"**: correct — Medplum's logout is a bearer-authenticated POST returning an `OperationOutcome` (OA-010) with no OIDC `end_session` semantics; the SDK's `signOut` depends on that shape (`client.ts:1601-1604`).
4. **BB-R-004 §8 "`/.well-known/openid-configuration` re-shaped"**: correct, but note Medplum advertises `registration_endpoint`/`introspection_endpoint` and no `end_session_endpoint`; nothing in the SDK reads discovery (`client.ts:1077-1079` hard-codes paths), so only external conformance tooling cares.
5. **BB-R-004 §3 "MFA (TOTP) per user"**: Medplum also has **email OTP** (`allowedMfaMethods=email`, AUTH-021/024/025) and a **project-wide** `mfaRequired` setting in addition to the per-user invite flag; and MFA is bypassed for Google/external/exchange logins (MW-018). Keycloak has no native email-OTP authenticator (extension) — list as a known gap.
6. **BB-R-004 §2 "client assertion (private_key_jwt)"**: Medplum's assertion is verified against `ClientApplication.jwksUri` with `aud` = token URL and `iss===sub` (OA-007) — Keycloak "Signed JWT" client authenticator with a JWKS URL matches. But the SDK's `startJwtBearerLogin` (`grant_type=jwt-bearer`) is **not** a Medplum server feature (OA-021); do not list it as a compat target.
7. **BB-R-004 §8a lists** `/auth/login|newuser|newproject|newpatient|profile|scope|mfa/*|changepassword|resetpassword|setpassword|verifyemail`; the real non-goal set is larger: also `/auth/method`, `/auth/login/:id`, `/auth/google`, `/auth/external`, `/auth/exchange`, `/auth/revoke`, `/auth/preauthorize`, `/auth/clientinfo/:id`, `/oauth2/introspect`, `/oauth2/register` (see table). `/auth/revoke` and `/auth/preauthorize` are deferrals rather than non-goals.
8. **BB-R-014 §3 "`Login` non-goal"** is consistent; note that `UserSecurityRequest`, `DomainConfiguration`, `JsonWebKey` and `SmartAppLaunch` are further Medplum admin resource types touched by auth that BB-R-014 §3 does not mention — `SmartAppLaunch` matters for BB-R-022.
9. **ADR-003 "everything else proxied to Keycloak unchanged"** vs `/oauth2/userinfo`: Medplum returns `sub`=`User.id` and `profile`="Practitioner/<id>" (OA-009); Keycloak's `profile` claim is a URL per OIDC. Only `medplum-client-external-idp-demo` reads userinfo; acceptable drift, but a `fhirUser` mapper is cheap.
10. **BB-R-004 exit test** "a user invited with `mfaRequired` cannot complete login without TOTP" matches Medplum only for password logins (MW-018).
11. **Rate limits**: Medplum's are per-IP path categories with a `RateLimit` header (MW-014); BB-R-023 (Traefik) is fine, but `/auth/me` must not fall in the auth bucket if the SDK's every-token-refresh `/auth/me` call is to stay cheap.

#### Notes for the Java port

**Token claims the SDK actually reads** (`packages/core/src/client.ts`): `exp` (`4716`, `3227` via `tryGetJwtExpiration`), `cid` / `client_id` (`4721-4731`), `login_id` (`packages/core/src/jwt.ts:93` → gates `/auth/me`, `client.ts:3247`). Everything else in MW-007 (`sub`, `username`, `scope`, `profile`, `email`, `aud`) is server-internal or for third-party SMART apps. Recommended Keycloak mappers: `login_id` ← `sid` (hardcoded/"session id" mapper or a tiny script mapper), `client_id` ← `azp` for user tokens (service-account tokens already carry `client_id`), `profile` ← per-organisation user attribute (e.g. `bigbook.profile.<orgAlias>`), and `organization` (native in Keycloak 26 with `organization` scope) as the project key. Because Medplum's `profile` differs per project, a token must be bound to one organisation — use the `organization:<alias>` dynamic scope or an org-selection step in the BB `/auth/me` glue.

**Token response fields the SDK stores**: `access_token`, `refresh_token`, `project: {reference:'Project/<id>', display?}`, `profile: {reference:'Practitioner/<id>', display?}` (`client.ts:4733-4738`, `568-583`). `expires_in`, `id_token`, `scope`, `token_type` are ignored. SMART fields (`patient`, `encounter`, `fhirContext`, `smart_style_url`, `need_patient_banner`, `hub.*`) are read by SMART apps only → BB-R-022.

**`/auth/me` fields** (AUTH-009): the SDK needs `profile` (full resource with `id`), `project.{id,name,superAdmin}` (+ `features`, `strictMode` used by the app), `membership.{id,admin,profile,user}`, `config` (`UserConfiguration` with `menu` — the app renders it; default menu generator in `auth/me.ts:135-171` is worth copying verbatim), `accessPolicy` (compiled effective policy — the React `AccessPolicy`-aware components hide fields from it). `user` and `security` are app-only (Security page). The response passes through attachment URL rewriting (presigned URLs, BB-R-009 §3).

**Cookie behaviour**: the only cookie is `medplum-<clientId>` (MW-010), set by the API on login responses (`SameSite=None; Secure; HttpOnly; Max-Age=3600`) and read only by `/oauth2/authorize` for silent re-auth. No API call is cookie-authenticated. Big Book needs none of this; Keycloak's `KEYCLOAK_SESSION`/`AUTH_SESSION_ID` cookies cover SSO and `prompt=none`. CORS must still allow credentials for the SDK's `credentials:'include'` token call (harmless).

**Refresh semantics to reproduce**: public-client refresh (`client_id` only) with rotation; the SDK retries a 401 once with a forced refresh and then calls `onUnauthenticated` (`client.ts:4147-4157`); default `refreshGracePeriod` 5 min drives proactive refresh (`client.ts:1087, 3208-3216`). Keycloak: mark the SDK/app client public, enable "Revoke Refresh Token", set access lifespan ≥ 5 min.

**Things Keycloak cannot do natively (glue or defer)**: (1) `project`/`profile` enrichment of the token response and `/auth/me` (glue, v0.1/v0.2); (2) HTTP Basic client credentials on resource endpoints (MW-002; glue cache for CLI compat, v0.2); (3) bearer-authenticated `/oauth2/logout` and `/auth/revoke` (glue via admin API `DELETE …/sessions/{sid}`); (4) email OTP as an MFA factor (extension); (5) HIBP breached-password check (community SPI); (6) external-to-internal token exchange is a preview feature in Keycloak 26 (`--features=token-exchange`), standard token exchange only handles internal tokens — decide in BB-R-024; (7) pre-authorized code grant for magic links (Keycloak's OID4VCI pre-authorized code is preview and credential-oriented) — glue if needed; (8) `X-Medplum-On-Behalf-Of` (impersonation token exchange with `requested_subject` needs fine-grained admin permissions; a Big Book filter honouring the header for org admins is simpler); (9) SMART `launch`/`aud`/`SmartAppLaunch` context and `patient/` scope compilation (ADR-005); (10) per-IP login rate limiting with the `RateLimit` header (Traefik); (11) IP access rules at login (Keycloak has no per-client IP allowlist authenticator natively — script/conditional authenticator); (12) `retiringSecret` dual-secret rotation (Keycloak "client secret rotation" policy covers it); (13) project-scoped issuers under `/projects/:id/` (non-goal).

**Error shapes**: `/oauth2/token` errors are OAuth JSON `{error, error_description}` (400), but several paths throw FHIR `OperationOutcome` (e.g. `patient/` scope with client credentials, IP block, 429 from upstream). Auth failures on other routes are `OperationOutcome` 401/403/400 (`Authentication error` is 400, not 401). Keycloak's token errors are already OAuth-shaped; Big Book's 401 entry point must emit `OperationOutcome` + `WWW-Authenticate` (MW-005).

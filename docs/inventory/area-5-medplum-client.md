### 5.1 Public methods, client-side behaviours, and the SDK-grade contract


Source snapshot: medplum `packages/core/src` at repo `main` (client.ts 4993 lines, read in full). `Source` paths in this area are relative to `packages/core/src` unless stated. BB-R mapping is against REQUIREMENTS.md / ADR-003 as of big-book `a1b9f49`.

Conventions follow README.md §Conventions. Two extra column meanings for this area:

- **Server contract it depends on** — the definition of *SDK-grade C*: what Big Book must return for this method to work against `@medplum/core` unpatched. "none beyond FHIR R4" means the method needs nothing Medplum-specific.
- **Java SDK disposition** — `port` (v0.1 BB-R-012), `port v0.2`, `skip (reason)`, `n/a local helper`.

Cross-references to areas 1–4 are by their IDs (ADM-*, D*, T*); this area does not re-derive their findings.

#### Notes

##### (a) The SDK-grade C contract, consolidated

An ordered checklist. Each item names the `client.ts` line that proves it. **[confirmed]** = areas 1–4 already found it and this area confirms; **[new]** = not previously recorded; **[uncovered]** = no Big Book brick covers it today.

**Phase 1 — the client must be able to mint a token.**

1. `POST {baseUrl}oauth2/token` accepts form-encoded `grant_type=client_credentials` with `client_id`/`client_secret` **in the body** *and* as HTTP Basic (`:4662-4675`). **[confirmed — BB-R-004.8]**
2. The token response body is JSON containing `access_token`, `refresh_token`, **`project: {reference:'Project/…'}`** and **`profile: {reference:'Practitioner/…'}`** (`:575-583`, `:4732-4737`). Medplum also emits `token_type`, `expires_in`, `scope`, `id_token`, `patient`, `smart_style_url` (`server/src/oauth/token.ts:956-970`); the SDK reads only the four. **[confirmed — D3]**
3. The access token is a **JWT** whose payload carries `exp` (`:4715`, `jwt.ts:104-114`). Without it `isAuthenticated()` is permanently false and `refreshIfExpired` never fires. **[new — D3 covers the claims but not the "must be a JWT at all" consequence]**
4. The JWT carries **`cid`** or **`client_id`** equal to the configured `clientId` (`:4720-4729`). A mismatch throws `unauthorizedTokenAudience` and wipes the login. Keycloak emits `azp`, not `client_id`, on user tokens — a mapper is required. **[confirmed — D3]**
5. The JWT carries a **`login_id`** claim (`jwt.ts:87-94`). This is the gate: without it `medplumServer` is false, `refreshProfile()` returns `undefined` at `:3247`, `/auth/me` is never called, and `getProfile()` stays undefined forever — the client silently behaves as signed-out with a perfectly valid token. **[confirmed — D3]**
6. A non-`ok` token response must carry either an `OperationOutcome` or an OAuth2 `{error, error_description}` body (`:4627-4645`). **[new]**
7. Access-token lifetime must exceed `refreshGracePeriod` (300 s default) or every request triggers a refresh (`:3211-3216`, `:4237`). Practical floor: **15 minutes**. **[new — uncovered]**

**Phase 2 — the client must be able to load the session.**

8. `GET {baseUrl}auth/me` (sent with `cache: no-cache`) returns `{project, membership, profile, config, accessPolicy}` (`:902-908`, `:3252-3256`). `profile` must have an `id` (dereferenced unguarded at `:3255`). **[confirmed — BB-R-004.8, ADR-003 option B]**
9. `project` must include `id`, `name` (used to self-heal the stored login display, `:3283`), `superAdmin` (`:3310`), and for the app `features`/`strictMode`. **[confirmed]**
10. `membership` must include `id`, `profile`, `admin` (`:3319`). **[confirmed]**
11. `config` is a `UserConfiguration` **with an `id`** (`:906`). **[confirmed — D4]**
12. `accessPolicy` is the **compiled** policy — parameters already substituted, admin rules already injected — because `access.ts` evaluates it client-side. **[confirmed — D4]**

**Phase 3 — the client must be able to do FHIR.**

13. FHIR base at `{baseUrl}fhir/R4/` (`:1076`). **[confirmed — BB-R-014.1]**
14. Every request carries `X-Medplum: extended` (`:4032`) ⇒ responses need `meta.project`, `meta.author`, `meta.compartment` (with `Project/<id>`). **[confirmed — D4, T14]**
15. Every request carries `Accept: application/fhir+json, */*; q=0.1` (`:114`, `:4029`); responses must have a `content-type` containing `json` or the body is read as text and, on ≥400, wrapped into a `badRequest` (`:3737-3738`, `:3790`). **[new]**
16. Every request sets `credentials: 'include'` for internal URLs (`:4047-4049`) ⇒ **CORS must allow credentials** and echo the origin, not `*`. **[new — uncovered]**
17. Writes return the **full resource body**, not a bare `Location` (`:2339`, `:2816`). **[new]**
18. Error responses carry `OperationOutcome` with the exact **`id` slug** from the 17-slug set (`outcomes.ts:8-25`). Missing from `medplum-parity.md` per the D4 note: **`multiple-matches`** (412) and **`business-rule`** (422). **[confirmed + 2 new]**
19. Search results emit `Bundle.link[relation='next']` with an absolute URL, and honour `_count=1000` (`:1933-1943`). **[new]**
20. `_summary`/`_elements`-narrowed resources carry `meta.tag.code = 'SUBSETTED'` (`:3688`) or they poison the read cache. **[new — uncovered]**
21. `_offset` is honoured on `_history` (`:2228`). **[new — uncovered]**
22. Conditional create (`If-None-Exist` header) and conditional update (`PUT {type}?{query}`) are supported (`:2392`, `:2421`). **[confirmed — BB-R-002]**
23. `POST /fhir/R4` accepts batch **and** transaction Bundles, returning entries in request order (`:2992`, `:3985-3993`). **[confirmed — BB-R-012.4]**
24. `POST /fhir/R4/$graphql` with `{query, operationName, variables}` (`:3094`). **[confirmed — BB-R-012.4]**
25. `POST /fhir/R4/{type}/$validate` accepts a **bare resource** body (`:2913`). **[new]**
26. `POST /fhir/R4/Binary` accepts a raw body, honours `?_filename=` and `X-Security-Context:`, and returns the `Binary` with a resolvable `url` (`:2597-2609`). **[partially confirmed — BB-R-009; the two Medplum-specific affordances are new]**
27. `401` (never 403) for an expired or invalid bearer token (`:3727`). **[new]**
28. If a `RateLimit` header is emitted at all, it is `"name";r=N;t=S` — malformed values **throw** in `rateLimitStatus()` (`:3888`, `:3896`). And a reset longer than 2 s silently disables all retries (`:3828`). **[new — uncovered]**

29. `POST {baseUrl}admin/projects/{id}/invite` accepting the `InviteRequest` shape and returning **200** with the `ProjectMembership` (`:4623-4625`, `:612-637`). It is the only admin route `@medplum/core` types. **[confirmed — D2, T5]**

31. `/ws/subscriptions-r4` + `Subscription/{id}/$get-ws-binding-token` → `Parameters{token, websocket-url, expiration}`. **[confirmed — BB-R-025]**

##### (c) Auto-batching: is the non-goal safe?

**What it actually does** (SDC-001, `client.ts:1363-1379`, `:3942-3994`): it is a **client-side read coalescer**, off by default (`autoBatchTime` default 0, `:1100-1106`). When on, `GET`s under the FHIR base are held for `autoBatchTime` ms and, if two or more accumulate, packed into a `Bundle{type:'batch'}` and POSTed to the FHIR base. It only ever batches `GET`s — the `AutoBatchEntry.method` type is the literal `'GET'` (`:803`). Writes are never batched (`post`/`put`/`patch`/`delete` go straight to `request()`). Responses are unpacked **positionally**, `entry[i]` ↔ caller `i`.

**Does any server behaviour depend on it?** No. It is purely a request-shape optimisation on the client side of the wire. The server sees an ordinary batch Bundle it must already support for `executeBatch` (checklist item 23). Two second-order requirements it *adds* to that support:
1. entries must come back **in request order** (no `fullUrl` correlation is attempted);
2. a failed entry must carry an `OperationOutcome` in `entry.response.outcome` whose `id` slug is not one of `ok`/`created`/`not-modified`/`accepted`, or the client resolves the caller with `undefined` instead of rejecting (`:3988-3991`).

Both are already implied by item 23 for `executeBatch`. Nothing is new.

**Is the non-goal safe? Yes** — and the reasoning in BB-R-012.8 ("server-side batches are enough") is correct but incomplete. Three supporting facts worth recording:
- It is **opt-in and off by default**, so `@medplum/core` itself does not exercise it unless an app sets `autoBatchTime`. It cannot break SDK-grade C.
- Its purpose is to rescue **React render storms** — dozens of independent `useResource()` hooks firing `readResource` in the same tick. A Java service does not have that shape; it batches by writing a batch.
- The JVM has a better tool anyway: virtual threads / `CompletableFuture.allOf` give real parallelism, where JS had only a single event loop to coalesce on.

One caveat for the docs: because a JVM client will *not* auto-batch, the server's per-request overhead is more exposed. If Baymax's read path turns out to be N+1-shaped, the answer is `executeBatch` or `_include`, not resurrecting this.

##### (d) What a Java SDK cannot reasonably reproduce

| MedplumClient mechanism | Why it does not port | JVM-idiomatic equivalent |
|---|---|---|
| `localStorage`-backed `ClientStorage` (SDC-008) | No browser origin; and writing refresh tokens to disk by default is a worse security posture on a server than in a sandboxed browser origin | A `TokenStore` SPI: `InMemoryTokenStore` (default), `FileTokenStore` (opt-in, 0600, for the CLI in BB-R-017), `VaultTokenStore` (`full` profile). Never persist unless asked. |
| Web Locks cross-tab refresh (SDC-003) | No sibling tabs; `navigator.locks` has no analogue | Keep the **single-flight** semantics with an `AtomicReference<CompletableFuture<Void>>` inside the client instance. Cross-*process* coordination is out of scope: two JVMs sharing one refresh token is a deployment mistake, not a client feature. |
| `window` `storage` event listener (SDC-009) | Same | Nothing. Drop it. |
| `EventTarget` / `TypedEventTarget` (SDC-011) | A DOM idiom | A small `BigBookClientListener` interface (`onResourceModified`, `onUnauthenticated`, `onOffline`) plus, in the Spring starter, `ApplicationEventPublisher` events. Keep `resourceModified`; drop `profileRefreshing`/`storageInitialized`. |
| PKCE stored in `localStorage` across a redirect (SDK-097, `:4166-4184`) | There is no page unload to survive; and hiding the verifier in client state is what forced the storage dependency | Return the verifier to the caller: `PkceChallenge startPkce()` → `{challenge, method, verifier}`, and take it back as a parameter in `exchangeAuthorizationCode`. | `signInWithRedirect` / `signOutWithRedirect` / `signInWithExternalAuth` (SDK-030/031/032) | They call `location.assign` | For desktop/CLI (which is what BB-R-012.1 actually means by "desktop/mobile"): a **loopback redirect** helper — bind `http://127.0.0.1:{ephemeral}`, open the system browser via `java.awt.Desktop`, capture `?code`, call `exchangeAuthorizationCode`. | `XMLHttpRequest` upload-with-progress (SDK-076) | XHR is browser-only; and it bypasses the whole retry/refresh pipeline | If progress is wanted, a counting `HttpRequest.BodyPublisher` wrapper — but keep it inside the normal request pipeline, unlike Medplum. |

#### Contradictions with REQUIREMENTS.md / ADRs

**C1 — BB-R-012.1: "authorization code + PKCE (desktop/mobile)".**
> "`BigBookClient` with auth: client credentials, password (dev only), authorization code + PKCE (desktop/mobile), token refresh, `getProfile()` = `/auth/me`."

Code reality: three separate corrections. (i) **"password (dev only)"** has no MedplumClient counterpart — `startLogin` (`client.ts:1540`) is the Medplum `Login`-protocol route, not an OAuth2 `password` grant, and ADR-003 keeps that route non-goal; Big Book's password login is a Keycloak ROPC call and is a Big Book invention, which is fine but should be labelled as such rather than implying a Medplum port. (ii) **PKCE state**: `startPkce` (`:4166-4184`) writes `pkceState` and `codeVerifier` into `ClientStorage`; a Java SDK must return the verifier to the caller instead (see (d)). (iii) **"`getProfile()` = `/auth/me`"** is not quite right: `getProfile()` (`:3346`) is a pure in-memory getter; the call is made by `refreshProfile()` (`:3246-3269`) and awaited by `getProfileAsync()` (`:3356`). Minor, but the brick reads as if `getProfile()` performs I/O.

**C2 — BB-R-012.2: `upsert(search)` is understated.**
> "Typed CRUD on HAPI R4 structures: `create/read/vread/update/patch/delete/upsert(search)`."

Code reality: `upsertResource` (`:2415-2442`) is a FHIR **conditional update** (`PUT /{type}?{query}`), which additionally requires the server to return `412` with `OperationOutcome.id = "multiple-matches"` on an ambiguous match (`outcomes.ts:195-207`, `getStatus` maps `multiple-matches` → 412 at `:479-481`). That slug is **not** in `medplum-parity.md`'s recorded list, nor in ADR-003's consequence line ("OperationOutcome mapping, 409→412 on `If-Match`"). HAPI returns `412` for ambiguous conditional updates but with no `id`, so `isConflict`/`getStatus` misclassify it as 400. Add `multiple-matches` to the D4/BB-R-014.6 glue list.

**C3 — BB-R-012.3: `next()` and `_include` helpers.**
> "`search(Class, params)` returning a page with `next()`; `searchOne`; `searchResources` (unwrapped); `_include` helpers."

Code reality: the paging analogue is `searchResourcePages` (`:1923-1945`), an async generator that forces `_count=1000` and follows `Bundle.link[relation='next']`. Two implications the brick does not state: the server **must** emit an absolute `next` link, and `_count=1000` must be accepted — BB-R-014.6 caps `_count` at 1000, so the cap has to be inclusive or every paged search fails on the first page. Separately, **`_include` helpers do not exist in MedplumClient**; `_include` is passed as a plain query parameter. The brick is promising something Medplum does not have, which is fine, but it is a Big Book addition not a port.

**C4 — BB-R-012.4: `graphql(query)` vs what the SDK actually needs GraphQL for.**
> "`executeBatch/Transaction`; `graphql(query)`; `validate`."

Code reality: all three port cleanly (SDK-071/072/070). But note `validateResource` (`:2913`) POSTs a **bare resource**, not a `Parameters` wrapper — worth a line in the parity guide. And the *interesting* GraphQL dependency is elsewhere: `requestSchema` (`:2081-2147`) issues a GraphQL query over `StructureDefinitionList(_filter: "name eq X")` and `SearchParameterList(base: "X", _count: 100)`, which HAPI's GraphQL provider does not expose. No Big Book brick records this divergence. It does not block SDK-grade C (nothing in a headless `MedplumClient` flow calls `requestSchema`) but it **does** block `@medplum/react`, and therefore should be recorded against the v1.0 app-grade line in ADR-003 rather than discovered later.

**C5 — BB-R-012.5: Binary is missing two Medplum-specific affordances.**
> "Binary: `createBinary(InputStream, contentType)`, `download(url)`."

Code reality: `createBinary` (`:2597-2609`) sends `?_filename={name}` as a query param and `X-Security-Context: {reference}` as a header. Neither is standard FHIR and neither is HAPI behaviour. BB-R-009 covers Binary storage but mentions neither; BB-R-009.4 defers "binary security context" to v0.2 without noting that the *header spelling* is what the SDK sends. Also `download` (`:3391`) accepts a bare `Binary/{id}` string and only attaches `Authorization` for internal URLs (`isInternalUrl`, `:4005-4021`) — so BB-R-009.3's presigned URLs must work **without** a bearer header, which is consistent, but the `isInternalUrl` path-prefix rule (same origin *and* under the baseUrl path) is a constraint on where MinIO/presigned hosts may live and is not recorded anywhere.

**C6 — BB-R-014.6 "422→400 on validation" contradicts `getStatus()`.**
> "v0.2 glue: OperationOutcome `id`/`issue.code` mapping, 409→412 on `If-Match`, **422→400 on validation**, `X-Trace-Id`."

Code reality: `outcomes.ts` has a `business-rule` slug (`:25`, `businessRule()` at `:392`) that `getStatus()` maps to **422** (`:502-503`). So Medplum does emit 422 for business-rule failures, and the SDK understands it. The "422→400" rule presumably comes from HAPI emitting 422 for *validation* failures where Medplum emits 400 (`badRequest`, no `id` → `getStatus` default 400). Both are true but the brick states only half of it, and as written it would also rewrite a legitimate `business-rule` 422 into a 400. Recommended wording: "HAPI validation 422 → Medplum 400 (`OperationOutcome` with no `id`); preserve 422 only for `OperationOutcome.id = 'business-rule'`."

**C7 — BB-R-012.8 "Autobatching — non-goal (server-side batches are enough)".**
Not a contradiction. Verified in (c): auto-batching is an opt-in client-side read coalescer, off by default, and no server behaviour depends on it beyond ordinary batch-Bundle support. The non-goal is safe. One wording tweak: "server-side batches are enough" is right for the *write* path but the mechanism is actually about *reads*; suggest "client-side read coalescing — a React-render concern; the JVM answer is parallel calls or an explicit batch."

**C8 — BB-R-014.5 / ADR-003's SDK-grade exit test does not prove SDK-grade compat.**
> BB-R-014 exit test (v0.2) and ADR-003's decision table both read: "`@medplum/core` `MedplumClient` with `baseUrl` pointed at Big Book completes client-credentials login, `/auth/me`, and a Patient create/read/search without patching."

Code reality: the test as written **would pass on a server that fails at least six checklist items in (a)**, because a client-credentials + create/read/search script never exercises them:

| Not exercised | Proof line | Consequence of failing it |
|---|---|---|
| `login_id` claim | `jwt.ts:87-94` | Actually *is* exercised — `/auth/me` is in the test. Good. |
| Error-slug mapping | `outcomes.ts:437-534` | A happy-path script never sees a 4xx. `isGone`/`isNotFound`/`isConflict` silently always-false. |
| `_offset` on `_history` | `client.ts:2228` | Paged history silently returns page 1 forever. |
| `Bundle.link` `next` + `_count=1000` | `:1933-1943` | `searchResourcePages` returns one page and stops. |
| `SUBSETTED` tagging | `:3688` | A `_summary` search poisons the read cache with truncated resources. |
| Conditional create / update (`If-None-Exist`, `PUT ?query`) | `:2392`, `:2421` | `createResourceIfNoneExist` and `upsertResource` fail. |
| 401-on-expired-token | `:3727` | A 403 instead of 401 turns a recoverable refresh into a hard failure. |
| Token lifetime ≥ grace period | `:3211-3216` | A short-lived script never notices; a long-running one refreshes on every call. |
| CORS with credentials | `:4047-4049` | Node-based tests never notice; a browser app fails entirely. |

Recommended exit test (replace both BB-R-014.5's v0.2 line and ADR-003's proof cell):

> An unmodified `@medplum/core` script against Big Book must, in one run: (1) complete `startClientLogin`; (2) have `getProfile()`, `getProject()`, `getProjectMembership()` and `getAccessPolicy()` all non-undefined after login; (3) `createResource` a Patient and get the body back with a server-assigned id; (4) `createResourceIfNoneExist` the same Patient and get the **existing** one; (5) `upsertResource` it by identifier; (6) `readResource` it, then `deleteResource` it, then `readResource` again and assert the thrown `OperationOutcomeError` satisfies `isGone(err.outcome)`; (7) `readResource('Patient','00000000-0000-0000-0000-000000000000')` and assert `isNotFound`; (8) create 1001 Patients and assert `searchResourcePages` yields two pages; (9) `readHistory` with `{offset:1}` and assert a different page; (10) run the whole script from a browser against a different origin.

Items 6, 7 and 10 are what turn a smoke test into a compat test.

**C9 — ADR-003 Consequences: the `/oauth2/token` wrapper is understated.**
> "Token issuer is the Big Book public URL; `/.well-known/openid-configuration` and `/oauth2/logout` are re-shaped by Big Book, everything else proxied to Keycloak unchanged (BB-R-004 §8)."

Code reality: `/oauth2/token` **cannot** be proxied unchanged at SDK-grade. `verifyTokens` (`:4708-4738`) reads `tokens.project` and `tokens.profile` from the response **body**, and `isMedplumAccessToken` (`jwt.ts:87`) requires a `login_id` **claim**. Area 1 **D3** already recommends wrapping the token endpoint in v0.2; ADR-003's consequence line still says "everything else proxied unchanged" and should be amended to name `/oauth2/token` alongside `/oauth2/logout` as re-shaped at SDK-grade.

**C10 — ADR-003 Options: "SDK-grade C — `@medplum/core` `MedplumClient` runs unmodified" is ambiguous.**
Code reality: `MedplumClient` has ~100 public methods (Table A), of which ~35 are `skip` on the Big Book side — `Login`-protocol auth, FHIRcast, CDS Hooks, key-value, `$expand-profile`, GraphQL schema introspection, Agent push, PDF. "Runs unmodified" cannot mean "every method works"; it means "a program that uses the supported subset runs unpatched". Recommend ADR-003 say so explicitly and point at this area's Table A `Java SDK disposition` column as the definition of the subset. Otherwise the v0.2 gate is unfalsifiable.

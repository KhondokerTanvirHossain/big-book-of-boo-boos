### Design calls

| # | Topic | What Medplum does | What the docs say now | Recommendation |
|---|---|---|---|---|
| D11 | Transaction atomicity (BB-R-001.4) | A `transaction` bundle is atomic **only** when the project carries the `transaction-bundles` feature. Without it the bundle runs as a batch, silently, and still returns `transaction-response`. Capped at 50 updates, and at 8 entries when any conditional operation is present. | Brick reads as though transactions are unconditionally atomic in v0.1 | Big Book: transactions **always** atomic (HAPI default), no feature gate, no caps. Record Medplum's gate and caps in `medplum-parity.md` as a deliberate divergence. The brick's exit test currently cannot detect the difference — add an entry-rollback assertion. |
| D12 | No-op update suppression (BB-R-001.1 "new version every time") | Byte-identical PUT returns the existing resource with no new version; the router surfaces 304 and `@medplum/core.upsertResource` branches on it (`client.ts:2425-2429`). HAPI versions unconditionally. | "PUT — new version every time" | Strike "every time" from BB-R-001.1. SDK-grade (v0.2) needs the 304 path as glue (~40 lines, compare before write). v0.1 may version unconditionally and say so in the parity guide. |
| D13 | Client-assigned ids inside bundles (BB-R-001.9) | Every batch/transaction entry gets `assignedId`, so any user's POST inside a bundle can carry a client-supplied id (uniqueness pre-checked). This is how `urn:uuid` references resolve. | "Server-assigned UUID ids only" | Add the sub-clause: ids may be client-assigned inside bundles to resolve `urn:uuid`, uniqueness enforced. Otherwise BB-R-001.4 and BB-R-001.9 contradict each other. |
| D14 | Access-policy filtering fails open (BB-R-006.1, ADR-001) | A malformed `criteria` makes `addAccessPolicyFilters` `return` out of the whole loop, dropping every remaining restriction for that request. Authorisation also runs **twice** per write, pre and post. | ADR-001 describes the pre-check only | Big Book fails **closed** on unparseable criteria, and ADR-001 must specify both phases (post-write check is what stops a resource being moved out of its policy's criteria). Record the divergence. |
| D15 | The in-memory matcher (BB-R-006.1, BB-R-007.1) | `matchesSearchRequest` backs `Subscription.criteria` and `AccessPolicy` write-side checks, and is wrong five ways: unknown/chained/`_has`/`_filter` codes → `false`; `number`/`quantity` → `false`; strings are case-insensitive substring where SQL is prefix, `:exact` ignored; `:not-in`/`:in`/`:above`/`:below`/`:text` degrade to equality (so **`:not-in` computes its own inverse** — a policy bypass); dates compare lexicographically. | Bricks assume criteria mean the same thing everywhere | **Validate criteria at write time and reject anything the matcher cannot evaluate.** Do not inherit silent `false`. HAPI's `InMemoryResourceMatcher` has its own gap list; enforce the intersection. Highest-severity finding in area 2. |
| D16 | Cross-project references (BB-R-005.1) | Nothing prevents *writing* a reference into another project. `checkReferencesOnWrite` is off by default and is what makes a dangling cross-project reference an error; the `projectId` predicate only stops *reads*. | "resources in one project never reference another" | Reword to "cannot *resolve* references into another project", and default `enforce_referential_integrity_on_write` **on** in Big Book — stricter than Medplum, and cheap. |
| D17 | Paging wire-compatibility (BB-R-002.7) | Cursor is `2-<epochMillis>-<csv uuids>`, not opaque as the docs claim, and engages only when four conditions hold at once (`_offset` unset, `_count>=20`, one sort rule, `_lastUpdated` ascending). HAPI's is `?_getpages=<uuid>` with server-side state. Separately Medplum **re-serialises** page links, silently dropping `_summary`/`_format`/`_pretty` — page 2 of a `_summary=true` search returns full resources. | "document the difference from Medplum's cursor" | Commit to: offset paging byte-compatible; `next`/`previous`/`self` present with correct semantics; cursor token explicitly **not** wire-compatible. Echo the caller's params in page links rather than re-serialising — fix Medplum's bug, don't port it. Exit test: blind `next`-following terminates. |
| D18 | GraphQL introspection and limits (BB-R-003.4) | Introspection is a **server-wide** config key on a lazily built singleton router, not the `graphql-introspection` project feature (that flag is read by no server code — it is dead, and Medplum's own two doc pages contradict each other). `graphqlMaxDepth` and the query-cost rule enforce **nothing**: both `reportError` calls are commented out, leaving a log line. | "togglable per project; depth/search-count limits configurable" | Reword: introspection server-wide in v0.1, per-project v0.2; depth and cost limits **enforcing** in Big Book (Medplum's are advisory). Enforcing depth is the only DoS control on `$graphql`, ~40-60 lines. |
| D19 | Quantity and number search correctness (BB-R-002.1) | Quantity search **discards system and code** and matches the number alone. Number search has no implicit precision ranges (literal `// TODO`). HAPI does both correctly. | "string/token/reference/date/quantity semantics" | Take HAPI's correct behaviour. Record in `medplum-parity.md` as "Big Book is more correct than Medplum here"; write no bug-compat glue. Note a Big Book quantity search returns **fewer** results than Medplum's. |
| D20 | `$export` and async (BB-R-020, BB-R-001.7) | `$export` at all three levels **ignores `Prefer: respond-async`** and is unconditionally async — non-conformant to the Bulk Data IG. Only five handlers in the server read that header, none of them a CRUD route. Poll URLs are Medplum-shaped (`/fhir/R4/job/:id/status`, `/fhir/R4/bulkdata/export/:id`); HAPI uses `$export-poll-status?_jobId=`. | BB-R-001.7 defers async batch to v0.2; BB-R-020 wires HAPI `$export` | Keep HAPI's conformant behaviour. For v0.2 SDK compat, alias the two Medplum poll URLs to HAPI's job status (the client follows the `Content-Location` we hand out, so a thin alias suffices). |
| D21 | FHIR quota and resource caps (no brick) | Per-interaction-weight quota (READ=1 … WRITE=100) with per-membership and per-project buckets, surfaced as a `RateLimit: "fhirInteractions"` header. Resource caps limit total resources per project. | Not mentioned anywhere | Both are SaaS controls. Resource caps → **non-goal**. Quota → non-goal in v0.x; `@medplum/core` does not require the header. BB-R-023 (Traefik) stays coarse HTTP limiting. |
| D22 | `$expunge` / hard delete (no brick) | Super-admin `$expunge` and `purgeResources` are the only ways to remove history; retention is otherwise unbounded with no pruning. | No brick mentions either | Add to BB-R-018 (v0.2, audit) as `wire HAPI $expunge`. Needed for GDPR-style erasure and for the `purge` super-admin row (area 1 D8). |

### Text fixes (area 2)

| # | Brick | Fix |
|---|---|---|
| T18 | BB-R-001.3 `_history` | Medplum has **instance-level `_history` only** — no type-level, no system-level (`GET /Patient/_history` returns 404). HAPI has all three. Reword to instance-level as the Medplum bar, note the HAPI superset. Retention is unbounded with no pruning. |
| T19 | BB-R-001.2 conditional operations | `multipleMatches` → **412** `id=multiple-matches` on conditional create, update, delete **and** patch. The brick mentions only conditional update. Pin HAPI `allow_multiple_delete=false`. Add the two conditional update-as-create cases: 0 matches with a body `id` → 400; 0 matches without → 201. |
| T20 | BB-R-001.5 `$validate` | Type-level only in Medplum (`POST /:resourceType/$validate`, validates the body). No instance-level, no GET. HAPI has both. |
| T21 | BB-R-003.1 `$graphql` paths | Only `POST /fhir/R4/$graphql` exists. No instance-level `$graphql`, no GET. Strike the instance path or mark it a HAPI superset. |
| T22 | BB-R-002.8 `_text`/`_content` | Medplum **never implemented** these — the params 400 as unknown. This is a new capability from HAPI + OpenSearch, not a deferral of parity. Medplum's nearest analogue is the token `:text` modifier over a 7-param allowlist. |
| T23 | BB-R-002.1 modifiers | Medplum parses and then **400s** on `:above`, `:below`, `:in`, `:not-in`, `:of-type`. HAPI implements them — a net gain, so the exit test must not assert Medplum's 400s. Medplum's own extensions `sw` and `:present` are non-goals. |
| T24 | BB-R-002.3 includes | `_include=*` / `_revinclude=*` unsupported in Medplum (400), supported in HAPI. `:iterate` capped at depth 5 / 1000 entries, breaching throws **500** not 400. `_revinclude` sub-searches hard-pinned to `_count=1000`, silently truncating. |
| T25 | BB-R-002.5 `_filter` | Keep `wire HAPI`, but add an exit item: measure which operators and whether dotted paths work. Medplum's `_filter` recurses into the full builder so dotted paths become chained searches; its documented `in`/`ni` ValueSet operators **throw 400** in code. |
| T26 | BB-R-002.6 compartment | Two parameters, not one: `_project` over `meta.project` and `_compartment` over `meta.compartment`. `_compartment` can also appear as a chain link. |
| T27 | BB-R-002.1 SearchParameters | Medplum loads them from **static JSON bundles at boot**; a `SearchParameter` resource POSTed to the store is inert. HAPI supports runtime registration plus `$reindex` — a free gain worth stating. |
| T28 | BB-R-014.1 status codes and content type | **422 is effectively unreachable**: only `business-rule` maps to 422, and `badRequest`/`validationError` emit no `id`, so validation lands on 400. Change to "404/410/412/400 semantics (422 only for `business-rule`)". `application/fhir+json` is not universal — `$graphql`, `/metadata`, `$versions`, well-knowns and the bulk manifest return `application/json`. |
| T29 | BB-R-014.6 v0.2 glue list | Add eight missing items: `Location` without `/_history/<vid>`; batch entry `response.status` bare `"201"` and relative `response.location`; DELETE body `OperationOutcome{id:'ok'}`; honouring `X-Medplum: extended`; method-not-allowed 404 not 405; the `Access-Control-Expose-Headers` list; `$graphql` returning `application/json`. Also: the `_count` cap 1000 lives in the search layer, not the route layer. |
| T30 | BB-R-005.7 super-admin | The code has **two** elevated identities: the super-admin *user* repo (skips project filters, keeps a policy) and the *system* repo (no projects, no policy), obtainable from any repository by calling `getSystemRepo()` with no audit trail. Big Book's system-repo equivalent must be internal, non-token-reachable, and logged. |
| T31 | BB-R-006.1 criteria restriction | "`:not`/`:missing` only, no chaining" is a **convention, not enforced** — `addAccessPolicyFilters` calls the full search builder, so a chained criteria compiles and works. Either enforce the restriction or drop the claim. |

#### 1. Contradictions with REQUIREMENTS.md / ADRs

**BB-R-001.3** — *"`_history` per resource and per type; every version retained."*
The code registers **only** `GET :resourceType/:id/_history` (`fhir-router/fhirrouter.ts:326`). There is no type-level `GET /Patient/_history` and no system-level `GET /_history`; `getResourceInteractions` defaults to a list that includes `history-instance` but **not `history-type`** (`config/capabilitystatement.ts:10-19`). `GET /fhir/R4/Patient/_history` in Medplum falls through to the `:resourceType/:id` read route and returns **404 `not-found`**. HAPI implements type- and system-level `$history` out of the box, so Big Book will *exceed* the brick here for free — but the brick's claim that Medplum has per-type history is wrong. **Fix**: reword to "`_history` per resource instance (Medplum); type-level history is a HAPI superset Big Book keeps."

**BB-R-001.4** — *"Batch (`type: batch`) and transaction (`type: transaction`) bundles, with internal (`urn:uuid`) and conditional references, `ifMatch` version checks, PATCH entries."*
Three mismatches. (a) In Medplum a `transaction` bundle is **only** atomic when the project carries the `transaction-bundles` feature; without it `isTransaction()` is false (`fhir-router/batch.ts:873-875`) and the bundle runs as a batch, **silently**, still returning `transaction-response`. The brick reads as though transactions are unconditionally atomic. (b) PATCH entries in Medplum require a base64 `Binary` or a `Parameters` resource (`batch.ts:763-799`) — a plain JSON-Patch array is impossible in a bundle. (c) Transactions are capped at **50 updates** and, when any conditional operation is present, at **8 entries** (`batch.ts:29-30,244-254`). Neither cap is mentioned in the brick and neither exists in HAPI. **Fix**: add "transaction atomicity is unconditional in Big Book (HAPI); Medplum's `transaction-bundles` gate and its 50/8 entry caps are not reproduced" and note the PATCH entry encodings.

**BB-R-001.9** — *"Server-assigned UUID ids only; `PUT /Type/<new-id>` (update-as-create) is rejected as in Medplum (ADR-003): 404 for project users; super-admin may set ids (BB-R-005.7) and gets 200."*
Consistent with the code (`repo.ts` per the parity guide, rows d/d') and with `CapabilityStatement.updateCreate: false` (`fhir/metadata.ts:302`). **But** the brick does not cover the *conditional* update-as-create case, which behaves differently: `PUT /Patient?identifier=X` with 0 matches and a body `id` → **400** `Cannot perform create as update with client-assigned ID`, not 404 (`fhir-router/repo.ts:347-353`, parity row a2); with 0 matches and no `id` → **201** (parity row a3). Two more paths a strict-parity test must cover. **Fix**: add a sentence to 001.9.

**BB-R-001.5** — *"`$validate` against base R4 and any loaded profile."*
Medplum registers `$validate` **only at type level** (`POST /:resourceType/$validate`, `fhir/routes.ts:432-436`) and it validates the request **body**. There is no instance-level `POST /Patient/:id/$validate` and no `GET`. HAPI provides both. Superset again, but the brick should not imply instance-level `$validate` exists in Medplum.

**BB-R-003.1** — *"`POST /fhir/R4/$graphql` **and `/fhir/R4/Type/id/$graphql`**, FHIR GraphQL spec."*
**Direct contradiction.** Only `POST $graphql` is registered (`fhir-router/fhirrouter.ts:334`). There is **no** instance-level `/Type/:id/$graphql` route in Medplum at all — such a request has 3 path segments and would match `:resourceType/:id/$graph`… no, `$graphql ≠ $graph`, so it falls to `POST :resourceType` (2 segments) — segment counts differ, so it 404s. There is also no `GET /$graphql`. **Fix**: strike the instance-level path from BB-R-003.1 or mark it as a HAPI superset (HAPI does implement instance-level `$graphql`).

**BB-R-003.4** — *"Introspection togglable per project (`graphql-introspection` feature)."*
In the code introspection is a **server-wide** config key, not a project feature: `new FhirRouter({introspectionEnabled: getConfig().introspectionEnabled})` is built **once, lazily, on the first request** (`fhir/routes.ts:221-235`) and reused for the process lifetime. The three genuinely per-project GraphQL knobs are `graphqlBatchedSearchSize`, `graphqlMaxDepth` and `graphqlMaxSearches`, passed per request via `req.config` (`routes.ts:493-496`). A `graphql-introspection` project feature does not gate this route. **Fix**: correct 003.4 to "server-wide `introspectionEnabled`; depth/search-count limits are per-project system settings."

**BB-R-014.1** — *"FHIR base `/fhir/R4` with Medplum-identical paths, headers (`Content-Type: application/fhir+json`), status codes (404/410/412/422 semantics)."*
Two problems. (a) `application/fhir+json` is **not** universal: `$graphql`, `/metadata`, `$versions`, both well-knowns and the bulk manifest all return `application/json` (FE-032); `$csv` returns `text/csv`; Binary reads return the blob's own type. (b) **422 is essentially unreachable on the FHIR routes.** `getStatus` maps only `business-rule` to 422 (`core/outcomes.ts:500-501`), and `badRequest()`/`validationError()` emit **no `id`**, so schema and profile validation failures land on **400** (`core/outcomes.ts:279-293, 506-507`). The parity guide's compat-action column already says "422→400 on validation". **Fix**: change 014.1 to "404/410/412/400 semantics (422 only for `business-rule`)" and qualify the content type.

**BB-R-014.6** — *"v0.1 by HAPI config (UUID ids, no update-as-create, `_count` cap 1000, `application/fhir+json`, `ETag`); v0.2 glue: OperationOutcome `id`/`issue.code` mapping, 409→412 on `If-Match`, 422→400 on validation, `X-Trace-Id`."*
Mostly right, but the v0.2 glue list is **incomplete**. Reading the routes, these also need rewriting and none is listed: (1) **`Location` has no `/_history/<vid>` suffix** in Medplum (FE-012) while HAPI always appends it; (2) **batch entry `response.status` is a bare `"201"`** while HAPI emits `"201 Created"` (FE-021); (3) **batch entry `response.location` is relative** (`Patient/abc`) while HAPI emits absolute; (4) **DELETE returns 200 + `OperationOutcome{id:'ok'}`**, and HAPI's 200 body differs in text (parity row b); (5) **`X-Medplum: extended`** must be honoured or `@medplum/core` clients lose `meta.project`/`meta.author` (FE-015); (6) **method-not-allowed is 404, not 405** (FE-038); (7) the **`Access-Control-Expose-Headers`** list (FE-016) is load-bearing for any browser SDK; (8) `$graphql` must return `application/json` (FE-032). **BB-R-002.7 / paging** — the brick says "Paging: offset (`_offset`) and cursor (`next` links)". Confirmed at the route layer only for `_history` (`_offset`/`_count` parsed at `fhir-router/fhirrouter.ts:197-198`); search paging is entirely inside the repository (Area 2b). No contradiction, just a scope note.

**ADR-003 (option B, v0.1)** — nothing in this area contradicts it. The four mount prefixes (FR-001) are an aliasing convenience; only the plain `/fhir/R4` form is needed for option B, and the `/projects/:id/` variant overlaps with BB-R-005.7's `X-Project` header decision — worth an explicit "we chose the header, not the path prefix" line in ADR-004.

##### (c) Batch vs transaction in Medplum

1. **The gate.** `isTransaction()` = `bundle.type === 'transaction' && req.config.transactions`, and `req.config.transactions = project.features.includes('transaction-bundles')` (`fhir/routes.ts:498`). **Without the feature a transaction bundle degrades to batch semantics silently** — no error, no warning, and the response is still typed `transaction-response`. Big Book should make transactions unconditionally atomic (HAPI does) and *not* reproduce the gate; but any Medplum migration script that assumed the gate was off will behave differently.

2. **Ordering.** Entries are **reordered before execution**, bucketed by REST interaction into the fixed sequence `transaction → batch → delete → create → update → patch → operation → search-system → search-type → read → vread → history-*` (`fhir-router/batch.ts:398-414,474-477`). Client entry order is not preserved. HAPI's `TransactionProcessor` orders DELETE → POST → PUT/PATCH → GET, which is close but not identical (Medplum runs *nested bundles* first and *reads last*).

3. **`urn:uuid` resolution.** Ids are assigned **eagerly at preprocess time** by `repo.generateId()` and stored in a `resolvedIdentities` map keyed by the entry's `fullUrl` (`batch.ts:554-569`). Only **then** are entries executed, and each entry is deep-walked to replace any string matching `urn(:|%3A)uuid(:|%3A)<uuid>` (`:32`, `:862-871`). Consequences: (i) forward *and* backward references both work — a Patient may reference an Observation declared later; (ii) the match is a **substring** replace, so `"urn:uuid:abc"` embedded inside a longer string (a FHIRPath expression, a narrative) is also rewritten; (iii) percent-encoded URNs inside batch entry URLs are handled; (iv) on a serialization retry, preprocessing is deliberately **not** re-run so ids stay stable (`:198-217`).

4. **Conditional references.** A conditional URL (`PUT /Patient?identifier=X`, `DELETE /Patient?…`, `PATCH /Patient?…`) is resolved by a `count=2` search **at preprocess time** and `entry.request.url` is **rewritten to the absolute `Type/id`** (`:615`), so the entry executes unconditionally. 0 matches: DELETE is skipped, PUT with a body `id` → `Cannot provide ID for create by update`, PUT without id gets a fresh id, PATCH → `Conditional PATCH did not match any resources`. 2 matches → `Conditional <M> matched multiple resources`. `ifNoneExist` on a create resolves to the **existing** resource's reference if exactly one match, so downstream `urn:uuid` references point at the pre-existing resource. **Note the resolution errors are `badRequest` (400), not `multipleMatches` (412)** — a conditional PUT that would return 412 standalone returns a 400-shaped entry inside a bundle.

5. **Per-entry errors.** Batch: the error becomes the entry's `response.outcome` with `response.status` set from `getStatus`, and processing continues. **A 429 short-circuits**: every remaining entry (in *ordering* order) is filled with the rate-limit outcome (`:683-690`). Transaction: any non-ok entry outcome throws out and the whole bundle returns a top-level 400.

6. **Entry response shape.** `{response: {outcome, status: '<decimal>', location: 'Type/id' | undefined}, resource}` (`:892-901`). `status` is a bare number string (`"201"`), **not** HAPI's `"201 Created"`; `location` is relative, **not** HAPI's absolute URL; `outcome` is always present, which HAPI only does on failure.

7. **Limits.** Transaction only: >50 update entries → 400; any conditional operation promotes to SERIALIZABLE and then >8 entries → 400; duplicate resolved identity → 400.

8. **`async-batch`.** A **separate** project feature from `transaction-bundles`. `POST /fhir/R4` with `Prefer: respond-async` requires `async-batch`, parses with `maxBatchSize` (50 MB) instead of `maxJsonSize` (1 MB), rejects `transaction` bundles **when `transaction-bundles` is also on**, and returns 202 + `Content-Location` to `/fhir/R4/job/:id/status`. Work in the job is exempt from the caller's FHIR quota. The re-entrant processor (`BatchProcessor.preprocess`/`fromState`/`processNextEntry`, `batch.ts:167-181,285-316`) checkpoints `{mutated bundle, bundleInfo, resolvedIdentities, preprocessResults}` plus a position marker so a worker crash resumes without re-assigning ids — a design note worth copying if Big Book ever does async batch.

##### (e) What HAPI JPA does differently — the BB-R-014.1/14.6 glue list

Ordered by how likely it is to break an `@medplum/core` client:

1. **`OperationOutcome.id` is absent in HAPI.** HAPI's `OperationOutcome` has no `id` and its `issue.code` vocabulary differs (`processing` where Medplum uses `deleted`/`multiple-matches`). `@medplum/core`'s `isOk`/`isNotFound`/`isGone`/`isConflict`/`isUnauthenticated` switch on `id`, **not** on HTTP status. Without a translating `@ControllerAdvice` every SDK error branch misfires. **This is the single highest-value piece of glue in the whole area.** The full slug table is §(b).
2. **Version conflict: HAPI 409, Medplum 412.** `ResourceVersionConflictException` → 409; Medplum returns 412 `id=precondition-failed`, `issue.code=processing` (parity row e). Also the two 412 flavours must be distinguished: `precondition-failed` (stale `If-Match`) vs `multiple-matches` (conditional operation matched >1).
3. **Update-as-create.** HAPI returns 201 + `Location` for `PUT /Patient/<fresh-id>`; Medplum returns **404 `not-found`** for project users and **200 with `ETag` and no `Location`** for super-admin (parity rows d/d'). Requires `client_id_strategy=NONE` plus an interceptor that maps the resulting rejection to 404 (and a super-admin bypass per BB-R-005.7). `CapabilityStatement.updateCreate` must be forced to `false`.
4. **`Location` suffix.** HAPI: `Location: https://…/fhir/R4/Patient/abc/_history/1`. Medplum: `https://…/fhir/R4/Patient/abc` (no history suffix, `fhir/response.ts:19-21,30-32`). Strip it.
5. **Batch entry response shape.** HAPI: `response.status = "201 Created"` (status + reason phrase), `response.location` absolute, `response.outcome` present only on failure. Medplum: `"201"`, relative `Patient/abc`, `outcome` always present. Rewrite in a bundle post-processor.
6. **`urn:uuid` placeholder resolution.** HAPI resolves placeholders during transaction execution in its own dependency order; Medplum assigns ids in a *preprocess pass* and then does a **string-level** substring replace over the entire entry (`batch.ts:862-871`). Differences that bite: Medplum rewrites URNs inside narrative text, extension values and FHIRPath strings; HAPI only rewrites `Reference.reference` and canonical fields. Also, Medplum's bucketed reordering (delete → create → update → patch → operation → search → read) differs from HAPI's. A bundle that works in Medplum may fail in HAPI if it relied on a read entry seeing a write from the same bundle.
7. **Conditional operations in bundles return 400, not 412.** Medplum's preprocess-time resolution errors are `badRequest` (`Conditional PUT matched multiple resources`), whereas the standalone route returns 412 `multiple-matches`. HAPI is consistent (412 both ways). If a Medplum client special-cases the 400, it will need the HAPI behaviour instead — recommend **not** reproducing Medplum's inconsistency, but documenting it.
8. **DELETE body.** Both return 200, but Medplum's body is `OperationOutcome{id:'ok', issue:[{code:'informational', text:'All OK'}]}` with **no `ETag`/`Location`**; HAPI's says "…was already deleted" on the second delete (parity row b). Rewrite the body.
9. **Deleted resource read.** Medplum: 410 `id=gone`, `issue.code=deleted`, text "Gone". HAPI: 410, `issue.code=processing`, "Resource was deleted at …" (parity row c). Rewrite both fields.
10. **Method-not-allowed.** Medplum's router matches on exact segment count, so a wrong verb on a valid path yields **404**; HAPI returns **405**. A strict-parity harness will catch this. Cheap interceptor.
11. **`_format` and XML.** HAPI honours `_format=xml` and serves XML by default. Medplum has no `_format` at all and advertises `format: ['json']` only. Narrow the `FhirContext` / restrict `Accept` handling, or accept the superset and document it.
12. **Conditional read.** HAPI implements `If-None-Match`/`If-Modified-Since` and will return **304**; Medplum never returns 304 and advertises `conditionalRead: 'not-supported'`. Superset — safe to leave on, but the CapabilityStatement must say `not-supported` if strict parity matters.
13. **Type- and system-level `_history`.** HAPI has them; Medplum does not (see §1). Superset.
14. **Instance-level `$graphql`.** HAPI has it; Medplum does not. Superset.
15. **`X-Medplum: extended`.** Nothing in HAPI. Big Book must implement it: without the header, strip the six `meta` fields (`author`, `project`, `account`, `accounts`, `compartment`, `deleted`) from every read; with it (and super/project-admin) allow writing `meta.account`. `MedplumClient` always sends it, so an SDK-grade client will *expect* the extended fields.
16. **JSON serialisation.** Medplum's `stringify` recursively strips `null`, `undefined`, `""`, `{}` and `[]`. HAPI's parser omits nulls but **keeps empty arrays**, and JSON responses differ byte-for-byte. Configure Jackson `NON_EMPTY` plus an empty-collection filter if byte parity is ever tested.
17. **Content types per endpoint.** `$graphql`, `/metadata`, `$versions`, the well-knowns and the bulk manifest are `application/json` in Medplum (FE-032). HAPI serves `/metadata` and `$graphql` as `application/fhir+json`. Cheap `produces=` overrides.
18. **`Access-Control-Expose-Headers`.** HAPI's `CorsInterceptor` defaults do not include `Content-Location`, `ETag`, `Last-Modified`, `Location`, `RateLimit`, `X-Request-Id`, `X-Trace-Id`. Without them a browser SDK cannot read the ETag or the async poll URL. **Mandatory glue for BB-R-014.2/13.**
19. **Batch PATCH entry encoding.** HAPI accepts a `Parameters` FHIRPath Patch in a bundle entry; it does **not** accept Medplum's base64-`Binary`-containing-a-JSON-Patch-array convention (`batch.ts:766-772`). Either add a bundle pre-processor or document the incompatibility.
20. **Async poll URL.** Medplum: `/fhir/R4/job/:id/status` (AsyncJob body, 200/202) and `/fhir/R4/bulkdata/export/:id` (manifest, 200/202-empty/404-on-cancelled). HAPI: `$export-poll-status?_jobId=…` returning a `Parameters`/manifest. Any Medplum client polling loop breaks; BB-R-020's glue must expose the Medplum-shaped URLs (the `Content-Location` we hand out is what the client follows, so a thin alias is enough).
21. **Body size.** `maxJsonSize` defaults to **1 MB** in Medplum, and a 1.1 MB create is rejected with **413 `id=content-too-large`, `issue.code=too-long`**. HAPI/Spring defaults are larger. Set the limit explicitly and map the Spring `MaxUploadSizeExceededException` to that outcome.
22. **Presigned attachment rewriting is a response-body transform** (FE-030), not an endpoint. Every authenticated FHIR response walks the body and replaces `url`/`path` strings pointing at a Binary with a presigned URL, **reading the Binary through the caller's own access policy** so unreadable attachments degrade to `Binary/<id>` rather than leaking. HAPI has no equivalent; this is a Big Book interceptor when BB-R-009.3 lands in v0.2.
23. **The tracing extension.** Every Medplum error body carries `extension[url=https://medplum.com/fhir/StructureDefinition/tracing]` with `requestId`/`traceId` sub-extensions. The parity guide already flags adding it as a v0.2 decision; note that Medplum puts it on **error bodies only**, not on success bodies.
24. **Query-string cap.** 70,000 characters → 400 (`urlrouter.ts:13`). Mainly relevant to batch entry URLs. One guard.
25. **Binary write path bypasses body parsing.** Medplum mounts the Binary router *above* all parsers so gigabyte uploads stream to storage (`app.ts:213`, comment `binary.ts:95-99`), and handles `Content-Encoding: gzip|deflate` itself. In Spring this means a dedicated `HttpServletRequest.getInputStream()` controller outside the normal `@RequestBody` path, or HAPI's `BinaryStorageInterceptor`.

#### Contradictions with REQUIREMENTS.md/ADRs

**1. BB-R-001.3 "every version retained" — true for Medplum, but the brick does not say history is *unprunable by ordinary users*.**
> BB-R-001.3: "`_history` per resource and per type; every version retained."

Code reality: retention is unbounded and there is **no pruning mechanism at all** short of super-admin `$expunge` (REPO-029) and super-admin `purgeResources` (REPO-030). Also, the brick says "`_history` per resource **and per type**" — `Repository.readHistory` is instance-only (`WHERE id = $1`). Type-level and system-level `_history` are not implemented in the repository layer. **Recommendation:** narrow BB-R-001.3 to instance-level `_history` in v0.1 and add a note that HAPI's type/system `_history` is free if wanted; add `$expunge` explicitly (it is currently unmentioned by any brick — REPO-029 is a GAP).

**2. BB-R-001.2 "many → error" is right, but the *status* is 412, not 409, and the same rule applies to conditional DELETE — where the spec allows deleting all matches.**
> BB-R-001.2: "`upsert` = conditional update `PUT /Type?search` — one match updates, zero creates, many → error."

Code reality (REPO-022/023/024): `multipleMatches` → **412** with `OperationOutcome.id = multiple-matches` on conditional create, update, delete **and** patch. HAPI's default is 412 with `issue.code=processing` and a different message; HAPI also has `allow_multiple_delete`, which **must be disabled** to match. The brick does not mention conditional delete or conditional patch at all. **Recommendation:** extend BB-R-001.2 to cover all four conditional interactions and pin `allow_multiple_delete=false`.

**3. BB-R-001.9 is correct and confirmed, but understates the super-admin case.**
> BB-R-001.9: "Server-assigned UUID ids only; `PUT /Type/<new-id>` … is rejected as in Medplum (ADR-003): 404 for project users; super-admin may set ids (BB-R-005.7) and gets 200."

Code reality: exactly matches `canSetId() === isSuperAdmin()` (REPO-004). **But** there is a third path the brick misses: `CreateResourceOptions.assignedId` (REPO-003), set by **batch/transaction bundle processing for every entry**. So inside a bundle, *any* user's `POST` can carry a client-supplied id, subject only to a uniqueness pre-check. Since BB-R-001.4 commits to transaction bundles with `urn:uuid` references in v0.1, Big Book needs the same escape hatch or an equivalent `urn:uuid` resolver. **Recommendation:** add a sub-clause to BB-R-001.9: "except inside batch/transaction bundles, where entry ids may be client-assigned to resolve `urn:uuid` references; enforce uniqueness."

**4. `isNotModified` (REPO-015) is a genuine behavioural surprise the bricks do not cover — and it has a latent inconsistency worth flagging upstream.**
BB-R-001.1 says "`update` (PUT — **new version every time**)". Medplum does **not** create a new version when the payload is byte-identical: `updateResourceImpl` returns `existing` untouched, which the router surfaces as a 304 and which `@medplum/core`'s `upsertResource` explicitly handles (`client.ts:2425-2429`). Note also that `isNotModified` compares `existing` against `result`, and `result.meta` has already been restamped with a fresh `versionId`/`lastUpdated` at that point (`repo.ts:1130-1139` runs before `repo.ts:1177`) — so the comparison can only return true when `stringify` normalisation happens to elide those differences. Either way the observable contract is "identical payload → no new version", and HAPI JPA **does** create a new version unconditionally. **Recommendation:** either strike "new version every time" from BB-R-001.1 and add a no-op-suppression glue item, or accept the divergence and document it in `medplum-parity.md`. Given `@medplum/core` depends on the 304, SDK-grade compat (BB-R-014.5, v0.2) needs the glue.

**5. BB-R-005.1 "resources in one project never reference another" is enforced only when `checkReferencesOnWrite` is on.**
> BB-R-005.1: "**Project** = isolated container: resources in one project never reference another."

Code reality: nothing prevents *writing* a cross-project reference. The `projectId` predicate stops you from *reading* the target, and `checkReferencesOnWrite` (REPO-028) — **off by default, a per-project flag (BB-R-005.6)** — is what turns a dangling cross-project reference into a write-time error. With it off, a resource in project A can happily store `Patient/<id-in-B>`. **Recommendation:** reword BB-R-005.1 to "resources in one project cannot *resolve* references into another", and make `enforce_referential_integrity_on_write` default **on** in Big Book (a stricter, cleaner default than Medplum's).

**6. BB-R-006 lists `readonly`/`readonlyFields`/`hiddenFields` but not the `writeConstraint` two-phase check semantics, and REPO-051 has a fail-open path.**
ADR-001 already records "readonly fields restore, not reject" (REPO-016) — consistent. But two things are unstated: (a) authorisation runs **twice** per write, before and after (REPO-053), which is what prevents a resource being moved out of a policy's criteria — Big Book's `AuthorizationInterceptor` mapping must reproduce both phases, not just the pre-check; (b) `addAccessPolicyFilters` **abandons all filtering for the request** when it meets a malformed `criteria` (`return`, not `continue` — `repo.ts:1901`), which is fail-open. **Recommendation:** add the two-phase requirement to BB-R-006.1 as an explicit exit-test line, and make Big Book's equivalent fail **closed** on an unparseable criteria. Note this as a deliberate divergence in `medplum-parity.md`.

**7. BB-R-005.7 "Super-admin project: server-wide view" — the code has *two* distinct elevated identities, not one.**
The super-admin *user* repo (`project.superAdmin`) still carries `projects: [superAdminProject, …]` and therefore still gets `addProjectFilters` **skipped** but keeps an access policy; the *system* repo (`getGlobalSystemRepo`, `getSystemRepo`) has `projects: undefined` and no policy at all, and is obtainable from **any** repository by calling `getSystemRepo()` (REPO-066) with no audit trail. **Recommendation:** BB-R-005.7 should say that Big Book's equivalent of the system repo is an internal, non-token-reachable context, and that every elevation is logged — Medplum's is neither.

**8. Nothing in REQUIREMENTS.md covers FHIR quota (REPO-059) or resource caps (REPO-060).**
BB-R-023 (v0.2, Traefik) is coarse HTTP rate limiting; Medplum's quota is *per-interaction-weight* (READ=1 … WRITE=100) with a per-membership and per-project bucket, surfaced as a `RateLimit: "fhirInteractions"` header that `@medplum/core` reads. Resource caps have no brick at all. **Recommendation:** both are SaaS controls; mark resource caps `non-goal` and record the `RateLimit` header shape as a BB-R-014.6 v0.2 line only if SDK-grade compat needs it (it does not — `@medplum/core` does not require the header).

#### Notes for the Java port

##### (a) What HAPI JPA genuinely cannot do

Most of Area 2b maps onto HAPI mechanisms. Five things do not, and one is a real gap.

1. **No-op update suppression (REPO-015).** HAPI JPA creates a new version on every `update()`, full stop — there is no `deepEquals` short-circuit and no configuration for one. This is a *genuine* gap, not a difference: reproducing it requires a `STORAGE_PRESTORAGE_RESOURCE_UPDATED` interceptor that re-reads the current version, normalises both sides, compares, and **aborts the write** — and HAPI's pointcut contract makes "abort silently and return the existing resource with 304" awkward (the interceptor can throw, but the natural throw is an error, not a 304). Estimate ~80 lines plus a custom exception mapped to 304. It matters because `@medplum/core.upsertResource` branches on the 304 (`client.ts:2425-2429`).

2. **Per-project storage-layer flags (`checkReferencesOnWrite`, `strictMode`, `validateTerminology`, `defaultProfile`).** HAPI's `enforce_referential_integrity_on_write` is a **server-wide** `JpaStorageSettings` boolean, not per-partition. Making it per-tenant means either an interceptor that does the reference check itself for partitions where the global flag is off, or accepting one setting for the whole server. For `lite`, one server-wide setting is the honest answer; per-project is glue in v0.2.

3. **`meta.author` / `meta.project` / `meta.compartment` / `meta.accounts` as first-class stored meta (REPO-048/049/050).** HAPI's `ResourceMetadataKeyEnum` has no slots for these; `Meta` in R4 has no `author`/`project`/`compartment` elements either — Medplum ships a patched `profiles-medplum.json`. Big Book must either (i) carry them as `meta.extension` (wire-incompatible with `@medplum/core`, which reads `meta.project` as a plain field) or (ii) register a custom `Meta` profile and a `IParser` post-processor. RES-M01/M02/M05 already assign this to glue; this area confirms the cost is a serialisation-layer shim, not just an interceptor. HAPI's `AUTHOR`/partition columns cover the *storage*; the *wire shape* is the work.

4. **Elevation-within-transaction (`getSystemRepo()`, REPO-066).** HAPI has no equivalent of "same JDBC connection, different authorisation" because authorisation lives in interceptors bound to the `RequestDetails`. The Java equivalent is a `SystemRequestDetails` (HAPI does provide this) passed to the DAO directly, which bypasses interceptors entirely — functionally equivalent and arguably cleaner, but it means every elevation site must be explicit rather than `repo.getSystemRepo()`.

5. **Conditional references outside transaction bundles (REPO-057).** HAPI resolves conditional references (`Patient?identifier=…`) inside transaction bundles. Medplum resolves them on **every** write, including a bare `POST /Observation` whose `subject.reference` is a search string. If Big Book wants parity, that is a `STORAGE_PRESTORAGE_*` interceptor walking the resource. Low value; recommend **non-goal for v0.1**, documented in `medplum-parity.md`.

Everything else has a named HAPI mechanism: soft delete + 410 (native), `$expunge` (`expunge_enabled`, `expunge_deleted_resources`), server-assigned UUIDs (`resource_server_id_strategy=UUID`, `resource_client_id_strategy=NOT_ALLOWED`), `If-Match`/version conflict (`ResourceVersionConflictException`, 409→412 rewrite is BB-R-014.6 glue), JSON/FHIRPath Patch (native), conditional CRUD (native, with `allow_multiple_delete=false`), lookup tables (`HFJ_SPIDX_*`, `HFJ_RES_LINK`, `TRM_CONCEPT*`), reindex (`ResourceReindexingSvc`), binary storage (`IBinaryStorageSvc`), validation (`FhirInstanceValidator` in `RequestValidatingInterceptor`), serialization retry (Spring `@Retryable`).

##### (b) Tenant isolation at the storage layer, and the HAPI partitioning map

**Medplum's mechanism is a single predicate.** Every main table has a `projectId uuid` column written from `meta.project` (REPO-045), plus a `compartments uuid[]` column carrying `Project/<id>` and every patient/account compartment (REPO-050). Non-super-admin reads and searches append `WHERE projectId IN (<permitted ids>)` (`addProjectFilters`); super-admins skip it entirely. There is **no RLS, no schema-per-tenant, no table partitioning, and no database-level enforcement of any kind**. Writes are additionally pinned: `canPerformInteraction` requires `meta.project === projects[0].id` for anything that is not a read, so linked projects are read-only (REPO-046). The Redis resource cache (REPO-007) is keyed `"<Type>/<id>"` with **no tenant prefix**, so cache isolation depends entirely on the in-memory `meta.project` check after the read — and the stronger compartment check on that path is commented out pending a migration (REPO-006).

The **"global shard"** (REPO-043) is a *different* axis and must not be confused with tenancy. It is a forward-looking physical-database split, currently dormant (`getProjectSystemRepo` is a passthrough to the global shard). Ten types are pinned to it because they must be readable *before authentication resolves a project*: `Project`, `ProjectMembership`, `User`, `UserSecurityRequest`, `ClientApplication`, `JsonWebKey`, `Login`, `SmartHealthLink`, `SmartAppLaunch`, `DomainConfiguration`. Several of these still carry `meta.project` — the criterion is "readable before the shard is knowable", not "not project-scoped".

**Mapping onto HAPI partitioning.** One Keycloak organisation ↔ one Big Book `Project` ↔ one HAPI partition id (BIGBOOK.md, BB-R-005.1). Configure `PartitionSettings` with `setPartitioningEnabled(true)`, `setIncludePartitionInSearchHashes(true)` (so index hashes are partition-scoped — a genuine storage-level isolation Medplum does not have), and a custom `IRequestPartitionHelperSvc` / `@Interceptor` on `Pointcut.STORAGE_PARTITION_IDENTIFY_READ` and `STORAGE_PARTITION_IDENTIFY_CREATE` that resolves the partition from the token's `project`/org claim. `meta.project` is then a *projection of the partition id* on read, not a stored column (RES-M01).

**Which types must be non-partitioned (`DEFAULT_PARTITION` / partition `null`) in Big Book:**

- **Must be non-partitioned, read before auth:** `ClientApplication` (resolved by `client_id` during token exchange) and `DomainConfiguration` (resolved by email domain before any project is known). Both are read by id/domain with no project context.
- **Not stored in Big Book at all** — they belong to Keycloak, so the question is moot: `User` (BB-R-014.3 says "read-only projection of Keycloak"), `Login` (BB-R-004.8a non-goal), `JsonWebKey` (Keycloak's realm keys), `UserSecurityRequest` (Keycloak flows), `SmartAppLaunch`/`SmartHealthLink` (BB-R-022, v0.2).
- **Partitioned, despite being global in Medplum:** `Project` and `ProjectMembership`. Medplum keeps them global because a Project's shard is stored *in* the Project; Big Book has no sharding, so both can live in their own partition — **except** that `Project` must be listable cross-partition for the super-admin project switcher (`GET /admin/projects`, ADR-004). Simplest: put `Project` in the default partition and `ProjectMembership` in its project's partition (a membership is always read with a project in hand).
- **Terminology and conformance resources** (`CodeSystem`, `ValueSet`, `ConceptMap`, `StructureDefinition`, `SearchParameter`) are worth putting in the default partition with cross-partition read enabled, mirroring Medplum's synthetic R4 project (`repo.ts:278-284`) and profile-cache fallback across linked projects (REPO-009). HAPI supports this via `setDefaultPartitionId` + `PartitionSettings.setAllowUnqualifiedCrossPartitionReference` for conformance types.

Recommended shortlist for BB-R-005.1: **non-partitioned = `ClientApplication`, `DomainConfiguration`, `Project`, plus the conformance/terminology types.** Everything else partitioned.

##### (c) Version and history semantics

- **How many versions are kept:** all of them, forever (REPO-027). One `<Type>_History` row per persisted write, appended by `writeResourceVersion`. Nothing trims it.
- **Is history pruned:** no automatic pruning. Two manual paths, both privileged: `$expunge` (super-admin or project admin, hard-deletes resource + all history + lookup rows + Binary objects, ≤10 000 ids, serializable — REPO-029) and `purgeResources` (super-admin only, `DELETE … WHERE lastUpdated <= $before`, server-wide, not transactional — REPO-030).
- **What a deleted resource's history looks like:** the main-table row is **overwritten in place** with `content = ''`, `deleted = true`, `__version = -1` and empty search columns — the live row is destroyed, not preserved. A new history row is appended with a **minimal tombstone body**: `{resourceType, id, meta: {versionId, lastUpdated, author, deleted: true, project}}` — no clinical content at all. In the `_history` bundle that entry renders as `request.method: DELETE`, `response.status: "410"`, with an inline `gone` OperationOutcome whose `details.text` is `"Deleted on <lastUpdated>"` and **no `resource` element** (REPO-025; `medplum-parity.md` row c2). Prior versions remain fully readable by `vread`. `readHistory` and `readVersion` both deliberately swallow the `gone` outcome from the authorisation read, which is what makes a deleted resource's history readable at all. Re-reading the resource itself is **410** (REPO-021).
- **What `versionId` is:** a **fresh v4 UUID generated on every write** (`resultMeta.versionId = this.generateId()`, `repo.ts:1132`) — not a counter, not monotonic, carrying no ordering information. History is ordered by `lastUpdated DESC`, not by versionId. `readVersion` **requires both `id` and `vid` to be UUIDs** and 404s otherwise (`repo.ts:989-991`).
  **HAPI uses an integer** (`HFJ_RES_VER.RES_VER`, starting at 1 and incrementing). `medplum-parity.md` records this: *"Medplum `versionId` is a UUID; HAPI's is an integer. `If-Match` values therefore differ in shape but both are opaque to a well-behaved client."* That verdict holds for `@medplum/core` (see (d)) but has two concrete consequences for Big Book: (i) a Medplum → Big Book data migration cannot carry versionIds across, so `_history` URLs from an old deployment break; (ii) any Big Book code that re-implements Medplum's `isUUID(vid)` guard would reject HAPI's integers — do not port that check.

##### (d) What would break `@medplum/core` if Big Book differed

Ordered by blast radius. Cross-references Area 1's D3/D4, which already flag the token-body and `X-Medplum: extended` dependencies.

1. **`OperationOutcome.id` slugs, not HTTP status.** Already in `medplum-parity.md`: `isOk`, `isNotFound`, `isGone`, `isConflict`, `isPreconditionFailed` all switch on `OperationOutcome.id`. Area 2b adds the exact slugs this area produces: `gone` (delete re-read, REPO-021), `not-found` (unknown id and update-as-create for non-super-admins, REPO-004/005), `precondition-failed` (stale `If-Match`, REPO-014), `multiple-matches` (all four conditional interactions, REPO-022/023/024), `ok` (idempotent delete, REPO-020), `conflict` (final serialization-failure retry, REPO-039). HAPI emits none of these ids. This is the single biggest SDK-grade item (BB-R-014.6, v0.2).
2. **304 on an unchanged conditional update.** `client.ts:2415-2441` (`upsertResource`): `const wasModified = result !== undefined; if (!result) { result = resource; }` — a 304 yields an undefined body and the SDK **falls back to echoing the caller's input** and suppresses the `resourceModified` event. If Big Book always writes a new version (HAPI's default), `upsertResource` still works but fires a spurious modify event on every no-op upsert; if Big Book returns a 304 *with* a body, the SDK's `result !== undefined` check misreads it as modified. Either implement REPO-015's suppression or accept the event noise — but do not return a body with a 304.
3. **`X-Medplum: extended` → `meta.project` / `meta.author` / `meta.compartment` must be present.** Already Area 1 D4. Area 2b confirms the server side: `removeHiddenFields` blanks all six extended meta fields when `extendedMode` is false (REPO-017), and the SDK sends the header on every call. A Big Book response lacking `meta.project` under that header will not crash the SDK but breaks `@medplum/app`'s project-scoping UI and any code reading `resource.meta.project`.
4. **`versionId` shape is genuinely safe.** `client.ts` has **no** `If-Match`/`ETag` handling of its own (grep for `If-Match`/`etag` in `client.ts` returns nothing) — version-aware updates go through raw `medplum.put(url, resource, {headers})`. `readVersion(resourceType, id, vid)` passes `vid` through as an opaque path segment. So HAPI's integer versionIds do **not** break the SDK. The parity guide's assessment is confirmed by the code.
5. **`readHistory` bundle shape.** `client.ts:2217` returns the `Bundle` verbatim; consumers (the app's history tab) read `entry[].resource.meta.versionId` and `entry[].response.status`. A deleted entry must have `resource` **absent** and `response.status = "410"` — HAPI's history does include delete entries, but the exact entry shape (`request.method`, inline `outcome`) needs verifying against the pinned HAPI version (#8). `Bundle.total` is populated by a separate `COUNT(*)` in Medplum; HAPI populates it too.
6. **Non-UUID ids.** `client.ts` does not validate id shape, but `@medplum/app` routes assume them. BB-R-001.9 already pins UUID-only, which matches Medplum (REPO-005) and requires `resource_client_id_strategy=NOT_ALLOWED` plus `resource_server_id_strategy=UUID` in HAPI. Do **not** port Medplum's `isUUID(vid)` guard on `readVersion` (see (c)).
7. **`RateLimit: "fhirInteractions"` header (REPO-059).** `@medplum/core` does not require it — `setRateLimitReset` is server-side only. Safe to omit.

#### Contradictions with REQUIREMENTS.md / ADRs

Brick text quoted verbatim; code reality follows. **D** = needs a design call, **T** = text fix.

**1. (T) BB-R-002.1 — "`:not`, `:missing`, `:exact`, `:contains`"**
Accurate but incomplete, and it hides two things. (a) Medplum *parses* `:above`, `:below`, `:in`, `:not-in`, `:of-type` and then **throws 400 on all five** (`token-column.ts:240-259`). HAPI implements at least `:above`/`:below`/`:in`/`:not-in`, so wiring HAPI is a **net gain**, not parity — worth saying so, because the exit test should not assert Medplum's 400s. (b) Medplum adds two non-R4 operators of its own: `sw` (starts-with prefix on values, `core/search/search.ts:132`) and `:present` (`presence.ts:29-37`). Neither is in the brick. Recommend: add "plus `:above`/`:below`/`:in` gained from HAPI; Medplum's `sw`/`:present` extensions are non-goals."

**2. (D) BB-R-002.1 — "string/token/reference/date/quantity semantics"**
Two of those five are **incorrectly implemented in Medplum**, and wiring HAPI silently changes behaviour:
- *quantity*: Medplum parses `number|system|code` and then **discards system and code** (`search.ts:1491`), matching on the number alone. HAPI matches units. A Big Book search for `value-quantity=5.4|http://unitsofmeasure.org|mg` will return **fewer** results than Medplum did.
- *number*: `parseNumberToRange` carries a literal `// TODO: Implement precision range` (`range-column.ts:279`), so implicit precision matching (R4 §3.1.1.5.3) is absent.
Recommend: record both in `docs/guides/medplum-parity.md` as "Big Book is more correct than Medplum here" and do **not** write bug-compat glue.

**3. (D) BB-R-002.7 — "Paging: offset (`_offset`) and cursor (`next` links) — HAPI paging cache; document the difference from Medplum's cursor."**
The brick is right that there *is* a difference, but understates it in three ways.
- Medplum's cursor is **not opaque**: it is `2-<epochMillis>-<csv of excluded uuids>` (`search.ts:664-671`), even though `search/paginated-search.md` calls it "an opaque string value". Anything that parses it (there is nothing in `@medplum/core` that does — `searchResourcePages` follows `next` blindly, `client.ts:1937`) would break.
- Medplum's cursor paging **only engages under four simultaneous conditions** (`canUseCursorLinks:568-576`): `_offset` unset, `_count >= 20`, exactly one sort rule, and it is `_lastUpdated` ascending. Every other search gets offset links. So "cursor vs offset" is not a client choice; the server decides silently.
- HAPI's paging cache is a **different shape entirely** — `?_getpages=<search-uuid>&_getpagesoffset=N&_count=M`, with server-side state and a TTL. A Big Book `next` link will not contain `_cursor` at all.
Recommend: BB-R-002.7 should commit to *(i)* offset paging being byte-compatible, *(ii)* `next`/`previous`/`self` links existing with correct semantics, and *(iii)* the cursor token being explicitly declared **not** wire-compatible, with the four-condition rule and the token format both written into `medplum-parity.md`. Add an exit test that `searchResourcePages`-style blind `next`-following terminates.

**4. (D) BB-R-003.4 — "Introspection togglable per project (`graphql-introspection` feature); depth/search-count limits configurable."**
Both halves are wrong about the code.
- Introspection is gated by the **server-wide config key `introspectionEnabled`** (`graphql.ts:128`, `routes.ts:235`, `config/types.ts:79`). The `graphql-introspection` Project feature code is declared in the valueset, the TypeScript types and the docs but **read by no server code** — its only non-test occurrences are `packages/mock` and two test setups. It is a dead flag. Medplum's own docs contradict each other here (`graphql/index.md` says server config; `self-hosting/project-settings.md:36` says project feature).
- Depth and cost limits are **advisory**: in both `MaxDepthRule` (`graphql.ts:542-549`) and `QueryCostRule` (`:639-643`) the `context.reportError(...)` call is commented out and only `router.log('warn', …)` remains. `graphqlMaxDepth` therefore limits nothing.
- `graphqlMaxSearches` *is* enforced, but it is simultaneously (mis)used as the max `_count` (`utils.ts:152`, `graphql.ts:365`).
Recommend: reword BB-R-003.4 to "introspection togglable (server config in v0.1, per-project in v0.2); depth and query-cost limits **enforcing** (Medplum's are advisory — Big Book is stricter)". Note that enforcing depth is a DoS control, so this is a small-but-real glue item, not a copy.

**5. (T) BB-R-003.1 — "`POST /fhir/R4/$graphql` and `/fhir/R4/Type/id/$graphql`"**
Medplum registers **only** `POST $graphql` at system level (`router/fhirrouter.ts:334`). There is no instance-level `$graphql` and no `GET`. The brick describes the FHIR spec, not Medplum. HAPI's `GraphQLProvider` does register system/type/instance and GET — so Big Book would be a superset of Medplum here, which is fine, but the brick should not imply Medplum parity is the bar. **verify on pinned HAPI**.

**6. (T) BB-R-002.8 — "Full-text `_text`/`_content` — defer v0.2"**
`_text` and `_content` are **not implemented in Medplum at all** — no handler exists, and the params 400 as unknown. The brick defers a capability Medplum never had. Reword to "`_text`/`_content` — **new capability**, HAPI + OpenSearch (`HSearch`), `full` profile, v0.2". Also note Medplum's nearest analogue is the token `:text` modifier (SRCH-009), which is a regex over a text column and only indexes values for a 7-entry allowlist of telecom params.

**7. (T) BB-R-002.5 — "`_filter` — wire HAPI (`filter_search` enabled)."**
The fill is right; the risk is unstated. Medplum's `_filter` is unusually powerful because each comparison recurses into the **full** filter builder (`search.ts:1188-1195`), so dotted paths inside `_filter` become chained searches and `_filter` can nest. HAPI's `_filter` is a separate grammar with its own operator subset and (to be measured) no chaining. Meanwhile Medplum's *documented* `in`/`ni` ValueSet operators (`search/filter-search-parameter.md:62-63`) **throw 400** in the code. Recommend: BB-R-002.5 keeps `wire HAPI` but gains an explicit "measure which `_filter` operators and whether dotted paths work" exit item — **verify on pinned HAPI**.

**8. (T) BB-R-002.1 / BB-R-006.1 — custom SearchParameters**
Neither brick says how a search parameter comes into existence. In Medplum they are **static JSON bundles loaded at boot** (`fhir/structure.ts:11-34`), optionally filtered by a server allowlist `enabledSearchParameters`; a `SearchParameter` resource POSTed to the store is inert. HAPI supports runtime-registered custom `SearchParameter` resources with `$reindex`. This is a **capability Big Book gains for free** and should be stated, because it is one of the more attractive HAPI differentiators. **verify on pinned HAPI** that it is enabled by default.

**9. (T) BB-R-002.6 — "`_compartment=Project/<id>` — glue: maps to the tenant partition"**
Medplum has **two** parameters, not one: `_project` over `meta.project` (`search.ts:1095-1102`) and `_compartment` over `meta.compartment` (`:1103-1105`). Area-1 fix T14 already flags that both must be emitted; the search brick should name both. `_compartment` can additionally appear as a **chain link** (`search.ts:1686-1689`), which no brick mentions.

**10. (T) BB-R-002.3 — "`_include`, `_revinclude`, `:iterate`"**
Three gaps. (a) `_include=*` / `_revinclude=*` are **not supported** in Medplum (400 `Invalid include parameter: *:…`) but are supported in HAPI — another free gain. (b) `:iterate` is capped at depth 5 and 1000 total entries, and breaching either throws a plain `Error` → **500, not 400** (`router/search-include.ts:96-98`). (c) `_revinclude` sub-searches are hard-pinned to `_count=1000` with no override (`:259`), so wide reverse includes silently truncate. If Big Book's exit test uses a patient with many Observations it will see a behaviour difference.

**11. (T) BB-R-006.1 — "`criteria` (search string; `:not`/`:missing` only, no chaining)"**
The restriction is a *convention*, not enforced. `addAccessPolicyFilters` calls the **full** `buildSearchExpression` (`repo.ts:1911-1916`), so a criteria string containing a chain compiles to a chained SQL subquery and works. Separately, invalid criteria (not starting `Type?`) cause the code to `return` out of the whole policy loop (`repo.ts:1893`) — **fail-open**, dropping all remaining restrictions. Big Book must fail closed. (Owned by Area 1 / ADR-001; recorded here because it is visible in the search path.)

##### (b) The paging model, precisely

**What a Medplum `next` link looks like.** Built at `search.ts:708-710` as `${baseUrl}fhir/R4/${resourceType}${formatSearchQuery(req)}`, where `formatSearchQuery` (`core/search/search.ts:508-559`) **re-serialises the parsed request** rather than echoing the client's query string. Concretely:

- Params are emitted in a fixed order (`_fields`, filters, `_sort`, `_cursor`, `_offset`, `_count`, `_total`, `_type`, `_include`, `_revinclude`) and then **sorted alphabetically** (`sortStringArray`, `:557`).
- `_elements` is rewritten to `_fields`.
- **`_summary`, `_format` and `_pretty` are dropped entirely** — they have no emit branch. A `GET /Patient?_summary=true&_count=50` returns a `next` link with no `_summary`, so page 2 comes back with full resources. This is a live Medplum bug; Big Book should echo the caller's params instead.
- `_offset` is omitted when 0.

Offset link example: `https://api.example.com/fhir/R4/Observation?_count=20&_offset=20&subject=Patient%2Fabc`.
Cursor link example: `…/Patient?_count=50&_cursor=2-1757635200000-3f2a…%2C9c11…&_sort=_lastUpdated`.

**Which links appear** (`search.ts:525-556`): `self` always; `first` + (`next` if a `count+1`-th row existed) + (`previous` if `offset>0`) only when `_count>0` and the page is non-empty. **`last` is never emitted.** `next` is present iff a further row exists, so there is no trailing empty page.

**Are cursors opaque?** The docs say yes (`search/paginated-search.md`: "an opaque string value"). The code says no: `formatCursor` (`:664-671`) produces `<version>-<epochMillis>[-<csv uuids>]`, and `parseCursor` (`:617-627`) reads v1 and v2. Nothing in `@medplum/core` parses it — `searchResourcePages` follows `next` verbatim (`client.ts:1937,1943`) — so treating it as opaque is safe for clients, and Big Book is free to use a different token.

**When cursors are used at all.** `canUseCursorLinks` (`:568-576`) requires **all four**: `_offset === 0`, `_count >= 20`, exactly one sort rule, and it is `_lastUpdated` **ascending**. Everything else gets offset links. Failure mode: if the boundary timestamp cannot advance, the server throws a **500** `Cursor fails to make progress` (`:542`).

**What BB-R-002.7 must document as the HAPI difference.** HAPI stores a server-side search result set and pages it with `?_getpages=<search-uuid>&_getpagesoffset=N&_count=M`, with a cache TTL and an optional total. So: (1) the `next` URL shape differs completely and contains no `_cursor`; (2) HAPI's page token expires, Medplum's never does (it is a timestamp); (3) HAPI may emit `last` and a `_total` where Medplum does not; (4) Medplum's four-condition cursor activation has no analogue — HAPI pages everything the same way. The contract Big Book should promise is **behavioural, not lexical**: `self`/`next`/`previous` exist, blindly following `next` terminates and visits every match exactly once, and `_offset` works up to the documented cap. Exit test: run `searchResourcePages`-equivalent over 2 500 resources with `_count=100` and assert 2 500 distinct ids and termination.

##### (c) GraphQL — which of BB-R-003's items 1-5 HAPI's provider covers

| BB-R-003 item | Medplum reality | HAPI expectation |
|---|---|---|
| **1.** `$graphql` at system + instance, nested refs, list filtering, `_reference` | Medplum has **system-level POST only** (`fhirrouter.ts:334`) — no instance, no GET. Nested refs via `Reference.resource` + `ResourceList` union (GQL-004); list filtering via `_count`/`_offset`/`fhirpath`/property args (GQL-019); `_reference` with generated enums (GQL-007). | HAPI `GraphQLProvider` registers system/type/instance and GET, and implements spec `_reference`. Likely a **superset**. **verify on pinned HAPI**: exact paths, the `[x]` field naming, the `_reference` enum type name, and whether `fhirpath` list args exist. |
| **2.** Connection-style queries | Medplum-implemented (GQL-008) with `count/offset/pageSize/edges{mode,score,resource}`; `first`/`previous`/`last` declared but **never populated**; `next` is a bare `_cursor`. | The Connection API **is** in the FHIR GraphQL spec, so HAPI may well have it. **verify on pinned HAPI** — this is the single highest-value measurement, because a yes flips BB-R-003.2 from `defer v0.2` to `wire HAPI`. |
| **3.** Mutations `<Type>Create/Update` | Medplum-implemented, plus `Delete` and an undocumented `Patch` (GQL-009, GQL-010). | **Most uncertain item.** HAPI's GraphQL support has historically been query-oriented; mutations may be absent. **verify on pinned HAPI**. If absent, BB-R-003.3's own rule applies — **defer v0.2, not glue**. Writing a mutation layer by hand would blow the 5-10k budget for little gain (REST covers writes). |
| **4.** Introspection toggle + depth/search limits | Introspection gated by **server config**, not a project feature; `graphql-introspection` is a dead flag. Depth and cost limits are **advisory only** (commented-out `reportError`). Only `graphqlMaxSearches` enforces, and it doubles as a `_count` cap. | HAPI almost certainly has **no** depth or cost guard. This is the one place Big Book should be *stricter* than both: enforce depth (~40 lines of a `ValidationRule` equivalent) and a per-request search counter. Introspection toggle is one config key. |
| **5.** Access policies at field level, same path as REST | **Fully satisfied in Medplum** — GraphQL has no policy code of its own; every resolver goes through `ctx.repo`, so narrowing, criteria subqueries and `hiddenFields` apply identically (GQL-011). | **Security-critical verification.** If HAPI's `GraphQLProvider` resolves through the DAO layer, `AuthorizationInterceptor`/`SearchNarrowingInterceptor` apply and item 5 is free. If it bypasses them, this is a **blocking gap**, not a nice-to-have, and GraphQL must be disabled in `lite` until closed. **verify on pinned HAPI first, before anything else in BB-R-003.** |

**Medplum-only regardless of HAPI:** `_cursor` as a GraphQL arg, `<Type>Patch`, the batched-search dataloader, the `graphqlMaxSearches`-as-`_count` conflation (a bug — do not port).

##### (d) What `@medplum/core` / `@medplum/app` need that a plain HAPI search would not return

1. **`Bundle.link[relation='next'].url` must be an absolute, directly-fetchable URL.** `searchResourcePages` does `new URL(nextLink.url)` and re-requests it verbatim (`client.ts:1937,1943`), and stops only when there is no `next` **and** no entries (`:1938-1940`). So: `next` must be absolute (HAPI's `server_address` config must be right behind a proxy), must not appear on the last page (or paging never terminates cleanly), and must carry authentication implicitly — the SDK re-attaches its own bearer, so a `next` URL with an embedded one-shot token would still work but a `next` on a *different host* would break.

2. **`Bundle.total` semantics drive the app's pager, and its absence is silently papered over.** `SearchControl` requests `total` defaulting to **`'accurate'`** (`packages/react/src/SearchControl/SearchControl.tsx:158`) and renders `~` before the number when the request asked for `estimate` (`:382-383`) — note it keys the tilde off *what was requested*, not off what the server returned, so a HAPI server that downgrades `accurate` to an estimate will display a precise-looking wrong number. When `total` is absent, `getTotal` (`:637-647`) fabricates one as `offset + entry.length + (has next ? 1 : 0)`, which makes the page count wrong but not broken. Requirement: HAPI must honour `_total=accurate` for the page sizes the app uses.

3. **`Bundle.entry[].search.mode` is produced but NOT consumed by the SDK — and that is the trap.** The server sets `mode:'match'` on matches (`search.ts:377`) and `mode:'include'` on includes (`router/search-include.ts:270`). But `bundleToResourceArray` (`client.ts:4942-4944`) does `bundle.entry?.map(e => e.resource)` with **no mode filter**. So `medplum.searchResources('Observation', '_include=Observation:subject')` returns an array containing the Patients as well, and callers rely on that happening to be positionally consistent — matches first, includes appended (`search.ts:375-383`). Big Book must preserve **both** the mode values and the match-before-include ordering, or SDK consumers get silently reordered arrays.

4. **`Bundle.entry[].fullUrl` on every entry**, match and include alike (`search.ts:376`, `search-include.ts:267`). Standard, but HAPI's `server_address` must be configured or `fullUrl` comes out wrong.

5. **`X-Medplum: extended` implies `meta.project`, `meta.author`, `meta.compartment` on every returned resource** — already captured as Area-1 D4/T14, restated here because it applies to *search* entries too, and because the SDK's client-side compartment check fails without `meta.compartment` carrying `Project/<id>`.

6. **`meta.versionId` and `meta.lastUpdated` on search entries** — `_lastUpdated` sorting, cursor construction and the app's "last modified" column all depend on `lastUpdated` being present and ISO-8601 in every search result.

##### Prioritised list: search features most likely to need glue

1. **Access-policy narrowing must reach `_include`/`_revinclude` sub-queries and GraphQL resolvers.** Medplum gets this right by construction (`search.ts:497-514`, GQL-011). On HAPI it depends on whether `SearchNarrowingInterceptor` fires for include sub-queries and whether `GraphQLProvider` goes through the DAO layer. A miss here is a **cross-tenant data leak**, not a feature gap. Measure first, before any other BB-R-002/003 work.
2. **`_compartment` / `_project` → partition mapping** (SRCH-051, SRCH-052), including `_compartment` as a chain link and emitting `meta.compartment` in extended mode. Owned by BB-R-005 but observable through search.
3. **Paging contract and link construction** (SRCH-046, SRCH-047, SRCH-048). Accept HAPI's token shape, but **echo the caller's query params in `self`/`next`** rather than re-serialising, so `_summary`/`_elements` survive paging — fixing Medplum's bug rather than porting it. Plus the `_fields`↔`_elements` alias.
4. **`_filter` operator coverage** (SRCH-061). Highest-variance unknown after item 1. If HAPI's `_filter` lacks dotted paths or the `co`/`sw`/`pr` operators, this becomes a real glue item or a v0.2 deferral, and BB-R-002.5's `wire HAPI` fill is wrong.
5. **The in-memory matcher** (SRCH-060 … SRCH-060e) — **promote this; it is closer to a correctness bug than a feature gap.** It backs `Subscription.criteria` (BB-R-007.1) *and* `AccessPolicy.criteria` write-side checks (BB-R-006.1), and Medplum's version silently gives the wrong answer in five distinct ways: unknown/chained/`_has`/`_filter` codes return `false`; `number`/`quantity` params return `false`; strings are case-insensitive *substring* where SQL is prefix, with `:exact` ignored; `:not-in`/`:in`/`:above`/`:below`/`:text`/`:of-type` degrade to plain equality (so `:not-in` means its own inverse); and dates are lexicographic string compares with no `ap` tolerance. In an `AccessPolicy` a silently-inverted `:not-in` is a **policy bypass**; in a `Subscription` a chained criterion means "never fires". Big Book's rule should be **validate criteria at write time and reject anything the matcher cannot evaluate**, rather than inheriting silent `false`. HAPI's `InMemoryResourceMatcher` has its own gap list — measure it and enforce the intersection.
6. **GraphQL depth and cost enforcement** (GQL-014, GQL-015). Medplum's are advisory; HAPI likely has none. Small (~40-60 lines) but it is the only DoS control on `$graphql`.
7. **`graphqlMaxSearches` as a real per-request search counter** (GQL-013), without Medplum's `_count` conflation.
8. **`_fields`, `:present`, `sw`, `_deleted`** — small accept-and-translate shims, or explicit non-goals. Decide once and record in `medplum-parity.md`.

> Part of the Medplum capability inventory — see [README.md](README.md) for conventions, the disposition of every D/T/V item, and the freeze. Snapshot `medplum/medplum` `main` @ `fbc8e7b4b`. **Frozen; do not edit.** Status: reconciled 2026-09-17 into REQUIREMENTS.md and the ADRs.

## Area 3 — decisions needed

Same convention. **D** = design call, **T** = text fix, **V** = verify on pinned HAPI. Evidence in sections 3.1–3.2 below.

Headline: of the 85 operations Medplum implements, **only 8 have any caller** in `@medplum/core`, `@medplum/app`, `@medplum/react` or `examples/`. HAPI supplies a strictly larger set of *standard* operations than Medplum does, from one dependency. The Big Book work in this area is therefore not implementing operations — it is suppressing the HAPI ones that leak across partitions, the ~200 lines of async-job shape if SDK-grade compat is wanted, and the terminology *content* loading story, which is an install-docs problem.

#### Contradictions with REQUIREMENTS.md / ADRs

**1. BB-R-001.5 — `$validate` is narrower than the brick implies.**
> BB-R-001.5: "`$validate` against base R4 and any loaded profile; `meta.profile` honoured; `Project.defaultProfile` (see BB-R-005) auto-applied when absent."

Code reality (OP-027): Medplum registers **only** `POST /fhir/R4/:resourceType/$validate` — there is no instance-level `Type/:id/$validate`, no `Bundle/$validate`, and the standard `mode` and `profile` input parameters are **not accepted**. The body is the bare resource, not a `Parameters` with a `resource` part, and `MedplumClient.validateResource` posts it that way. HAPI implements the full standard (type + instance, `mode`, `profile`, `Parameters` or bare body). *Recommendation:* leave HAPI's superset on; add one line to BB-R-001.5 saying the bare-resource body form must be accepted for SDK-grade compat (v0.2), and record in `medplum-parity.md` that Big Book additionally supports instance-level `$validate` and the `profile` parameter. No design change.

**2. BB-R-001.8 — `$match` non-goal is correct, but the reason in the brick is wrong.**
> BB-R-001.8: "Patient `$match` / dedup pipeline — **non-goal** (workflow guide, not platform)."

Code reality (OP-016): `Patient/$match` **is** a first-class server operation in Medplum, not a workflow guide — it is a standard R4 operation with a real implementation (the CMS 11-factor match algorithm, `utils/cms-patient-match.ts`, ~370 lines plus a 130-line handler), it writes `AuditEvent`s on the `onlyCertainMatches` path, and the Medplum Provider app calls it (`SmartHealthLinkImport.tsx:210`). Medplum's *dedup pipeline* is the workflow guide; `$match` is not. The **decision** (non-goal) is still right for Big Book — HAPI has no `$match` in core (MDM is a separate module with its own EMPI storage) — but the parenthetical reason should be corrected to "no HAPI core support; MDM module out of scope" so a future reader does not conclude it is cheap.

**3. BB-R-020 — `$export` is listed as pure `wire HAPI`; three sub-behaviours are glue.**
> BB-R-020: "Bulk export `$export` | wire HAPI | `api/fhir/operations`"

Code reality (OP-021/022/023 + OP-004/005 + area 2 FR-010…FR-013): the operation itself wires cleanly, but the *async contract around it* does not. Medplum returns `Content-Location: <base>/fhir/R4/bulkdata/export/<id>` and serves a Bulk Data manifest there with a hardcoded `requiresAccessToken: false`; HAPI returns `$export-poll-status` with a different body. `MedplumClient.bulkExport` → `startAsyncRequest` → `pollStatus` follows whatever `Content-Location` it is given, but D4 already records that the SDK expects an `AsyncJob` body at that URL. So: (a) the poll URL and manifest shape, (b) the `AsyncJob` resource type, and (c) `$cancel` (OP-030) are **glue**, not wire. Also note Medplum's `$export` ignores `_outputFormat`, `_elements` and `_typeFilter` while HAPI supports them — a superset, safe to leave on. *Recommendation:* re-word BB-R-020 as "wire HAPI bulk export + glue for the Medplum poll/manifest URL shape and the `AsyncJob` resource (v0.2)", and add an exit test that `MedplumClient.bulkExport()` completes end-to-end.

**4. The v0.3 terminology line understates what is already needed and overstates Snowstorm's role.**
> v0.3 placeholders: "terminology with Snowstorm (`terminology/`)"; BIGBOOK.md stack table: "Terminology | HAPI terminology + Snowstorm | Snowstorm `full` only".

Code reality (OP-006…OP-013): Medplum implements **eight** terminology operations, and one of them — `ValueSet/$expand` — is the single most-used operation in the entire product: it is the only terminology op with a `MedplumClient` method (`valueSetExpand`), it backs every coded input in `@medplum/react` (`ValueSetAutocomplete`, `QuestionnaireFormItem`, `Spotlight`), and the Provider example mocks it in a dozen tests. `CodeSystem/$lookup` is used by the app's `ValueSetPreview`. The other six have **no** caller anywhere in the repo. Meanwhile Snowstorm is a **SNOMED CT** server: it does not serve LOINC, RxNorm, ICD-10 or the `http://terminology.hl7.org` CodeSystems that the base R4 ValueSets reference — HAPI's own JPA terminology tables do. So "terminology = Snowstorm, v0.3" mis-assigns the work. *Recommendation (design call):* split the line — **v0.2: `wire HAPI` terminology for `$expand`, `$lookup`, `$validate-code` (both), `$subsumes`, `$translate` over locally-loaded CodeSystems/ValueSets** (this is free once HAPI JPA is embedded, it is just configuration plus a terminology upload step in the install docs), and **v0.3: Snowstorm for SNOMED CT specifically**, wired as an external terminology service in the `full` profile. As written, a Big Book v0.1 has base-R4 ValueSets in its HAPI tables and `$expand` working, and the brick says it does not.

**5. BB-R-014.6 status alignment — two more operation-specific status mismatches to add.**
`findTerminologyResource` returns **400** (not 404) for an unknown ValueSet/CodeSystem/ConceptMap url (`utils/terminology.ts:67`), and `$expand-profile` returns **400** for a profile that does not exist. HAPI returns 404 in both cases. Minor, but it belongs on BB-R-014.6's v0.2 slug-rewrite list if terminology reaches SDK-grade.

**6. No brick owns `Patient/$everything`.**
It is the second-most-used operation in the product (SDK method, React component, demo bot), HAPI implements it natively, and it costs nothing to enable — yet it appears in no brick. *Recommendation:* add it to BB-R-001 as sub-item `.10`, v0.2, `wire HAPI`, with the Medplum extensions (`_inlineAttachments`, care-date windowing, cross-compartment reference chasing) declared non-goals.

##### (b) The custom operation mechanism (`custom.ts`) — and whether to reproduce it

**How a project defines one** (OP-039, three resources, no server change, no restart):
1. Deploy a `Bot` with the implementation.
2. Create an `OperationDefinition` in the project with `code: "my-operation"` and the input/output `parameter[]` you want enforced.
3. Link them with the extension `https://medplum.com/fhir/StructureDefinition/operationDefinition-implementation` → `valueReference: {reference: "Bot/<id>"}`.

Then `POST /fhir/R4/Patient/$my-operation`, `GET /fhir/R4/Patient/123/$my-operation` and `POST /fhir/R4/$my-operation` all reach the Bot.

**What it can do.** Anything a Bot can do — arbitrary JS, outbound HTTP, FHIR reads/writes under its own membership. It gets the request body (or, for an instance-scoped definition, the target resource pre-read), the content type, all headers and the trace id. It can return a `Parameters` verbatim, an `OperationOutcome`, or a plain object that `buildOutputParameters` shapes and *validates* against the declared out-params.

**Its security model is the interesting part, and it is good:** the Bot is read through the **caller's** repo before it is executed. A caller with no read access to the Bot resource gets a plain 404 — the operation simply does not exist for them. So visibility of a custom operation is governed by ordinary `AccessPolicy` rules on `Bot`, with no new concept. That is worth stealing regardless of what else is decided.

**Its weaknesses**, which matter for a port: the lookup is `searchOne` on `code` with **no check that the URL shape matches the definition's `system`/`type`/`instance` flags**, and no check that the definition's `resource[]` includes the type in the path — so `POST /Observation/$my-patient-op` invokes a Patient-scoped operation. Two OperationDefinitions with the same `code` in one project resolve non-deterministically. And because it only runs **after** the built-in router returns not-found, a project cannot override a built-in operation (arguably a feature).

**Recommendation for Big Book: do not reproduce it as-is; fold the capability into BB-R-016 with a different spelling.** Reasons:

1. **It competes with BB-R-016 for the same job, and BB-R-016's spelling is better for Java.** In Camel, "expose a route at a URL" is one line of DSL. Requiring a developer to also hand-author an `OperationDefinition` resource and a Medplum-specific extension, and to deploy a Bot, in order to get a `$my-op` endpoint, is strictly more ceremony than `@Bot(path = "Patient/$my-op")` on a Camel route — and the Java developer already has a build step, which is exactly what the `OperationDefinition`-as-data design exists to avoid for JS users.
2. **The runtime lookup is a per-request search on the miss path.** Every 404 under `/fhir/R4` would pay an `OperationDefinition` search. HAPI's `@Operation` registration is a startup-time concern.
3. **It is not a compat surface.** Nothing in `@medplum/core`, `@medplum/app`, `@medplum/react` or `examples/` depends on the mechanism; the SDK just posts to a URL. So neither SDK-grade (v0.2) nor app-grade (v1.0) compat requires it. A Big Book bot exposed at the same path is wire-identical from the client's side.

**Do reproduce three things from it**, as part of BB-R-016:
- **AccessPolicy-governed visibility** — resolve the bot/route through the caller's authorisation so an unauthorised caller gets 404, not 403.
- **Declared-parameter validation on the way out** — reject a bot return value that does not match its declared output shape, as a 500, rather than shipping a malformed `Parameters`. This is what keeps custom operations honest.
- **The instance-scope convenience** — for a route bound to `/Type/:id/$op`, pre-read the resource and hand it to the bot.

**Open question for Tanvir (design call):** if a low-code path to custom operations is later wanted for the n8n/ops audience (BB-R-008), the right shape is an `OperationDefinition` → **Subscription rest-hook** binding, not a Bot reference — that keeps it inside the already-decided n8n story instead of inventing a second extension mechanism.

##### (c) Terminology — what Medplum implements, what HAPI gives, and the Snowstorm plan

**Medplum implements eight operations**, all against its **own** derived SQL tables (`Coding`, `Coding_Property`, `CodeSystem_Property`, `ConceptMapping`), not against the FHIR resource JSON:

| Operation | Levels | Standard? | Has a caller in the repo? |
|---|---|---|---|
| `ValueSet/$expand` | type | yes (R4) | **yes** — `MedplumClient.valueSetExpand`, 3 React components, bots, many example tests |
| `CodeSystem/$lookup` | type + instance | yes | **yes** — `app/resource/ValueSetPreview.tsx` (hand-built URL) |
| `CodeSystem/$validate-code` | type + instance | yes | no |
| `ValueSet/$validate-code` | type + instance | yes | no |
| `CodeSystem/$subsumes` | type + instance | yes | no |
| `ConceptMap/$translate` | type + instance | yes (R5-flavoured params) | no |
| `CodeSystem/$import` | type + instance | **no** — Medplum-proprietary | no (README prose only) |
| `ConceptMap/$import` | type + instance | **no** — Medplum-proprietary | no |

Notably **absent** from Medplum: `ValueSet/$expand` at *instance* level, `CodeSystem/$find-matches`, `ConceptMap/$closure`, and `$upload-external-code-system`.

**What HAPI's built-in terminology server gives for free.** HAPI JPA's `TermReadSvc` + `ValueSetOperationProvider`/`CodeSystemOperationProvider` implement `$expand` (type **and** instance, with `filter`, `offset`, `count`, `displayLanguage`, `includeDesignations`, pre-expansion), `$validate-code` on both ValueSet and CodeSystem, `$lookup`, `$subsumes`, and `ConceptMap/$translate` — a **superset** of Medplum's standard operations, over the base R4 CodeSystems that ship with HAPI. It additionally has `$closure` and `$find-matches`. Loading terminology is a *different* wire shape: `ITermLoaderSvc` / `POST CodeSystem/$upload-external-code-system` / the `hapi-fhir-cli upload-terminology` tool, which understand the native distribution formats for SNOMED CT, LOINC, ICD-10 and IMGTHLA — where Medplum's `CodeSystem/$import` takes a hand-built `Parameters` of up to 1000 codings. HAPI's is better; it just is not wire-compatible.

**Therefore, on the v0.3 Snowstorm plan.** Snowstorm is a **SNOMED CT terminology server**. It does not serve LOINC, RxNorm, ICD-10, CPT, or the `http://terminology.hl7.org/CodeSystem/*` systems that the base R4 ValueSets bind to. HAPI does. So the current framing — "terminology = v0.3 = Snowstorm" — leaves v0.1 and v0.2 with no terminology at all, which is wrong: HAPI JPA embedded gives Big Book working `$expand`/`$lookup`/`$validate-code` on day one, for free. The three-line restatement should be:

- **v0.1:** base R4 CodeSystems/ValueSets are in the HAPI tables; `$expand` works. Ship it and say so. *(Zero cost — it is already true the moment ADR-006's embedded HAPI boots.)*
- **v0.2:** document the terminology **content** loading path (`hapi-fhir-cli upload-terminology` or `$upload-external-code-system` for LOINC/ICD-10/RxNorm) in the install guide, and turn on `$lookup`/`$validate-code`/`$subsumes`/`$translate`. Still zero code. This is a docs deliverable under BB-R-011, not a brick of its own.
- **v0.3:** Snowstorm in the `full` profile **for SNOMED CT only**, wired as a HAPI external/remote terminology service so `$expand` of a SNOMED ECL-backed ValueSet delegates to it. This is the only part that needs a new container and new configuration.

Also: **do not** port `CodeSystem/$import` or `ConceptMap/$import`. They are Medplum-proprietary, nothing calls them in the repo, and HAPI's loaders are strictly better. Declare them non-goals and point the install docs at `upload-terminology`.

##### (d) How operations declare themselves, and whether clients discover them

**They essentially do not declare themselves.** `CapabilityStatement.rest.resource[].operation` is populated from a hand-written map (`fhir/metadata.ts:150-156`) that contains **exactly one entry**: `Group/$export`. Of the 40 rows in this area, **39 are invisible in `/metadata`**. There is no `rest[0].operation` array at all, so no system-level operation (`$export`, `$rebuild-base-definitions`, `$validate-smart-health-card`, the `$db-*` family) is advertised anywhere. Project-defined custom operations (OP-039) never appear, and could not — the statement is built once per process and cached (`metadata.ts:192-195`).

The `OperationDefinition` **resources** do exist and are searchable at `/fhir/R4/OperationDefinition` (seeded into the shared `r4ProjectId` by OP-029, plus whatever a project creates for custom ops). But nothing links them to the CapabilityStatement, and for the ~15 operations built with `makeOperationDefinition` at module scope (`$set-accounts`, `$rotate-secret`, `$rate-limits`, `$presigned-url`, `$rescope`, `$update-email`, `$cancel` ×2, `$init`, `CodeSystem/$import`, `ConceptMap/$import`, `$summary`) the definition is a **JS constant that is never persisted at all** — it exists only to drive `parseInputParameters`/`buildOutputParameters`.

**Do `@medplum/core` / `@medplum/app` discover them? No — every path is hard-coded.** There is no `/metadata` read anywhere in `packages/core`, `packages/app` or `packages/react` (area 2's FR-002 records the same finding). Every call is a literal built with `fhirUrl(…, '$op')`:
- `core/client.ts`: `valueSetExpand` → `fhirUrl('ValueSet','$expand')` (:1956); `readPatientEverything` → `fhirUrl('Patient', id, '$everything')` (:2279); `readPatientSummary` → `'$summary'` (:2302); `validateResource` → `fhirUrl(type,'$validate')` (:2913); `readResourceGraph` → a template string `${fhirUrl(type,id)}/$graph?graph=${name}` (:3113); `bulkExport` → `fhirUrl(\`${level}/$export\`)` (:3549); `requestProfileSchema` → `fhirUrl('StructureDefinition','$expand-profile')` (:2171).
- `packages/app`: `$csv` (HomePage:66), `$rate-limits` (RateLimitsPage:132), `$rescope` (RescopeUserWidget:84), `$update-email` (UpdateEmailPage:53), `$lookup` (ValueSetPreview:132), `$apply` (PlanDefinitionApplyForm:41), `$resend` (ResendSubscriptionsModal:31) — all string-built.
- `packages/react`: `$set-accounts` (PatientAccountsForm:112), `$everything`/`$summary`/`$ccda-export` (PatientExportForm:34-45).

**Three consequences for the Java port:**
1. **The CapabilityStatement is free.** HAPI's `ServerCapabilityStatementProvider` auto-advertises every `@Operation`-annotated method — a strict superset of Medplum's one entry. No client compares the two, so there is no compat work here. (Area 2's FR-002 already flags the three fields — `updateCreate:false`, `format:['json']`, `conditionalDelete:'single'` — that *do* need forcing; operations are not among them.)
2. **Path compatibility is the whole contract.** Since every client hard-codes the path, "supporting operation X" means exactly "answer at `/fhir/R4/<that path>` with the right body shape". Get the eight paths that actually have callers right (`$expand`, `$everything`, `$summary`, `$validate`, `$graph`, `$export`, `$expand-profile`, `$csv`) and the rest is invisible.
3. **HAPI advertising *more* than Medplum is harmless — but audit the list once.** Turning on the embedded HAPI providers will advertise `$meta-add`, `$meta-delete`, `$reindex`, `$expunge`, `$closure`, `$apply-codesystem-delta-*`, type-level `$history` and more. None of it breaks a client, but several are admin surface that must be behind the `AuthorizationInterceptor` rules from ADR-001, not merely undocumented. **Add a v0.1 exit check: `GET /fhir/R4/metadata` on a fresh `lite` stack, and confirm every advertised operation is either intended or denied by the default policy.** That is the one concrete action item this area produces for v0.1.

###### 1. Contradictions with REQUIREMENTS.md / ADRs

**(a) BB-R-007.8 "WebSocket subscriptions — **defer v0.2**" understates the surface.**
The brick line is a single deferral. In code, WebSocket subscriptions are four moving parts, only one of which HAPI plausibly supplies: (i) a project **feature flag** `websocket-subscriptions` (`getwsbindingtoken.ts:146`) that gates the whole thing; (ii) the `$get-ws-binding-token` operation (OPX-017), which is Big Book **glue** because it mints a bespoke JWT carrying `subscription_id` + `membership_id` extra claims (`getwsbindingtoken.ts:183-199`) — the token is minted by Medplum's own key material, not by an IdP, so on Big Book it must come from the Big Book server, not Keycloak; (iii) the `ws/subscriptions-r4` endpoint with the `bind-with-token` / `unbind-from-token` / handshake protocol (`ws/subscriptions.ts:48,352,530-541,606`); (iv) shared Redis state (`medplum:subscriptions:r4:project:*:active:*`, per-user active sets) that three super-admin operations exist purely to inspect and repair (OPX-018/019/020). BB-R-025 ("Subscription extras (WebSocket, …) — wire/glue") is the right home but currently says nothing about the binding-token mint being glue. **Recommend:** amend BB-R-007.8 to name `$get-ws-binding-token` as glue and the `websocket-subscriptions` project feature as a settings row, and note that Medplum's Redis-backed subscription registry (and its three ops endpoints) is explicitly *not* being ported.

**(b) BB-R-016 "Bot SDK (Camel, `@Bot` on a route; triggers: subscription, cron, `$execute`; deploy via CLI)" names three triggers. The code has seven.**
Missing from the brick: the **anonymous public webhook** `POST /webhook/:membershipId` gated on `Bot.publicWebhook` (OPX-005), **CDS Hooks** `POST /cds-services/:botId` (OPX-006), **user-defined custom FHIR operations** backed by a Bot via the `operationDefinition-implementation` extension (OPX-007), and **pre-commit hooks** that run inside the write transaction and can veto or rewrite a resource (OPX-003). OPX-007 is load-bearing beyond bots: `Claim/$submit` and `CoverageEligibilityRequest/$submit` are nothing but dispatchers into it (`utils/submit.ts:36-42`). Also missing: `$deploy` (OPX-008) presumes uploaded JavaScript, and `$init` (OPX-009) presumes the server creates the bot resource *and* its `ProjectMembership` — neither maps onto "one annotated class on a Camel route", where deployment is a JVM redeploy. **Recommend:** BB-R-016 lists the trigger set explicitly and states which of the seven v0.2 covers; and that Big Book's `$deploy`/`$init` equivalents are CLI/registration operations, not code upload.

**(c) The v0.3 line "HL7v2 agent (`agent/`, `integration/hl7-interfacing`)" has no brick ID, and the operations it implies are seven, not one.**
Area 1 flagged this as T15/BB-R-028; it is still a `GAP` in REQUIREMENTS.md. Concretely, OPX-010 through OPX-016 plus a websocket control channel (`ws/agent.ts`), a Redis pub/sub channel per agent, and a cache-Redis liveness key. Two of them (`$stats` OPX-015, `$fetch-logs` OPX-016) are observability that BB-R-015's OTel path should absorb rather than reimplement as FHIR operations, and one (`$upgrade` OPX-014) is a software-distribution channel that is a packaging decision (BB-R-011), not a FHIR one. **Recommend:** open BB-R-028 with sub-items so the v0.3 scope is explicit, and record the OTel/packaging displacement rather than implying a 1:1 port.

**(d) The non-goals list is broadly correct and the code confirms it — with two caveats.**
"DICOM, FHIRcast, CDS Hooks, C-CDA, ePA, Analytics/Athena, AI features" and "US integrations (… Stedi, Candid …)" and "clinical workflow features (… scheduling …)" cover OPX-006, OPX-030–OPX-037, OPX-043, OPX-044 cleanly. Two gaps: **SMART Health Cards / Links** (OPX-038–OPX-041) are a distinct verifiable-credential family that no non-goal names — they are not "AI", not "US billing", not DICOM. **Recommend:** add "SMART Health Cards / Links" to the non-goals list explicitly. Second, `$ai` is listed as a non-goal feature, but note it is also a *project secret + feature-flag* consumer (`OPENAI_API_KEY`, `LLM_BASE_URL`, feature `ai`) — area 4 should still inventory those keys even though the operation is a non-goal.

**(e) BB-R-011 / BB-R-015 vs. the nine DB operations (OPX-021–OPX-029).**
No brick claims them, and none should: they are Postgres catalog introspection and DDL executed over the FHIR API, tied to Medplum's own schema and index layout. Two are genuinely dangerous as a pattern — `$db-configure-indexes` (OPX-023) and `$db-configure-column-statistics` (OPX-028) run `ALTER` statements from an HTTP body — and `$db-schema-diff` (OPX-026) only makes sense for a server that generates its own migrations, which ADR-006 explicitly hands to HAPI. **Recommend:** REQUIREMENTS.md states once, under BB-R-011 or a non-goals bullet, that Medplum's `$db-*` and `$explain` super-admin operations are not ported and that database operations happen through Postgres tooling and the Grafana stack.

**(f) `Bot.runAsUser` interacts with BB-R-006 in a way no brick captures.**
When `Bot.runAsUser` is true, the bot executes with the **caller's** `ProjectMembership` and therefore the caller's `AccessPolicy` (`bots/utils.ts:52-63`), and the caller's HTTP `Cookie` header is forwarded into the bot's client (`bots/utils.ts:73-81`). On a subscription trigger it resolves to the *author's* membership (`workers/subscription.ts:906-911`). This is an authorization-relevant behaviour that ADR-001's policy adapter has to reproduce, and BB-R-006 does not mention it. **Recommend:** add a BB-R-006 sub-item (or an ADR-001 note) for bot identity: bot-owned membership by default, caller's membership under `runAsUser`.

###### 2. Notes for the Java port

###### (a) `$execute` in full — the invocation surface and what BB-R-016 must reproduce

**Six ways into the same `executeBot(BotExecutionRequest)` call** (`bots/execute.ts:26`):

| Path | Entry point | `input` | `contentType` | `runAs` |
|---|---|---|---|---|
| `$execute` operation | `fhir/operations/execute.ts:95` | POST body / GET query | the request's own `Content-Type` | bot's membership, or caller's under `runAsUser` |
| Subscription channel `Bot/<id>` | `workers/subscription.ts:920` | changed resource (`{deletedResource}` on delete) | `application/fhir+json` | bot's, or the **resource author's** under `runAsUser` |
| Pre-commit hook | `fhir/precommit.ts:128` | candidate resource | `application/fhir+json` | bot's membership (mandatory) |
| Cron (`Cron` resource) | `workers/cron.ts:397` | the whole `Cron` resource | `application/fhir+json` | bot's membership |
| `POST /webhook/:membershipId` | `webhook/routes.ts:48` | POST body / GET query | request's `Content-Type` | the membership named in the path |
| CDS Hooks `POST /cds-services/:id` | `cds/routes.ts:67` | CDS Hooks request JSON | `application/json` | **caller's** membership |
| Custom `$<code>` operation | `fhir/operations/custom.ts:86` | target resource (instance) or body/query | request's `Content-Type` | bot's, or caller's under `runAsUser` |
| Agent inbound message | `ws/agent.ts:248` | HL7v2 / DICOM payload from the on-prem agent | `x-application/hl7-v2+er7` etc. | bot's membership |

**Content types.** `$execute` accepts and returns **non-FHIR bodies**. `MIRRORED_CONTENT_TYPES = [text/plain, x-application/hl7-v2+er7]` are echoed back as-is; every other input yields `application/json` (`bots/utils.ts:310-320`). A `Resource` return value goes through `sendFhirResponse(… forceRawBinaryResponse: true)`, so a returned `Binary` is emitted raw. A returned number is stringified so Express does not read it as a status code (`bots/utils.ts:95-99`). No return value at all yields `allOk` (200) on success or `badRequest(logResult)` (400) on failure; a non-OK `OperationOutcome` return value both flips `success` to false and sets the HTTP status from that outcome (`bots/utils.ts:140-145,370-374`).

**`runAsUser`.** `Bot.runAsUser` (`Bot.d.ts:154`) switches the execution identity from the bot's own `ProjectMembership` to the caller's — with the caller's access policy — and additionally forwards the caller's `Cookie` header into the bot's `MedplumClient` default headers (`bots/utils.ts:52-81`). On the subscription path it resolves to `resource.meta.author`, not the HTTP caller. Documented at `bots/bot-run-as-user.md — Automate > Bots > Security & Permissions > Run as User`.

**Secrets.** `getBotSecrets` (`bots/utils.ts:282-308`) merges up to four sources in this precedence, lowest to highest: bot-project `systemSecret` (only when `Bot.system` is true), bot-project `secret`, runAs-project `systemSecret` (only when `Bot.system` and it is a different linked project), runAs-project `secret`. The result is a `Record<name, ProjectSetting>` injected into the bot event. "Most specific beats more general; defer to local control."

**Auth token.** Each run mints a fresh `Login` with `authMethod: 'execute'` and a short-lived access token for `runAs` (`bots/utils.ts:237-261`), which is what the bot's in-process `MedplumClient` uses — so a bot's writes are attributed to `runAs.profile` and pass through the same access policies as any other caller.

**Timeout.** Runtime-dependent, not a single value. `vmcontext`: `DEFAULT_VM_CONTEXT_TIMEOUT = 10000` ms as a Node `vm` script timeout (`bots/vmcontext.ts:48`), and the runtime is **off unless `config.vmContextBotsEnabled`** with an explicit "not a sandbox boundary" security note (`vmcontext.ts:23-46,59`). `awslambda`: `Bot.timeout` seconds, lazily populated at deploy time from the Lambda's own config, default `DEFAULT_LAMBDA_TIMEOUT = 10` s (`cloud/aws/deploy.ts:28,128-144`). Overall bot latency is recorded as the `medplum.bot.execute.time` histogram and every run writes an `AuditEvent` (`bots/execute.ts:63-73`, gated by `Bot.auditEventTrigger`: `always` \| `never` \| `on-error` \| `on-output`).

**Other side effects of every run.** `writeBotInputToStorage` (`bots/utils.ts:177-235`) writes one JSON row per execution to binary storage under `bot/<runAsProjectId>/YYYY/MM/DD/<ts>-<uuid>.json`, partitioned for Athena, with HL7v2 messages parsed into indexed columns (MSH sending/receiving app+facility, message type, version; PID id/MRN; OBX id/accession). Partitioning is by the **runAs** project, not the bot's owning project, so a bot shared from a linked project does not deposit the caller's data in the publisher's partition.

**Feature gate.** `isBotEnabledForProject` checks `Project.features` includes `bots` on the **runAs** project for execution (`bots/execute.ts:35`) but on the **bot's own** project for deploy (`deploy.ts:93`) — deliberately asymmetric, with a comment explaining why.

**What Camel-based BB-R-016 must reproduce for a bot to be callable the same way.** In descending order of how much wire-compat depends on it:
1. `POST /fhir/R4/Bot/:id/$execute` and `/fhir/R4/Bot/$execute?identifier=…` with pass-through request and response bodies and the mirroring rule for `text/plain` and HL7v2 — this is what `medplum.executeBot` and `BotEditor` call, so it is the one path SDK-grade compat (ADR-003 C, v0.2) actually needs.
2. The result→HTTP mapping: return value verbatim; nothing returned → `allOk`/`badRequest(log)`; non-OK `OperationOutcome` → that status.
3. Identity: run the route with a `runAs` principal (bot's membership by default, caller's under `runAsUser`), issue it a scoped token, and enforce the same access policies on its writes.
4. Secrets injection with the four-source precedence, from Keycloak client attributes / env in `lite` and Vault in `full`.
5. A per-route timeout with a sane default (Medplum's 10 s is a reasonable starting point) and an execution `AuditEvent`.
6. The `bots` project feature gate — cheap and it keeps `Project.features` wire-compatible.
7. `Prefer: respond-async` returning 202 + `Content-Location` to an `AsyncJob`, if BB-R-001.7's async machinery is in place by then.
8. Optional / later: SSE streaming (`Accept: text/event-stream` + `Bot.streamingEnabled`), the input-archival rows, the `identifier` lookup form.
Not needed: `$deploy` in Medplum's shape (BB-R-016 deploys via the CLI + a JVM redeploy) and `$init` (a bot is a class in a repo, though something must still create the `Bot` resource + `ProjectMembership` pair so `runAs` and access policies exist).

###### (b) The Agent operations as a group — what the protocol actually is, and what v0.3 needs

The Medplum "agent" is a **separately installed on-prem process** (`packages/agent`) that bridges hospital-network HL7v2 MLLP / ASTM / DICOM endpoints to the cloud server. The FHIR operations are only the control plane; the data plane is a websocket plus Redis pub/sub:

- **Connect.** The agent opens a websocket to the server and sends `agent:connect:request` with an access token; the server verifies it, associates the socket with an `Agent` resource, and starts a heartbeat (`ws/agent.ts:56-120`, `DEFAULT_HEARTBEAT_MS`).
- **Liveness registry.** The connection writes `medplum:agent:<id>:info` (`{status, version, lastUpdated}`) into the **cache** Redis with a 24 h TTL, refreshed on each heartbeat response. `$status` (OPX-011) and `$bulk-status` (OPX-012) are pure reads of this key — they never touch the agent.
- **Server → agent.** Every operation publishes a JSON message on the **pub/sub** Redis channel literally named `Agent/<id>`, which that agent's socket is subscribed to (`utils/agentutils.ts:245-250`). Message types: `agent:transmit:request`, `agent:reloadconfig:request`, `agent:upgrade:request`, `agent:stats:request`, `agent:logs:request`, `agent:heartbeat:request`.
- **Agent → server, request/response.** For a request that expects a reply, the server generates a callback channel `Agent/<id>-<uuid>`, subscribes to it, publishes the message with that `callback`, and races the reply against a timer (default 5 s; 10 s for `$push`, 45 s for `$upgrade`). The agent echoes `callback` back on its `*:response` message and the socket handler republishes it onto that channel (`ws/agent.ts:100-112`). `agent:error` uses the same callback path and surfaces as a 400.
- **Agent → server, inbound data.** An `agent:transmit:request` *from* the agent (an HL7v2 message arriving at an on-prem listener) calls `executeBot` on the server (`ws/agent.ts:248`) — this is how HL7v2 reaches a bot. So the agent is also a seventh `$execute` invocation path.
- **Bulk semantics.** All the type-level agent operations run an `Agent` search from the query string (`_count` capped at 100) and fan out with `Promise.allSettled`, returning a `Bundle{collection}` of `Parameters{agent, result}` wrappers where each `result` is either `Parameters` or an `OperationOutcome`. Partial failure is the normal case and never fails the request.

**What a v0.3 Big Book HL7v2 bridge would need** (this is currently a `GAP`; area 1 proposed T15/BB-R-028):
1. An `Agent` resource (Medplum-shaped) holding channel definitions — endpoint, port, protocol, target bot — plus `Device` resources for outbound destinations, since `$push` addresses a `Device/<id>` or `Device?search`.
2. A **duplex control channel** from the on-prem process to the server. Big Book's stack already has the pieces: Camel HL7 + HAPI HL7v2 on the agent side (BIGBOOK.md, v0.3), and either a websocket endpoint or — more in keeping with "reuse first" — the event bus from ADR-002 if it can reach outside the cluster. The requirement is: authenticated persistent connection, server-initiated request/reply with correlation ids and timeouts, and a liveness key.
3. A **liveness registry** with a TTL so `$status`-equivalents are a cheap read. In `lite` this can be an in-JVM map since HAPI is embedded and there is one node (ADR-006); the multi-node story needs the ADR-002 bus or Redis.
4. Inbound routing: an arriving HL7v2 message must invoke a bot (a Camel route) with `contentType: x-application/hl7-v2+er7` and the ability to return an ACK synchronously — i.e. the OPX-010 `waitForResponse` / `returnAck` semantics, which are the whole point for MLLP.
5. Outbound `$push` with `waitForResponse`, a bounded `waitTimeout` and the response echoed back with the agent's own status code and content type.
6. Bulk fan-out over an `Agent` search, since a real deployment has many sites.
7. **Displace, don't port:** `$stats` (OPX-015) and `$fetch-logs` (OPX-016) should be OTel metrics and log shipping under BB-R-015, not bespoke FHIR operations; `$upgrade` (OPX-014) should be whatever the agent's packaging story is (Helm/systemd/container image under BB-R-011), not an HTTP-triggered self-update.
Sizing note: the seven operations themselves are thin (~1.4k lines including `agentutils.ts`); the cost is the agent process and the transport, not the operations.

###### (c) `$get-ws-binding-token` and BB-R-007.8

`GET /fhir/R4/Subscription/:id/$get-ws-binding-token` (OPX-017) is the HL7 R5-backport operation, shipped with the upstream `OperationDefinition` inline (`getwsbindingtoken.ts:18-127`). Mechanically:

1. Gate on the project feature `websocket-subscriptions` (400 otherwise).
2. Read the `Subscription` **as the caller**, so the access policy decides who may subscribe.
3. Validate: `channel.type === 'websocket'`, non-empty `criteria`, and `criteria.split('?')[0]` is a real R4 resource type — the last check exists explicitly to stop a bad criteria from "gumming up the pipes" of the in-memory matcher.
4. Mint a JWT with `generateAccessToken` carrying the login's normal claims (`client_id`, `login_id`, `sub`, `username`, `scope`, `profile`) **plus two extra claims** `subscription_id` and `membership_id`, `lifetime: '1h'`.
5. Return `Parameters{token, expiration (now+1h), subscription, websocket-url}` where the URL is `baseUrl` with the scheme swapped to `ws`/`wss` plus `ws/subscriptions-r4`.

The client then opens that websocket and sends `{type: 'bind-with-token', payload: {token}}`; the server verifies the JWT, requires `subscription_id`, `login_id` and `membership_id` to be present (`ws/subscriptions.ts:352`), looks the Subscription up in the cache Redis, registers the socket, and replies with a **handshake bundle** before starting heartbeats (`ws/subscriptions.ts:377-447`). `unbind-from-token` reverses it. One socket can carry many subscriptions; each is bound with its own token.

**Implications for BB-R-007.8 (deferred v0.2, and BB-R-025):**
- The token mint is unavoidably **glue**, not `wire Keycloak`. It is a per-subscription capability token with claims Keycloak has no reason to issue, and Medplum's own key material signs it. On Big Book the natural shape is: Big Book signs a short-lived binding token derived from the already-validated Keycloak access token, and the websocket endpoint verifies it locally. Roughly 100–150 lines.
- **Check what HAPI gives you before writing anything else.** HAPI has R5 websocket subscription support and its own `$get-ws-binding-token`; if its token and bind protocol are usable, the brick reduces to configuration plus the Medplum-shaped envelope. If HAPI's binding differs on the wire, decide whether SDK-grade compat (ADR-003, v0.2) requires matching Medplum's `bind-with-token` protocol — `@medplum/core`'s `SubscriptionManager` and `@medplum/react`'s `useSubscription` both speak it, so app-grade compat (v1.0) certainly does. This is a good candidate for the issue-#8 "verify on pinned HAPI" list.
- Add the `websocket-subscriptions` **project feature** to the area-4 settings inventory; without it the operation 400s, so a wire-compatible client that forgets it sees a confusing failure.
- Do **not** port OPX-018/019/020. They exist only because Medplum keeps subscription registration in Redis hashes that can desynchronise; they are an artefact of that design, not a capability.

###### (d) Load-bearing for `@medplum/app` / `@medplum/core` vs. purely operational

This is the ADR-003 question: which rows block SDK-grade (v0.2) or app-grade (v1.0) compat.

**SDK-grade — a `MedplumClient` method exists, so `@medplum/core` cannot run unmodified without it:**
- **OPX-001 `$execute`** — `client.ts:2924` `executeBot(idOrIdentifier, body, contentType)`. Note it supports the `?identifier=system|value` type-level form as well as the instance form. This is the only bot row in this area that is SDK-grade.
- **OPX-010 `Agent/$push`** — `client.ts:3127` `pushToAgent(agent, destination, body, contentType, waitForResponse, {waitTimeout, returnAck})`. SDK-grade in the strict sense, but only reachable if an agent exists at all — v0.3 by the roadmap, so it does not block v0.2.

No other operation in this area has a `MedplumClient` method. `$book`/`$find`/`$hold`/`$confirm`, `$deploy`, `$init`, the DB ops, the SMART Health rows and `$ai` are all called through the generic `medplum.get/post(medplum.fhirUrl(...))` escape hatch.

**App-grade (`@medplum/app` runs unmodified, v1.0) — the app calls these directly:**
- `Bot/:id/$deploy` and `Bot/:id/$execute`, including the SSE variant — `app/src/resource/BotEditor.tsx:160,179,205`. The Bots screen is already **v0.2** in BB-R-013.3, so the app's bot editor is the first place app-grade pressure appears.
- Agent `$status`, `$reload-config`, `$upgrade`, `$fetch-logs`, and `pushToAgent` for ping — `app/src/resource/ToolsPage.tsx:291-354`. Only relevant once agents exist (v0.3+).
- `$verify-smart-health-card`, `$resolve-smart-health-link` — `app/src/BatchPage.tsx:151,196`. Non-goal; app-grade compat would need them stubbed or the screen removed.
- The whole super-admin database console — `$clear-all-ws-subs`, `$db-stats`, `$db-invalid-indexes`, `$db-schema-diff`, `$explain` (`app/src/admin/SuperAdminPage.tsx:84,118,136,154,652`), `$db-column-statistics` + `$db-configure-column-statistics` (`admin/db/ColumnStatistics.tsx:38,79`), `$db-indexes` + `$db-configure-indexes` (`admin/db/GINIndexes.tsx:34`, `ConfigureGINIndexesForm.tsx:57`), `$db-index-bloat` (`admin/db/IndexBloat.tsx:87,140`), and `$get-ws-sub-stats` / `$get-ws-sub-project-stats` (`admin/WsSubStatsWidget.tsx:243,261`).
  **This is the sharpest ADR-003 finding in this area:** twelve of the nine-plus operational rows exist *only* to feed `@medplum/app`'s super-admin console. If v1.0 app-grade compat is read as "every screen works", it drags in Postgres catalog introspection and DDL-over-HTTP that Big Book has decided (correctly) not to have. **Recommend ADR-003 record explicitly that app-grade compat is scoped to the project-user surface and excludes the super-admin database console**, otherwise the v1.0 exit criterion is unachievable-by-design rather than merely hard.

**Purely operational — no client, no app, server-internal or third-party callers only:**
OPX-002/003/004 (subscription, pre-commit, cron bot triggers — internal), OPX-005 (`/webhook/:id`, called by third parties), OPX-006 (CDS Hooks, called by EHRs), OPX-007 (custom operations — called by whoever defines them), OPX-036/037 (`$submit` dispatchers, used by `examples/medplum-provider`), OPX-045 (`$install`, CLI/app package flow), OPX-042 (`$smart-launch`, browser redirect from the app's Apps tab).

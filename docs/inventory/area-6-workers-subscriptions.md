##### Design calls

| # | Topic | What Medplum does | What the docs say now | Recommendation |
|---|---|---|---|---|
| D53 | **ADR-002 (event bus) is not needed for anything in v0.1–v0.2** | Medplum's "event bus" is BullMQ-on-Redis: a durable job queue with per-job retry/backoff, not a broker. Nothing in the subscription, cron, download, or bot path is pub/sub between services; the only true pub/sub (`pubsub.ts`) exists solely to fan a WebSocket event out to whichever HTTP node holds the socket — a multi-node concern that `lite` (one JVM) does not have. | ADR-002 "Kafka vs RabbitMQ vs none in `lite`"; "requirements blocked on this: BB-R-007 (v0.2 extras), BB-R-016" | **Decide ADR-002 = none, in both profiles, for v0.1–v0.2.** HAPI's `SubscriptionMatcherInterceptor` + `SubscriptionDeliveryQueue` already gives an in-JVM delivery queue; Spring `@Scheduled` + a Quartz/ShedLock-backed DB table covers cron and retries. Revisit only if (a) Big Book ever runs >1 JVM *and* needs WebSocket subscriptions (BB-R-025), or (b) BB-R-016 wants bots on separate worker nodes. Neither is v0.1/v0.2 scope. Unblocks BB-R-007 and BB-R-016 today. |
| D54 | **Retry numbers in BB-R-007.3 are unspecified; Medplum's are extreme** | Two layers. BullMQ `attempts` is set to `MAX_JOB_ATTEMPTS = 19` on the queue, but the *effective* cap is `subscription-max-attempts` (default `DEFAULT_ATTEMPTS = 4`) enforced in `catchJobError`; on exceeding it the worker throws `UnrecoverableError` so BullMQ stops. Backoff is custom `cappedExponential`: `min(20_000 * 2^(attemptsMade-1) * jitter, 8h)`, jitter uniform in [0.9, 1.1]. Server-side errors (loading the Subscription/resource, "the preamble") get a separate, much larger budget: up to 19 attempts, then the job is silently dropped. | BB-R-007.3 says only "Retry with backoff; configurable max attempts" | **Pin the numbers in the brick:** default 4 attempts total, base delay 20s, exponential ×2, cap 8h, ±10% jitter, honour `subscription-max-attempts`. Also adopt the **preamble/delivery split** (infrastructure errors retry longer than the subscriber's endpoint failing) — HAPI has no equivalent and it is ~20 lines. |
| D55 | **Rest-hook retries are not resumed across restart in `lite`** | BullMQ persists every job in Redis, so a delayed retry survives a server restart and is picked up by any node. Note: HAPI's own `SubscriptionDeliveryQueue` is **in-memory (LinkedBlockingQueue) by default** — a HAPI restart drops pending deliveries — so this is glue Big Book must write regardless of "wire HAPI". |
| D56 | **`X-Signature` HMAC is over the body only, no timestamp, no replay defence** | `createHmac('sha256', secret).update(body).digest('hex')`, hex-encoded, sent as `X-Signature` (`workers/subscription.ts:855-860`). Secret is read from `subscription-secret` (with legacy fallback URL `…/StructureDefinition-subscriptionSecret`). No timestamp, no nonce, no version prefix, and no signature at all when the extension is absent. | BB-R-007.4 "Signature header (`X-Signature`, HMAC of body with a per-subscription secret)" | **Match the wire format byte-for-byte** (n8n/bot recipes in BB-R-008 depend on it) but **additionally** send `X-Bigbook-Timestamp` and accept a `v1=<hex>` form in a second header for new integrations. Document that `X-Signature` alone is replayable. Cheap; avoids shipping a known-weak scheme as the only option. |
| D57 | **Subscription access-policy enforcement is a no-op for rest-hooks** | `satisfiesAccessPolicy` (`workers/subscription.ts:236-308`) builds the subscription author's `AccessPolicy` and checks READ on the resource — then **`return subscription.channel.type === 'websocket' ? satisfied : true`**. For rest-hooks it logs a warning and delivers anyway. The `TODO` at `:228` admits this. | BB-R-007.1 "scoped to the project"; BB-R-006 says policies gate reads | **Do not inherit the bug.** In Big Book, a rest-hook Subscription delivers only what the author's `AccessPolicy` permits to read, enforced, from v0.1. This is a divergence from Medplum wire behaviour and must be stated in `medplum-parity.md`. It is also the cheapest place to enforce it (one `satisfiedAccessPolicy` call the policy adapter already has). |
| D58 | **`Bot.runAsUser` on the subscription path resolves to the resource *author*, not a caller** | `workers/subscription.ts:903-911`: `requester = resource.meta.author`; with `runAsUser` the bot runs under **the membership of whoever wrote the resource**, which may be an entirely different user from the Subscription's author. No cookie is forwarded on this path (there is no HTTP request). | Area 3 D26 covers `runAsUser` generally; no brick mentions the subscription-path resolution | **Fold into D26** as an explicit sub-case: on a subscription trigger, `runAsUser` = the triggering resource's author's membership. | D59 | **Cron is a first-class resource in Medplum, and BB-R-016 only mentions it as a bot trigger** | Two schedulables: `Bot.cronString`/`Bot.cronTiming` (legacy, scheduler key = bare bot id) and the `Cron` resource (`cronString`, `active`, `endTime`, `targetReference`, `onBehalfOf`; scheduler key `Cron/<id>`). `Cron` carries its own identity (`onBehalfOf` membership, validated same-project) and the whole `Cron` resource is passed as the bot's input. | D60 | **`subscriptionAutoDisable` is Redis-only and would be lost in `lite`** | `subscription-failure-tracker.ts`: a Redis **sorted set** per subscription (`medplum:sub:failures:<id>`), score = epoch ms, pruned to the largest configured window, `ZCOUNT` per trigger. | D61 | **WebSocket subscriptions (BB-R-025) cannot be built the Medplum way without Redis** | The whole WS path is Redis: an active-subscription hash per `(project, resourceType)` (`pubsub.ts:25-27`), a per-user active set, a `Subscription/<id>` cache entry, a pub/sub channel `WEBSOCKET_SUB_PUBLISH_CHANNEL` that fans the event to the node holding the socket, and a 1h JWT from `$get-ws-binding-token`. | BB-R-025 "Subscription extras (WebSocket …) — wire/glue" | **For a single-JVM `lite`, none of it is needed**: an in-JVM `Map<subscriptionId, Set<WebSocketSession>>` plus Spring's `@ServerEndpoint`/`WebSocketHandler` reproduces the protocol exactly, and HAPI has a `websocket` channel type already. #### Notes

##### (a) The full subscription delivery contract — direct input to BB-R-007

**Where criteria matching happens.** Exactly one place decides whether a change fires a Subscription: `resourceMatchesSubscriptionCriteria` in `core/subscriptions/index.ts:727-804`, called from `workers/subscription.ts:459` (async path) and `fhir/precommit.ts:98` (sync pre-commit path). Its step 6 is `matchesSearchRequest(resource, parseSearchRequest(criteria))` — **the in-memory matcher that area 2 (SRCH-060, D15) found silently wrong five ways.** The WebSocket path calls the matcher a *second* time, directly, on the criteria string cached in Redis (`workers/subscription.ts:538`), bypassing the extension checks entirely — so a websocket Subscription's `subscription-supported-interaction`, `fhir-path-criteria-expression` and account extensions are evaluated once in `resourceMatchesSubscriptionCriteria` (via the resource loaded from the Redis cache) but the pre-filter at `:538` is criteria-only. Consequences Big Book inherits if it copies the design: a chained criterion (`Observation?subject.name=x`) means the Subscription **never fires** and nothing tells the author; `Patient?_count=1` fires on every Patient; a `:not-in` criterion fires on exactly the wrong set. The area 2 recommendation stands and is the single most important BB-R-007 design rule: **validate `Subscription.criteria` at write time and reject (400) anything the matcher cannot evaluate**, and use the *same* validated matcher for `AccessPolicy.criteria`.

**Every Medplum extension URL found, with its effect:**

| URL | Value | Effect |
|---|---|---|
| `https://medplum.com/fhir/StructureDefinition/subscription-supported-interaction` | `valueCode` (repeatable) | Interaction filter. OR across entries; absent ⇒ all of create/update/delete. |
| `https://www.medplum.com/fhir/StructureDefinition/subscription-secret` | `valueString` | HMAC secret ⇒ `X-Signature` header. |
| `https://www.medplum.com/fhir/StructureDefinition-subscriptionSecret` | `valueString` | **Legacy** spelling of the same, still honoured. |
| `https://medplum.com/fhir/StructureDefinition/subscription-max-attempts` | `valueInteger` | Delivery attempt cap; default 4. |

| `https://medplum.com/fhir/StructureDefinition/fhir-path-criteria-expression` | `valueString` | FHIRPath over `%current`/`%previous`; must be truthy. |
| `https://medplum.com/fhir/StructureDefinition/subscription-audit-event-destination` | `valueCode ∈ {resource, log}` (repeatable) | Where the delivery AuditEvent goes; default `resource`. |

**Retry policy, exact numbers** (`workers/subscription.ts:80-107, 151-185, 933-962`):
- Queue-level `attempts` = `MAX_JOB_ATTEMPTS` = **19**.
- Effective delivery cap = `subscription-max-attempts` ?? `DEFAULT_ATTEMPTS` = **4**; exceeding it throws `UnrecoverableError`.
- Preamble (loading the Subscription/resource) cap = `MAX_PREAMBLE_ATTEMPTS` = **19**, after which the job is logged and abandoned with no auto-disable consequence.
- Backoff = `min(20_000 ms × 2^(attemptsMade − 1) × jitter, 8 h)`, `jitter` uniform in **[0.9, 1.1]**.
- 19 attempts ≈ **72–80 hours** (10 attempts to reach ~5h delay, then 9 spaced 8h).
- Outbound HTTP timeout = **120 000 ms**.
- On each retry, job priority is lowered to `1 + attemptsMade`.

**`X-Signature` computation.** `createHmac('sha256', secret).update(body).digest('hex')` — lowercase hex, over the **exact bytes posted**: `stringify(resource)` for create/update, the two-character string `{}` for delete, and `JSON.stringify(input)` on the bot path. No timestamp, no nonce, no version prefix. A verifier must hash the raw body before any JSON re-serialisation.

**Delivery AuditEvents.** One per attempt, `type.code = 'transmit'`, `source.observer = Subscription/<id>`, `entity = [resource, subscription, bot?]`, `period` spanning the change time to now, `outcome` 0 (success) / 4 (minor failure) / 8 (serious failure, auto-disable only), `outcomeDesc` = `Attempt <n> received status <code>` or `Attempt <n> received error <err>` (`n` is 0-based). Tenanted by copying `meta.project/account/accounts` from the Subscription. Destination `resource` (default) or `log` per SUB-009. `redactAuditEvents` (server or project setting) redacts `source.observer`.

**`subscriptionAutoDisable` / failure tracking.** Triggers `[{maxConsecutiveFailures, timeWindowSeconds}]` from `Project.systemSetting[subscriptionAutoDisable]` (JSON) falling back to server config. Counter = a Redis sorted set per subscription, pruned to the largest window, `ZCOUNT` per trigger, cleared on any success. Tripping runs an atomic JSON-Patch transaction (`test /status == active`, `replace /status = 'off'`, `add /error = <message>`) plus a `SeriousFailure` AuditEvent.

**On permanent failure.** (1) The job goes to BullMQ's `failed` set — retained, inspectable, never retried. (2) A `MinorFailure` AuditEvent exists for every attempt. (3) The failure is recorded in the auto-disable counter; if a trigger is configured and trips, `Subscription.status` becomes `off` with a human-readable `Subscription.error`, and a `SeriousFailure` AuditEvent is written. (4) **If no trigger is configured (the default), nothing else happens** — the Subscription stays `active`, the payload is dropped, and the only signal is the AuditEvent trail. There is no dead-letter queue and no notification. Big Book should either ship a default trigger or surface failed deliveries in the admin UI; silently dropping is the worst of the three.

##### (b) Queueing infrastructure and the Big Book equivalent

**What Medplum has.** BullMQ over Redis: durable jobs, per-job `attempts` and pluggable backoff, delayed jobs, priorities, repeatable "job schedulers" (cron), queue-level global concurrency stored in Redis, stall detection via lock renewal, and a `failed` set that survives restart. On top of that sits a **separate, genuinely pub/sub** use of Redis (`pubsub.ts`) for WebSocket fan-out across nodes, plus Redis as a resource cache (`Subscription/<id>`), the WS active-subscription registry, the FHIRcast subscription/context store, the agent info store, the subscription failure counters, and the server registry.

**What HAPI FHIR JPA provides natively.** HAPI has a complete subscription subsystem: `SubscriptionMatcherInterceptor` on `STORAGE_PRECOMMIT_RESOURCE_*`, a `SubscriptionRegistry` refreshed by `SubscriptionLoader`, `InMemoryResourceMatcher` (with its own documented gap list — chained params, `_has`, some modifiers) falling back to a database match, and `SubscriptionDeliveringRestHookSubscriber` / `…EmailSubscriber` / websocket delivery. Channels are `LinkedBlockingQueue`-backed in-memory by default (`subscription_matching` and `subscription_delivery` channels), with a Spring Messaging `ChannelFactory` SPI that can be pointed at JMS/Kafka. Crucially: **HAPI's default delivery channel is in-memory, so pending deliveries are lost on restart, and HAPI's rest-hook subscriber has no HMAC signature, no custom-header list, no success-code list, no max-attempts extension, and no auto-disable.** "Wire HAPI" for BB-R-007 therefore means: use HAPI's matcher interceptor and registry for *detection*, and write Big Book's own *delivery* on top.

**What Spring needs, concretely.**
1. A Postgres table `subscription_delivery(id, subscription_id, project_id, resource_type, resource_id, version_id, interaction, attempt, next_attempt_at, status, last_error, consecutive_failures)` written by the HAPI `SUBSCRIPTION_AFTER_ACTIVE_SUBSCRIPTION_TRIGGERED` (or `STORAGE_PRECOMMIT`) hook.
2. One `@Scheduled(fixedDelay = 1000)` poller doing `SELECT … WHERE status='pending' AND next_attempt_at <= now() ORDER BY attempt, next_attempt_at FOR UPDATE SKIP LOCKED LIMIT n`, dispatching to a bounded `ThreadPoolTaskExecutor`. `SKIP LOCKED` is what makes this safe if a second JVM ever appears, so the design does not have to change for `full`.
3. Backoff computed in Java with Medplum's numbers; `next_attempt_at = now + min(20s × 2^(attempt-1) × jitter, 8h)`.
4. Cron via Quartz with the Postgres JobStore (or `@Scheduled` + ShedLock), keyed on `Cron.id`.
5. `RestClient` with a 120s timeout and the SSRF allowlist for the outbound call.

**Camel is not needed for BB-R-007** — it is a queue-and-retry problem, not a routing problem. Camel *is* the right tool for BB-R-016 (bots), where the "from(…).to(…)" shape and the component library earn their keep, and a Camel route can be the *consumer* of the delivery table (`from("sql:…?consumer.delay=1000")`) if the team prefers one mechanism.

**Does this force ADR-002's hand?** **No — and that is the finding.** Nothing in BB-R-007, BB-R-008, BB-R-016 or BB-R-020 needs a broker. Medplum's use of Redis is (i) a durable work queue, which Postgres does adequately at Big Book's scale, and (ii) cross-node WebSocket fan-out, which a single-JVM `lite` does not have. **Recommend deciding ADR-002 = "none" for v0.1 and v0.2** (D53). The only future trigger is BB-R-025's WebSocket subscriptions on a multi-replica `full` deployment, and even there sticky sessions at Traefik are the cheaper answer; a broker becomes genuinely attractive only if bots get their own worker nodes.

##### (c) Bot execution mechanics

**Invocation from the subscription worker** (`workers/subscription.ts:883-931`): endpoint `Bot/<id>` ⇒ read the Bot on the system repo ⇒ resolve `runAs` (bot's own membership, or the **triggering resource's author's** membership under `runAsUser`) ⇒ input is the resource or `{deletedResource}` ⇒ `contentType = application/fhir+json` ⇒ the rest-hook headers including `X-Signature` are passed through as `headers` ⇒ `executeBot`. Failure propagates into the same retry/auto-disable machinery as an HTTP failure.

**Invocation from the cron worker** (`workers/cron.ts:369-398`): for a `Cron` resource, `runAs = cron.onBehalfOf` (validated same-project) and the **whole `Cron` resource** is the input, so a bot can read its own schedule parameters. For a legacy `Bot.cronString`, `runAs` is the bot's own membership and the `Bot` is the input. No headers, no subscription.

**`executeBot`** (`bots/execute.ts:26-75`) is the single funnel for all seven surfaces: checks `isBotEnabledForProject(runAs.project)` — **the project entitled to run bots is the one the run executes in, not the one that owns the bot** (so a bot shared from a linked project runs on the caller's entitlement); writes the input to binary storage at `bot/<runAsProjectId>/<yyyy/mm/dd>/<epoch>-<uuid>.json` for debugging/replay/analytics (HL7v2 input is additionally decomposed into MSH/PID/OBX columns); mints a short-lived access token; assembles secrets; dispatches on `runtimeVersion`; normalises the result (a returned non-OK `OperationOutcome` counts as failure); records `medplum.bot.execute.time`; writes the bot AuditEvent.

**Execution contexts.**
- `awslambda` — `InvokeCommand` with `InvocationType: RequestResponse`, `LogType: Tail`; the payload is `{bot, baseUrl, requester, accessToken, input, contentType, secrets, traceId, traceparent, headers}`. Timeout comes from the Lambda function's own configuration (`Bot.timeout` is lazily filled from it at `$deploy`, default 10s). Logs are the tail-decoded CloudWatch output. A streaming variant exists for `Bot.streamingEnabled` + SSE.
- `vmcontext` — `vm.runInNewContext` with a sandbox exposing `console` (a `MockConsole` that *is* the log capture), `fetch`, `require`, `process`, `ContentType`, `Hl7Message`, `MedplumClient`, and an `event` object. **Timeout = `Bot.timeout × 1000` ms, default `DEFAULT_VM_CONTEXT_TIMEOUT = 10 000`.** Disabled unless `vmContextBotsEnabled`; the file's own security note says it is explicitly *not* a sandbox boundary for untrusted code.
- `fission` — delegated to `cloud/fission/execute`.
- Anything else ⇒ `{success: false, logResult: 'Unsupported bot runtime'}`.

**Timeout.** `Bot.timeout` (integer seconds) caps `vmcontext` and (via `$deploy`) the Lambda. There is **no timeout at all on the `executeBot` call itself** — a Fission or Lambda call that hangs hangs the worker thread until the runtime's own limit fires.

**Secrets injection.** `getBotSecrets` (`bots/utils.ts:282-308`) merges `ProjectSetting[]` from up to four sources, later overriding earlier: bot-project `systemSecret` (only if `Bot.system`), bot-project `secret`, runAs-project `systemSecret` (only if `Bot.system` and a different project), runAs-project `secret`. Collapsed to `Record<name, ProjectSetting>` and handed to the runtime as `event.secrets`. Principles stated in the source: most specific beats general; local control beats system.

**Identity (`runAsUser`, cross-ref area 3 D26).** By default the bot runs under its **own** `ProjectMembership` (created by `Bot/$init`, where `user` and `profile` both point at the Bot), so it has its own `AccessPolicy`. `getBotAccessToken` creates a `Login` with `authMethod: 'execute'` and mints an access token with `login_id`, `sub`/`username` = the membership's user id, `profile` = the membership's profile, `scope: 'openid'`. With `runAsUser: true` the identity becomes: on `$execute`/custom operations, the HTTP caller's membership **plus the caller's `Cookie` header forwarded into the bot's client**; on a **subscription trigger, the triggering resource's author's membership** (`workers/subscription.ts:903-911`) — a different person from the Subscription's author, and no cookie. On the agent path, always `authState.membership` (the agent's credentials), never the Bot's. See D58: recommend not implementing `runAsUser` on the subscription trigger.

**Output capture.** `BotExecutionResult = {success, logResult, returnValue?}`. `logResult` is the runtime's captured stdout (MockConsole for vmcontext, tail-decoded CloudWatch for Lambda). `success` is false if the runtime failed, the handler threw, execution timed out, **or the handler returned a non-OK `OperationOutcome`** (`normalizeBotExecutionResult`). `returnValue` is passed through to the HTTP response for `$execute` (numbers coerced to string so Express does not read them as a status code), wrapped into `Parameters` for custom operations, and used as the replacement resource on the pre-commit path. The bot AuditEvent is gated by `Bot.auditEventTrigger ∈ {always, never, on-error, on-output}` and routed by `Bot.auditEventDestination ∈ {log, resource}` (default: a resource).

**What a Camel-based BB-R-016 must reproduce.** (1) One `executeBot` funnel that every trigger goes through, so the entitlement check, input archival, AuditEvent and metrics are written once. (2) A `runAs` principal resolved per trigger, issued a scoped token, with the same `AccessPolicy` enforced on the bot's own writes — this is an ADR-001 concern, not a bot-runtime detail. (3) The four-source secrets merge, in order, gated on `Bot.system`. (4) A per-route timeout defaulting to 10s, honouring `Bot.timeout`. (5) Log capture surfaced as `logResult`, with the non-OK-`OperationOutcome`-means-failure rule. (6) On the subscription trigger, expose `X-Medplum-Subscription`, `X-Medplum-Interaction` and `X-Signature` as Camel headers. (7) `auditEventTrigger`/`auditEventDestination` semantics. Not needed: `$deploy` of uploaded JS, the Lambda/Fission runtimes, input archival to object storage (nice-to-have, not v0.2).

##### (e) Ordering, idempotency and delivery guarantees

**Rest-hook: at-least-once, unordered, not idempotent.**
- *At-least-once*: a worker that dies after the POST but before the job is acked re-runs the whole job and POSTs again. There is no idempotency key in the request — `X-Medplum-Subscription` identifies the subscription, not the delivery; the closest thing a receiver has is `meta.versionId` inside the body. A receiver **must** dedupe on `(X-Medplum-Subscription, resource id, meta.versionId)`.
- *Unordered*: jobs for the same resource are independent. With `concurrency > 1`, or multiple worker hosts, or any retry at all, v2 can be delivered before v1. The stale-version guard at `workers/subscription.ts:647-651` only runs on **retries** (`attemptsMade > 0`) and only drops the job — it never reorders, and the first attempt of a superseded version is still delivered.
- *Concurrent updates*: two rapid updates enqueue two jobs; both deliver (correctly — a subscriber should see both). If the first fails and retries 20s later, by which time the resource has moved on, the retry is dropped, so the subscriber sees v2 but **never** v1. That is a silent gap in the event stream with only an AuditEvent to show for it.
- *Exactly-once is not achievable* and Big Book should not promise it. Document at-least-once, ship the dedupe guidance in the BB-R-008 n8n recipe, and consider a `X-Bigbook-Delivery-Id` header so receivers have a proper key.

**WebSocket: at-most-once.** `socket.send` is fire-and-forget with no ack, no buffering and no replay. A client that is disconnected when the event fires never sees it; on reconnect it must re-read. Ordering per socket follows TCP, so events are ordered *within* one connection but nothing survives a reconnect.

**Cron: at-most-once per tick, no catch-up.** BullMQ job schedulers do not backfill missed ticks after downtime, and `reloadCronBots()` obliterates and re-registers rather than replaying.

**BB-R-007's "within 5 seconds" exit test.** Easily met by the D55 design: the HAPI interceptor writes a row in the same transaction, a 1s poller picks it up, the HTTP POST follows. Worst case ≈ 1s poll + RTT. Medplum's own first attempt has no deliberate delay at all (BullMQ processes immediately), so 5s is generous for both. The risk to the exit test is not latency but **the matcher**: a criteria string the matcher silently evaluates to `false` produces zero deliveries and a green-looking log. The exit test should assert both "a matching create delivers within 5s" **and** "a criteria the server accepted actually fires" — which is why D15's write-time validation belongs in BB-R-007, not only BB-R-006.

#### Contradictions with REQUIREMENTS.md / ADRs

**BB-R-007, all nine sub-items checked:**

1. *"R4 `Subscription` with `criteria` (search string) and `channel.type = rest-hook`; fires on create/update/delete matching the criteria, scoped to the project."* — Understated in three ways. (a) "scoped to the project" is true for **selection** but the access-policy check that would make it true for **content** is a deliberate no-op for rest-hooks (`workers/subscription.ts:307`, `TODO` at `:228`) — a rest-hook can currently exfiltrate resources its author could not read (D57). (b) Delivery is additionally suppressed by `meta.account` intersection, by the `AuditEvent` and websocket-`Subscription` blanket exclusions, and by the outbound-URL allowlist (T55). (c) Only the first 1000 active Subscriptions in a project are ever evaluated (SUB-002). Brick is wrong by omission; fix per T55 and D57.

2. *"Interaction filter extension … — HAPI supports; map the Medplum extension URL."* — **"HAPI supports" is wrong.** HAPI R4 `Subscription` has no interaction filter; the R5 `SubscriptionTopic` notion of `supportedInteraction` is a different resource and a different wire shape. This is glue on a HAPI delivery hook (~20 lines), not configuration. Also the extension is repeatable with OR semantics. T54.

3. *"Retry with backoff; configurable max attempts; delivery status visible as one `AuditEvent` per delivery attempt."* — Directionally correct and the AuditEvent-per-attempt claim is exactly right (SUB-018). But the numbers are unspecified, and Medplum has **two** retry budgets (delivery 4, preamble 19) with a custom capped-exponential backoff. D54 pins them. Also: the brick says nothing about what happens when retries are exhausted, and the honest answer is "nothing, unless `subscriptionAutoDisable` is configured" — see D60.

4. *"Signature header (`X-Signature`, HMAC of body with a per-subscription secret) — **glue** if HAPI lacks it."* — HAPI does lack it, so `glue` is correct. Two corrections: two extension URLs are accepted (one legacy, with `www.` and a `-`), and the digest is lowercase **hex**, not base64. T56. Note also the scheme has no timestamp and is replayable (D56).

5. *"`$resend` operation to re-fire a resource's subscriptions — **glue** (thin)."* — `thin` is right, but it is **not an operation** — it is a route on the repository, and it requires project-admin, returns **412** if the resource has moved since, and **re-evaluates criteria** rather than force-sending. T57.

6. *"Expression-based criteria (FHIRPath `%previous` vs `%current`) — HAPI `in-memory` matcher gap; **defer v0.2**."* — Correct, and the deferral is right. Add the URL and the detail that `%previous` is `{}` on create. T59.

7. *"AuditEvent as destination / log-only — **defer v0.2** with BB-R-012 audit."* — **Mis-stated.** This is not "AuditEvent as a subscription channel"; it is the *destination of the delivery AuditEvent* (`resource` vs `log`), controlled by `subscription-audit-event-destination`. And it is not separable from sub-item 3 — you cannot ship "one AuditEvent per attempt" in v0.1 without deciding where it goes. Reword and fold into v0.1. T58.

8. *"WebSocket subscriptions — **defer v0.2**."* — Correct, and consistent with BB-R-025. Add D61's caveat: in a single-JVM `lite` this needs no Redis and no broker, but a multi-replica `full` needs sticky sessions or ADR-002.

9. *"Server-scoped (cross-project) subscriptions for super-admin — **defer v0.2**."* — Correct. Note the mechanism (`_filter: "_project eq X or _project pr false"`, gated by `serverScopedSubscriptionsEnabled`) and that Medplum deliberately **skips the access-policy check** for these, which is safe only because creation is super-admin-only.

**Also missing from BB-R-007 entirely (GAPs):** `subscription-success-codes` (SUB-007); `subscriptionAutoDisable` (D60); the 120s outbound timeout; the at-least-once/unordered guarantee (note (e)); the 1000-subscription cap; the pre-commit bot extension (D63).

**BB-R-008 (n8n).** *"Documented recipe: Subscription → n8n Webhook node → n8n HTTP node writing back through `/fhir/R4` with a ClientApplication token"* — sound, and rest-hooks are exactly the right seam. *"Signature verification snippet for the webhook node"* — the snippet must hash the **raw body before JSON parsing** (n8n's Webhook node parses by default; the recipe needs "Raw Body" enabled) or verification fails on any whitespace difference. *"One shipped example workflow: on Patient create, send welcome email"* — needs `subscription-supported-interaction: create` on the Subscription, otherwise it fires on every update too. And the recipe must cover the **delete** shape (empty `{}` body, `X-Medplum-Deleted-Resource` header) or the example workflow errors on deletes. T60. No contradiction, but three omissions that would break the exit test.

**BB-R-016 (Bot SDK).** *"Camel, `@Bot` on a route; triggers: subscription, cron, `$execute`; deploy via CLI"* — the three triggers are the right three, but (a) "cron" should mean the **`Cron` resource**, not `Bot.cronString`, and `Cron` carries an identity (`onBehalfOf`) the brick does not mention (D59); (b) the brick says nothing about **timeout** (10s default), **secrets** (four-source merge), or **identity** (`runAsUser`) — all three are load-bearing (T62, D58); (c) "deploy via CLI" is a genuine divergence worth stating: Medplum bots are uploaded JS compiled to a Lambda/Binary, Big Book bots are compiled JVM classes on the classpath, so `Bot.executableCode`/`$deploy` have no equivalent and `Bot` becomes a pure descriptor. ADR-002 is listed as blocking BB-R-016 — **it does not** (D53); Camel runs in-process on the Cron/delivery threads.

**BB-R-020 (bulk export).** No contradiction found in area 6. The relevant coupling is WRK-010: `AsyncJob` is the durable handle every long-running Medplum worker writes to, with a conditional-update-on-`versionId` protocol so a concurrent cancel is not clobbered. BB-R-020 should reuse that shape, and `MedplumClient` SDK-grade compat (area 1 D4) already requires an `AsyncJob` body at `Content-Location`.

**BB-R-025 (subscription extras).** Contents are right (WebSocket, expression criteria, AuditEvent destination, server-scoped) except that "AuditEvent destination" belongs in v0.1 with BB-R-007.3 (T58), which leaves BB-R-025 as three items. Add the `lite`-only/single-node caveat for WebSocket (D61).

**ADR-002 (event bus) — the headline.** ADR-002 says "requirements blocked on this: BB-R-007 (v0.2 extras), BB-R-016". **Neither is actually blocked.** Medplum's "event bus" is a durable job queue (BullMQ/Redis) plus a single-purpose pub/sub for cross-node WebSocket fan-out. The queue maps to a Postgres table with `FOR UPDATE SKIP LOCKED` and a 1s poller; the fan-out is unnecessary in a one-JVM `lite`. HAPI supplies the matching half natively. **Recommend deciding ADR-002 = none, v0.1 and v0.2, with the reversal trigger written down: multi-replica `full` running WebSocket subscriptions, or bots moving to dedicated worker nodes.** That unblocks BB-R-007 and BB-R-016 immediately and removes a container from `full`.

**ADR-006 (no Redis in `lite`) — confirmed compatible, with a caveat.** Nothing in BB-R-007 v0.1 needs Redis. But note that five distinct Medplum features are Redis-only and therefore need a different home in Big Book if they are ever wanted: subscription failure counters (→ delivery-table columns, D60), the WS active-subscription registry (→ in-JVM map, D61), the FHIRcast store (non-goal), the agent info store (v0.3), and the server registry (non-goal). None of these is v0.1. ADR-006 stands.
